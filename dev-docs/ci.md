# CI, releases, skills and toolchain pins

## CI on pull requests

CI on pull requests is opt-in. `backend.yml`, `backend-vulncheck.yml`, `cli.yml`, `cli-lint.yml`, `cli-contract.yml`, `eval-guard.yml`, `frontend.yml` and `plugin-scanner.yml` listen for `pull_request: types: [labeled]` and every job is gated on `github.event.label.name == 'ci'`, so a PR runs nothing until a maintainer applies the `ci` label (only collaborators can), and applying any other label runs nothing either. Each application validates the PR as it is at that moment: to validate later pushes, remove and re-add the label. The same workflows still run on pushes to `main` that touch their paths (`backend/**`, `cli/**`, `frontend/**`, `skills/traceway/**` for `cli.yml`, `.nvmrc` for `frontend.yml`, `.github/workflows/**`, `.github/actions/**`, `cli/justfile` and `cli/test/evals/**` for `eval-guard.yml`, their own workflow file; `plugin-scanner.yml` runs on every push to `main` because it scans the whole repo), on their daily schedules (the two vulnchecks), and from the Actions tab via `workflow_dispatch`. `cli-evals.yml` (the skill and MCP evals) is the one exception to this pattern: its **only** trigger is `workflow_dispatch`, a person starts every run by hand, the paid shard job waits for a required reviewer on the `evals` environment (the only place `OPENROUTER_API_KEY` lives, never a repository or organization secret; GitHub creates a missing environment without protection, so the preflight refuses a paid run unless `evals` exists with a required reviewer), and `max_cost_usd` is a required input with no default. It must never get a push, pull request, label, schedule, `workflow_run`, `workflow_call` or `repository_dispatch` trigger, no other workflow or composite action may call, dispatch (by file, name or `just eval-dispatch`) or use its environment, and no `just check`/`test`/`default` recipe may run it; `cli/test/evals/internal/guard/triggers_test.go` fails if any of that changes. `cli/test/evals` is its own Go module, which `cli.yml`'s `go test ./...` never reaches, so `eval-guard.yml` runs that test. `twevals run` itself refuses every CI context but a dispatched, approved `cli-evals.yml` job, and locally it needs `yes` typed on a terminal. Validate edits to it (or Dependabot bumps of its actions) with `dry_run: true`, which costs nothing but skips the paid and report jobs, so it does not exercise `download-artifact` or the shard matrix.

## Dependabot, action pins and release workflows

Action versions are watched by `.github/dependabot.yml` (the `github-actions` ecosystem only; npm and Go modules are deliberately not watched there). It opens a weekly PR per group — `actions/*` in one, every third-party action in the other — and deliberately does **not** auto-apply `ci`, so a bot PR passes the same collaborator gate as any other. Label the first-party group to validate it; `golangci/golangci-lint-action` is reachable the same way via `cli-lint.yml`. The rest of the third-party group lands on `release-*.yml`, `benchmark-*.yml` and `traceway-autofix.yml`, which no label reaches — and `workflow_dispatch` is **not** a dry run on the release path: dispatching `release-docs.yml` or `release-website.yml` deploys to Cloudflare for real, and the other `release-*.yml` workflows publish real assets, so dispatching one from an unreviewed bot branch ships it. Validate those by reading the action's release notes instead, and dispatch only where the target is disposable. cli.tracewayapp.com serves `cli/install.sh` and is the one host no workflow deploys: it is uploaded by hand to Cloudflare Pages, so re-upload it after every change to the script. `traceway-autofix.yml` is the in-repo caller of the reusable `autofix.yml` (composite actions `.github/actions/autofix-prepare` and `autofix-publish` around the agent step; `docs/pages/learn/auto-fix.mdx` documents the contract); its `workflow_dispatch` takes an `issue_number` and runs the whole loop from the dispatched branch, which is the one pre-merge validation path for the `claude-code-action` pin — the most privileged action here — but it runs the agent for real, so dispatch it only at a scratch issue. Note too that labelling a PR which touches no gated workflow yields zero checks, which reads like a pass but is silence. Every updatable pin is a bare major tag, so Dependabot only ever proposes major bumps here. The exception is `plugin-scanner.yml`, which pins both actions to commit SHAs because the HOL scanner scores unpinned actions down; Dependabot bumps those SHAs along with their version comments. It uses the scanner config in `.plugin-scanner.toml`, whose `ignore_paths` cover fixtures, demos and build output plus three reviewed production files (the read-only token mask in both `project.repository.go` copies and `KindPassword` in `cli/internal/state/state.go`). The HOL registry's own scan ignores that file and still fails on syntax-highlighter strings in the committed `backend/static/frontend` bundle; that is accepted.

## Node version

**Node's version lives in `.nvmrc`** (a bare major, currently `26`) and nothing else derives it independently: every `setup-node` step uses `node-version-file: .nvmrc`, `flake.nix` reads it for the dev shells, and `release-traceway.yml` passes it to all five image builds as `--build-arg NODE_VERSION`. The Dockerfiles each carry an `ARG NODE_VERSION=<major>` default because a bare `docker build` cannot read `.nvmrc`; that default is the one value that can drift, which is what `scripts/check-node-pins.sh` exists to catch (it also fails on a literal `node:<major>` tag reintroduced in a `FROM`). To move Node, edit `.nvmrc` and the ARG defaults, then run the script. `frontend/package.json`'s `engines.node` is deliberately left as a floor (`>=22`) rather than a pin — it is what npm enforces on consumers, and `node-version-file` pointed at it resolves a range to the *newest* release. `testing/devtesting-nestjs/Dockerfile` is out of scope: it pins the runtime of a sample third-party app, not anything Traceway builds.

## CLI editions, skills mirror and evals

Go/Cobra command-line client for the backend HTTP API (`/cli`), built twice from one source: read-only `traceway`, and `traceway-write` (`-tags write`, own config dir and OAuth client, write commands in `cmd/traceway/edition_write.go`). Skills: `skills/traceway` (read), `skills/traceway-learn` (the product guide, one file per area from `knowledge/learn/`, also served as `traceway://knowledge/learn/*`) and `plugins/tw-write/skills/traceway-write` (write, separate plugin), all generated from `cli/pkg/mcpserver/knowledge` by `just gen-skills`. `skills/traceway-setup` (instrumenting a repository) is written by hand, except `rum.md` and `dashboard-embedding.md`, which the same generator copies in. It also runs on one part of a codebase ("Scoped Runs" in its `SKILL.md`): `/traceway-setup track ai use` follows `ai-usage.md`, whose "Where Traceway differs from the spec" table must stay in step with `buildAiTrace`, `extractConversation` and `extractToolCalls` in `otelcontrollers/trace_converter.go`. Users install them from `tracewayapp/skills`, a generated mirror of `.claude-plugin/`, `skills/`, `plugins/` and `.github/skills-mirror/README.md` that `release-skills.yml` publishes after each CLI release (a job of `release-cli.yml`; logic in `.github/scripts/sync-skills-mirror.sh`, pushed with the `SKILLS_DEPLOY_KEY` deploy key, versions stamped to the release only when content changed). Never edit the mirror by hand. The skill and MCP evals live in `cli/test/evals/` (own Go module, see its README), never under `skills/`: anything in a skill directory ships to users and to the agent under test
