# Backend environment variables

Defaults, limits and sizing notes of every backend variable. `AGENTS.md` lists only the few a local run needs; document a new variable here.

```
JWT_SECRET=<min 32 char secret for JWT signing>   # required in the standalone binary and every server image, including All-in-One. Missing, short and former public keys exit 1 with an actionable message. Docker's environment takes precedence over .env. Embedded Run(opts...) ignores JWT_SECRET (it belongs to the host app there): it uses WithJWTSecret, else TRACEWAY_JWT_SECRET (an explicitly empty value fails validation), else a random key per start, so set a stable value to preserve sessions across restarts. Retired public keys are matched by SHA-256 digest in jwt.service.go so no secret literal sits in scanned code.
DB_TYPE=                              # sqlite | postgres. Defaults to sqlite in every build EXCEPT -tags transactional_pg, where an empty value still selects PostgreSQL. Without that tag SQLite is the only supported main DB (the migration runner applies SQLite-dialect migrations unconditionally), so the default is set once in config.defaultDBType rather than at each DBType call site.
PORTS=80,8082                         # comma-separated HTTP listen ports. Every port is bound up front; a port that fails to bind (typically :80 as a non-root user) logs a warning (and reports via CaptureException when monitoring is configured), and startup only fails if NO port binds. Order is not significant: a listener that later stops serving takes the process down whichever position it holds.
SQLITE_CACHE_SIZE_MB=512              # PRAGMA cache_size of the SQLite TELEMETRY DB in MB, per connection (the main DB keeps SQLite's 2MB default; no effect on DuckDB or ClickHouse telemetry). The telemetry pool opens up to 4 connections (`telemetryMaxOpenConns`, db_sqlite_open.go) and modernc's allocator rounds each ~4.4KB page buffer up to an 8KB slot, so resident memory is about 2x the value per connection: worst case 8x the value, 4GB at the default. A cache fills from ingest, from the retention DELETE scan at startup and every hour, and from reads of pages still in the WAL (write transactions and WAL pages bypass the 1GB mmap window), and it is held for as long as the pooled connection lives. At the default a 1GiB container is OOM-killed on a 24h dashboard or under sustained ingest. Rule of thumb: container MB / 32 (16 for 512MB, 32 for 1GB, 64 for 2GB). A non-positive or unparsable value falls back to 512 (`config.SizeMB`). The effective value is logged at startup, and the embedded `Run(opts...)` path honors the env var through `applyEnvOverrides`. Operator docs: `docs/pages/server/sqlite.mdx#memory-sizing`.
SQLITE_PATH=                          # main DB path, defaults to ./traceway.db in the working directory. The telemetry DB derives from it (_telemetry.db, or _telemetry.duckdb under -tags telemetry_duckdb).
BOOTSTRAP_FILE=                       # YAML/JSON file that pre-configures a fresh instance (cmd/bootstrap.go, run from run() after the startup migrations, standalone binary and server images only, never embedded Run(opts...)): one organization, users with roles and password or bcrypt passwordHash, projects with operator-chosen token/sourceMapToken (16-128 chars of [A-Za-z0-9._~-], unique across the file; an omitted token is generated and printed with LogfLocal). Applied only while the main DB has no organization and no user (isFreshInstance), in one transaction behind pg advisory lock 824737010 so replicas starting together apply it once; afterwards every start skips it with a log line and never reads the file. Strict decoding (unknown fields fail with their line), every validation problem is reported at once, and a bad or missing file on an empty DB exits 1 through exitOnMisconfiguration with nothing created. Projects go through ProjectRepository.CreateWithOrganizationAndTokens + controllers.PopulateDashboardsOnCreate, and PostRegistrationHooks run for the first owner, so the result matches a dashboard registration. Operator docs: docs/pages/learn/preconfigure.mdx.
APP_BASE_URL=                         # public origin of this server (e.g. https://traceway.example.com). Used as the OAuth issuer / device verification URL and SSO redirect base, and to absolutize the deep links in notifications. If unset, the device-auth + well-known endpoints derive it per-request from the Host / X-Forwarded-* headers; set it explicitly behind a proxy that doesn't forward Host.
TRUSTED_PROXIES=                      # comma-separated IPs/CIDRs whose X-Forwarded-For/X-Real-IP gin trusts for c.ClientIP() (every per-IP rate limiter keys on it, and `/api/report` stores it on every session as `client.ip`). Unset = loopback only, so no peer can spoof its IP. Private ranges are deliberately NOT trusted by default: on a Docker/k8s network every peer has a private address, the clients included when the port is published directly, so trusting RFC1918 would let any of them forge XFF past every per-IP limiter. Set it to the CIDRs of whatever sits in front (a proxy container's compose network, the ingress pod range, the CDN ranges); otherwise every visitor shares one rate-limit bucket keyed on the proxy. The value REPLACES the default, so it must name every hop in the chain, not just the outermost (a CDN-only list leaves a private ingress untrusted and disables XFF entirely); `*` trusts every peer. A malformed entry exits 1 at startup with a FATAL message, before the database is opened (`trustedProxyNets`, cmd/run.go). The first request carrying X-Forwarded-For/X-Real-IP from a peer outside the list logs a one-time warning naming that peer (`warnOnUntrustedForwardedFor`, cmd/run.go), which is how a forgotten proxy hop shows up. Parsing lives in `Cfg.TrustedProxyList` (config.go), covered by config_test.go.
TRUSTED_PROXY_HEADER=                 # optional header taken verbatim as the client IP on every request (gin TrustedPlatform: X-Real-IP behind ingress-nginx, CF-Connecting-IP behind Cloudflare); it wins over TRUSTED_PROXIES and turns the untrusted-forwarder warning off. Only safe when every request provably passes through a proxy that overwrites the header.
UPLOAD_MAX_CONCURRENT=4               # concurrent /api/sourcemaps/upload + /api/symbols/upload requests; excess waits 30s then gets 503. Separate from INGEST_MAX_CONCURRENT so a CI upload burst cannot starve telemetry ingest. Each upload holds a whole file in memory while parsing, so this bounds peak upload memory at roughly concurrency x largest file. It is a count-based gate, not a memory budget: on a memory-capped container size it from the limit rather than trusting the default. Same gate and bounded waiting room as ingest, its own instance. The source-map warm-up that follows an upload (`services.GenerateTWArtifacts`) runs outside this gate on its own 2-worker pool with a 2048-job queue (the queue holds keys, so the workers are what bound the work; it must fit whole uploads, since one code-split build is a few hundred jobs, a job per bundle plus one per debug-id alias): the stale `.tw` artifact is deleted and the cache invalidated inline, the rebuild is queued, identical pending jobs are coalesced, and a full queue drops the warm-up (rate-limited `CaptureException` whose message names the project but no file, so drops stay one issue; counted in `traceway.sourcemap.warmup_dropped.delta`, backlog in `traceway.sourcemap.warmup_backlog`) because lookups build a missing artifact on demand anyway. The upload handler itself stores files with bounded concurrency (`sourceMapStoreConcurrency` = 8 files at a time per upload, and a process-wide 128MB budget of file bytes in flight, `sourceMapStoreBudget`); `keyedWriteOrder` keeps the result equal to writing in upload order when two files share a storage key, and an oversized file is rejected before anything is stored.
REPORT_MAX_BODY_MB=64                 # cap on the DECOMPRESSED /api/report and /api/profiles/ingest body (middleware.UseGzip bounds both the raw and gunzipped stream, so gzip cannot raise it). Deliberately far above the 10MB OTLP cap: session-replay frames carry rrweb segments and are a different size class, and the shipped browser SDKs re-queue a rejected batch forever, so a reachable cap is a permanent wedge rather than shed load. It is reached anyway (the failed batch is put back and merged with new data, so it only grows), and a 200 is the one status that makes a 1.x SDK drop a batch, so `/api/report` answers an overrun with 200 + `X-Traceway-Discarded: body_too_large` after reading the rest of the upload off the wire without keeping it (`middleware.DiscardOversizedReport`, counted in `traceway.ingest.oversized_discarded`, span attribute `ingest.oversized_discarded`); it falls back to 413 when more than the cap is still unread. `/api/profiles/ingest` overruns answer 413. `UseGzip` also meters the body (`ingestBodyMeter`): the request span carries `ingest.body.wire_bytes`, `ingest.body.network_ms` (time blocked on the client, including a read-ahead before the gate, see `INGEST_PREFETCH_BUDGET_MB`; the OTLP routes record the same two through the prefetch or `middleware.MeterRawIngestBody`), `ingest.body.decoded_bytes` and `ingest.body.gunzip_ms`, every ingest request carries its own `ingest.<table>.convert_ms`, `.store_ms` and `.rows` (`monitoring.RecordIngestBatch`, which also feeds the `traceway.ingest.batch.*` maxima), UseClientAuth stamps `project_id` and `organization_id`, `traceway.ingest.oversized_discarded` is tagged `project_id`, and `report.parse_body` has the children `report.read_body` and `report.decode_json`. Bind rejections are counted in `traceway.ingest.body_rejected` (tag `reason`), the longest client-blocked read per interval in `traceway.ingest.body.network_ms`, and every admission gate reports `traceway.admission.in_use_pcnt` and `traceway.admission.wait_ms` under its `gate` tag (`ingest`, `upload`, `opamp`).

CLICKHOUSE_DATABASE=traceway
CLICKHOUSE_USERNAME=default

# DuckDB telemetry backend (only with -tags telemetry_duckdb build; see "DuckDB Telemetry Backend" in AGENTS.md). The embedded Run(opts...) path honors these three and DUCKDB_RETENTION_DAYS through applyEnvOverrides.
DUCKDB_MEMORY_LIMIT=                  # e.g. 4GB. Unset = DuckDB auto-tunes (~80% RAM). Set explicitly in memory-capped containers to avoid OOM.
DUCKDB_THREADS=                       # e.g. 4. Unset = DuckDB auto-tunes (= cores). Cap in constrained/shared environments.
DUCKDB_CHECKPOINT_THRESHOLD=          # e.g. 256MB. Unset = DuckDB default (16MB). Raise under sustained ingest to reduce WAL checkpoint stalls; costs a larger WAL and longer restart replay.

# Ingest admission gate (all telemetry ingest endpoints: /api/report, /api/profiles/ingest, /api/otel/*)
INGEST_MAX_CONCURRENT=                # max concurrently processed ingest requests. Unset = 4×CPU cores (`middleware.IngestSlotsPerCPU`, which a binary built on `Run` may raise before calling it), min 4 (a slot is held while the store inserts, so it is mostly waiting, not CPU; a body the prefetch could not read ahead is also uploaded under it). Bounds ingest memory so overload sheds load with 503s instead of the process being OOM-killed (on DuckDB an OOM death is followed by a minutes-long WAL-replay stall on restart). The gate (`newAdmissionGate` in `middleware/ingest_admission.go`, a buffered-channel semaphore) also bounds waiters at 16×capacity (min 64, `admissionWaitersPerSlot`; a waiter holds a connection and a timer but no body, so the room is sized by what the slots can serve inside the wait window, not by memory); beyond that a request gets an immediate 503 instead of parking a goroutine and a timer for the wait window.
CLIENT_METRICS_MAX_CONCURRENT=        # concurrent OTLP metrics requests of client (browser/mobile) projects; unset = 64x CPU cores, min 256. Own gate (`client_metrics`, `middleware.MetricsAdmission` picks it by `clientlogs.IsClient`), no waiting: over it an immediate 503 + Retry-After: 60, and the SDK sends the payload once more on the next page load. A slot costs one body of at most 64 KB and is held while a slow phone delivers it, hence the high default.
CLIENT_METRICS_FLUSH_SECONDS=10       # how often the in-memory client metrics cells are written (see telemetry-internals.md). A crash loses at most this much; the binary flushes on SIGTERM/SIGINT.
CLIENT_METRICS_MAX_CELLS=500000       # cells held between two flushes; bounds the aggregator's memory. New cells past it are dropped and counted (reason `memory`).
CLIENT_METRICS_DEDUP_MB=16            # memory of the filter that recognizes a payload a device sends a second time (`clientmetrics/dedup.go`): two Bloom generations of a day each, half the memory each. Fixed size, per instance.
GEOIP_COUNTRY_HEADER=                 # header that carries the ISO 3166-1 alpha-2 country of every request (CF-IPCountry, CloudFront-Viewer-Country). Trusted as it is, so only safe when every request passes a proxy that overwrites it. Wins over GEOIP_DB_PATH.
GEOIP_DB_PATH=                        # country database in MaxMind DB format (GeoLite2-Country, DB-IP country lite), read into memory and re-read within an hour of being replaced. Looked up with c.ClientIP(), so TRUSTED_PROXIES must be right. Neither set = client metrics carry no `country`. An unreadable file logs a warning and reports an exception; the header, if set, still works (`app/geoip`, `services.ClientOf`).
INGEST_ADMISSION_WAIT_SECONDS=5       # how long a request may wait for a slot before the 503 + Retry-After; 0 = reject immediately when saturated
INGEST_PREFETCH_BUDGET_MB=64          # memory for reading ingest bodies in full BEFORE the ingest gate (`middleware.PrefetchIngestBody`, `ingest_prefetch.go`; `PrefetchReportBody` on the UseGzip routes, `otelcontrollers.PrefetchBody`/`PrefetchMetricsBody` on OTLP, client metrics projects skipped), so a slow upload never holds a slot. Only bodies with a Content-Length within the route cap and at most a quarter of the budget, while the budget has room; anything else is read under the slot as before (span attribute `ingest.body.prefetch_skipped` = no_length/too_large/budget_full, counter `traceway.ingest.prefetch.skipped`, gauge `traceway.ingest.prefetch.budget_used_pcnt`). The read is an `ingest.read_body` span under the route's own body guard, and a failed read is rejected through `RejectIngestBindError`. 0 = off.

OPAMP_MAX_CONCURRENT=                 # concurrent OpAMP polls; unset = 4x CPU cores, min 8. Own admission gate (separate from INGEST_MAX_CONCURRENT so polls and ingest cannot starve each other); rejections answer 503 + Retry-After: 60.

# Notifications
NOTIFICATION_POLL_SECONDS=60          # polled rule evaluation interval; minimum 5, invalid values fall back to 60
ONCALL_POLL_SECONDS=30                # on-call escalation worker interval; minimum 5, invalid values fall back to 30. Kept separate from NOTIFICATION_POLL_SECONDS so raising rule-evaluation intervals never delays paging. A buffered Wake() channel makes freshly opened pages notify L1 near-instantly regardless of this interval.
OUTBOX_POLL_SECONDS=15                # notification outbox drain interval; minimum 5, invalid values fall back to 15. The outbox (backend/app/outbox, notification_outbox table in the main DB) is the persist-then-send layer for ALL notifications: rule dispatch and the escalator only enqueue (with an adapter-config snapshot) inside their transactions; the drain worker sends with retries (backoff 1m/5m/15m/60m, 5 attempts, then terminal failed + CaptureException). Crash-safe at-least-once: stale 'sending' rows are reclaimed after 5 min, cancelled rows can never resurrect (guarded status transitions), ack/resolve cancels queued page deliveries via outbox.CancelByKey. Cooldown and event-rule dedup record at enqueue commit (the durable promise), and fired_notifications is written at the terminal outcome. /api/health/deep exposes an `outbox` block; `traceway.outbox.*` metrics are emitted when monitoring is on; terminal rows are pruned daily (sent/cancelled 7d, failed 30d).
SLO_POLL_SECONDS=60                   # SLO worker interval (backend/app/slo): recomputes the last 10 minutes of every enabled SLO into the telemetry `slo_buckets` table (every 15 minutes, in a slot derived from the SLO id and decided against its persisted `computed_at` (`passDue`, `slo/schedule.go`) so passes are spread over ticks and a restart or shard move neither skips nor bunches them, the other kinds also recompute the last 75 minutes, for long requests and retried exports, and session and task SLOs their exception slack plus 25 minutes, since a crash or failure lands after the bucket of its start; once a day session SLOs recompute the last 72 hours through the gap fill, for native crashes uploaded on the next launch), computes `SLO_COMPUTE_WORKERS` (default 4, max 64) SLOs at a time with a per-SLO `SLO_COMPUTE_TIMEOUT_SECONDS` (default 30; a timed-out SLO keeps its old snapshot and resumes from `last_bucket_at` on the next tick), works through the SLOs in groups of 200 so memory stays bounded and each group's buckets go out in one batched insert stamped at write time (ClickHouse makes a part of every insert); the window sum is incremental (`slo/snapshot_cache.go`): the part of the window before an anchor 7h back (73h for session SLOs) is cached in memory and only loses the buckets that slide out, the recent part is read every tick, and the whole window is re-read when the cache is missing, the revision or `computed_at` differs from what this process wrote (an edit, or another instance computed it), a bucket was written before the anchor, or once an hour in the SLO's slot; an SLO with no `last_bucket_at` (new, or reset by a definition change) has its buckets deleted by the worker before anything is written, never by the controller, so a delete cannot land after the new buckets; backfills older history in 6h chunks (24h for metric SLIs so ClickHouse reads the 1m rollups) under one 5s budget shared by every SLO of the tick (start rotated per tick), records an outage longer than the 24h catch-up as a `gap_from`/`gap_to` range it fills under the same budget, writes the snapshot columns on `slos` only while the row is still at the `revision` it loaded (an edit during a tick makes it drop its result; the reset of a definition change clears the buckets on the next tick), on Postgres splits the SLOs over 64 shards (`id % 64`) leased per instance through `slo_workers` (heartbeat) and `slo_shard_leases` (pg/0157, pg/0158; `slo/shards.go`): each tick an instance renews its leases, releases any above its fair share (`ceil(64 / live instances)`) and claims free or expired ones, renews again between groups, leases last max(5 min, 3x the poll) and a crashed instance's shards move once it ages out, while one stopped by SIGTERM deletes its leases and worker row first (`slo.Stop`, run by `cmd.Shutdown`), so a deploy's new instance takes every shard on its next tick instead of computing nothing for five minutes, shard 0's owner runs the daily prune; SQLite owns all shards, counts metric slices without samples as bad only from `sli_since` (set on create and on every definition change), rounds slo_burn_rate windows up to whole slices and clears it when either window drops below the threshold, slo_budget_consumed reads the snapshot's `budget_remaining` instead of re-summing the window, rule state moves through `NotificationRuleStateRepository.Transition` (a conditional update, so two instances never both notify), both slo_* rules hold their state while the SLO has no `last_bucket_at` (a definition change being recomputed) so a reset never sends a false recovery, a recovery notice does not record a cooldown fire, prunes buckets older than 120 days daily, and reports the `slo` block of `/api/health/deep` (totals incl. timeouts, `runningForSec`, owned shards and instances, the last tick's phase timings with its slowest SLO, and `freshness` read from the main DB: enabled, stale > 5 min, max staleness, backfill pending), which `monitoring.StartSLOReporter` emits every 30s as `traceway.slo.*` metrics when self-monitoring is on (documented in `docs/pages/server/capacity-monitoring.mdx`); minimum 5, invalid values fall back to 60. `slo.Wake()` runs a tick right after an SLO is created or changed. Buckets are deliberately NOT in the telemetry retention list; slo_* notification rules read them (never raw data) and keep their firing state in `notification_rule_states` so they can send recovery notices across restarts.
SLO_COMPUTE_WORKERS=4                 # SLOs computed at once per instance (max 64)

# Synthetics (synthetic uptime monitoring: backend/app/synthetics, /monitors frontend route)
SYNTHETICS_POLL_SECONDS=15            # scheduler tick for due checks; minimum 5, invalid values fall back to 15. The scheduler enqueues due checks into the check_runs queue (main DB, outbox-style guarded claims, advisory lock 824737004) and records expired queued runs as `missed` in telemetry — a probe is never executed late. In-process executors claim http/tcp runs always, browser runs only when mode=embedded.
SYNTHETICS_BROWSER_MODE=off           # off | embedded | remote. Browser checks are real @playwright/test specs executed by spawning Node against a harness dir (no npm/npx at runtime; allowlisted env so user scripts never see server secrets). `embedded` requires the :browser image (Dockerfile.browser, DuckDB base + Node + Chromium) and fails fast at startup otherwise; `remote` queues browser runs for traceway-runner binaries that long-poll /api/runners/poll authenticating with SYNTHETICS_RUNNER_SECRET. Hard-blocked in cloud mode (startup panic + 422 at check creation).
SYNTHETICS_BROWSER_SANDBOX=auto       # auto | bwrap | off. Isolation for the Playwright subprocess in embedded mode and in traceway-runner. The env allowlist alone does not contain a spec: node runs as the same uid as its parent, so unconfined it can read the parent's /proc/<pid>/environ (the runner secret), overwrite node_modules in the shared harness to backdoor later runs, and read a sibling run's directory. `bwrap` gives each run its own pid/ipc/uts/user namespace with a fresh /proc, a read-only harness bind with only that run's dir writable, an empty tmpfs over the .runs container so sibling run dirs are hidden (not exposed by the wholesale harness bind), and no /etc beyond DNS/CA/locale (so a secret in the unit file or EnvironmentFile is unreachable); the network namespace stays shared since probes must reach the internet. `auto` uses bubblewrap when the host can and degrades to off with a warning; explicit `bwrap` fails fast at startup instead. Resolved once via browserexec.ResolveSandbox, which probes by running `node --version` through the real bind set.
SYNTHETICS_RUNNER_SECRET=             # shared bearer credential for the operator's runner fleet; required for remote mode (fail-fast at startup). Runners are deployment infrastructure, NOT tenant entities: no dashboard CRUD, no per-runner tokens. A runner self-registers a liveness row in synthetic_runners under its X-Traceway-Runner-Name on first poll (upsert throttled to 1/min via an in-memory cache; claim identity is "runner:<name>"). Rotation = change the secret + restart runners. Runner-side env: TRACEWAY_URL, TRACEWAY_RUNNER_SECRET, TRACEWAY_RUNNER_NAME (default hostname), RUNNER_WORKERS (default 2, max 16), and optional TRACEWAY_RUNNER_MONITORING (<project_token>@<url>; a legacy `/api/report` suffix is accepted) which self-instruments the runner over OpenTelemetry through `app/traceway` (see "Self-monitoring" in AGENTS.md): Go runtime metrics, a CONSUMER `browser_run` task span per executed run (attributes check_id/run_id/status, service.name = runner name), and exceptions on infra failures recorded on that task (start/report errors, per-job panics recovered without killing the worker).

# Metric rollup repair (ClickHouse only; see telemetry-internals.md)
METRIC_ROLLUP_REPAIR=                 # "true" merges the rollup rows of the last year that unsorted tag maps split into several, in the background, a partition at a time; "false" or unset leaves it off. Runs at startup; ends after the first pass that leaves nothing behind, retries an hour after a failed pass or a skipped partition. May be set on every instance (advisory lock). No effect on SQLite or DuckDB telemetry. Needs free disk of about twice the largest part of a partition, and briefly doubles `sum`/`count` of the series being merged.

# V2 trace tables move-over (see telemetry-internals.md)
V2_MOVE_OVER=                         # "true" copies the legacy trace tables into the V2 tables, in the background, newest day first. Runs at startup and one hour after each pass; resumable (progress in the transactional DB v2_move_over_days, sqlite/0077 + pg/0143), so it can stay set. Finish upgrading old writers before enabling it: completed source-table/date pairs are skipped. With several backend instances set it on exactly one. On SQLite and DuckDB it stops at the telemetry retention window, since older days would be pruned at once.
V2_MOVE_OVER_OLDEST=                  # optional YYYY-MM-DD; days before it stay in the legacy tables. An unparsable value logs and does not start the move.
V2_MOVE_OVER_WORKERS=1                # source days copied concurrently inside the one enabled instance (max 16; invalid/non-positive = 1). Each day keeps table order; days are scheduled newest first. Increase to 4 for parallel backfill when the telemetry DB has spare capacity. Progress rows and logs update after successful batches roughly every 10s; slow queries/inserts can delay updates. Errors cancel and join all workers before the next hourly pass.
```
