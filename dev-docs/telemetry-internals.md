# Telemetry internals

The deep reference for three areas whose rules `AGENTS.md` only summarizes: trace storage, client metrics and the ClickHouse metric rollup repair.

## Trace storage (V2 tables)

A trace is a trace and a span is a span. Five tables hold traces on every backend: `spans_v2`, `endpoints_v2`, `tasks_v2`, `ai_traces_v2`, `exceptions_v2` (migrations `ch/0085`-`0089`, one `CREATE TABLE` each; `sqlite_telemetry/0025_create_v2_tables`; `duckdb_telemetry/0005_create_v2_tables`). The legacy tables (`spans`, `endpoints`, `tasks`, `ai_traces`, `exception_stack_traces`) hold history only: nothing reads or writes them except the move-over and retention. `migrations/v2_tables_test.go` holds the V2 migrations to `CREATE TABLE`/`CREATE INDEX` on `_v2` tables only.

- **Ids.** Every row carries the ids its span arrived with, as lowercase hex: `trace_id` (32 characters), `span_id` (16 for OTel, 32 for a native run or span), `parent_span_id` (`''` for a root). Entities and exceptions keep a UUID `id` for URLs and notifications. For OTel rows it is `otelOccurrenceID` = `uuid.NewSHA1(projectId, traceId + spanId)`, so a retried export produces the same id. Nothing about identity lives in the attributes JSON, and ingest adds no `traceway.otel.*` keys.
- **Sessions and profiles** carry the same canonical ids: `sessions.trace_id` is a non-null string (empty = no association) and profiles have `trace_id` / `span_id`.
- **Ingest** (`otelcontrollers/trace_converter.go`) validates and indexes spans once per resource, then returns canonical spans, entity projections, exceptions and the invalid-ID count together. Each span is promoted when its own kind and attributes make it an entry point, and each exception event becomes an `exceptions_v2` row with the span's trace id and span id. Canonical span attributes are rendered directly from the OTLP payload at storage time. Trace and log JSON IDs are normalized at the decoder boundary (`otelcontrollers/otlp_json.go`); converters consume decoded bytes without a UUID/base64 repair roundtrip. No owner resolution, no caches, no reads. `trace_type` on an exception is stored only when that span itself was promoted (native rows say it themselves). Every entity is recorded at its span's **start**, OTel tasks included. Spans are inserted **before** the rows promoted from them, and a transient storage error answers 503 + `Retry-After` (`abortIngestStorage`, `telemetry.IsTransientStorageError`) so OTLP exporters retry. Retries are append-only; the span reader deduplicates per span.
- **Entry points.** An HTTP SERVER span becomes an endpoint unless a local span above it already is one (`isEntryPoint`), which is what keeps a SERVER span nested under another (Next.js under the HTTP instrumentation) from counting as a second request. This is the one check that looks beyond the span, and only inside its `ResourceSpans` block. The walk up the parent chain stops at a remote parent per the OTLP span flags (`0x100` has-is-remote, `0x200` is-remote) and at a CLIENT or PRODUCER span. A missing parent has an unknown kind even when flags mark it local, so it cannot suppress an HTTP entry point. Separately exported nested HTTP spans can create extra projections.
- **Native `/api/report` rows** go to the same tables (`clientmodels.ClientTrace.RootSpan`, `ClientSpan.ToSpan`): a run is stored as the root span of a trace, `span_id` = the run's id, `trace_id` = the run's id. Its spans hang under it, and a native exception sits on the run's span. The report wire format is unchanged: an exception's `traceId` names its owning run, `distributedTraceId` is ignored on runs, exceptions and sessions until the JS SDK supports canonical trace propagation, and native run/span IDs remain UUIDs.
- **`spans_v2`** keeps the lossless payload of accepted OTLP spans (`resource_pb`/`scope_pb`/`span_pb` on ClickHouse, `otlp` on SQLite and DuckDB; `shared.AssembleOtelPayload` joins them back) next to the readable columns, built once by `OtelSpanRow.NestedValues`: `span_attributes` is a string map (a `Map(LowCardinality(String), String)` on ClickHouse, a JSON object elsewhere) filled by `shared.StringAttributes` the way the OpenTelemetry Collector's ClickHouse exporter does it, and `resource`, `scope`, `events`, `links` are JSON text. A span that did not arrive as OTLP gets a payload synthesized from its available fields (`NewOtelSpanRow`), including string attributes and service/scope metadata. Native UUID span IDs remain in the API; their exported span/parent IDs use a stable eight-byte hash mapping with original IDs carried in `traceway.native.*` attributes. Native synthesis cannot recover metadata never sent by the SDK. On ClickHouse `recorded_at` is `DateTime64(6)` on endpoint/task/exception tables and `DateTime64(3)` on AI traces (the waterfall's origin is the entity's `recordedAt`) and a plain partition time on `spans_v2`.
- **Reads.** A waterfall is `spans_v2` by project and trace, the subtree under the entity's `span_id`: `telemetry.SpanRepository.FindGraph(ctx, shared.NewSpanLookup(projectId, traceId, spanId, recordedAt))`, answered by `shared.FindOtelGraphs` (topology first, attributes second). A limit never fails the page: the result carries `spanGraphStatus` (`complete`/`partial`/`unavailable` plus reasons) and spans may have `attributesOmitted`. The subtree includes spans that are entities of their own, such as a CONSUMER span started inside the request.
- **Distributed trace card** (`controllers/distributed_trace.controller.go`, `POST /api/distributed-traces/:traceId`, hex or dashed). `FindByTraceIds` on the four entity and exception repositories matches only `trace_id IN (...)` across projects the user can open. Every returned node belongs to the requested trace; W3C propagation makes browser and backend share that identity. Nodes are nested by one read of the trace's topology, without attributes (`SpanRepository.FindTraceParents`): each node walks up until it meets another node's span (`parentEntitySpanId`). An exception is attached to the nearest node above its span, else it is a node of its own.
- **Exceptions.** A detail page reads `exceptions_v2` by trace and keeps those on its own span or a span of its subtree (`findOccurrenceExceptions`). `telemetry.FindExceptionOwner` does the walk the other way, from the exception's span up to the nearest endpoint, task or AI trace of the same project. The exception responses return it as `relatedEntity`, and notification text uses it (`resolveExceptionOwner`). A failed task, for the task failure rule, is a task with an exception on its own span.
- **Every span read is bound in time.** A lookup reads `recorded_at` within 24 hours either side of the entity it starts from (`shared.OtelLookupWindow`, `shared.TraceWindowBounds`; entity lookups by trace id use 48 hours), which on ClickHouse prunes the read to a few daily partitions. A lookup that names no time is anchored on now. The cost is deliberate: a span recorded more than 24 hours away from its entity is not shown on that entity's page. Tests that store spans under a fixed timestamp must pass that timestamp as the lookup time, never the wall clock.
- **Orphans.** A span whose parent never arrived has no place in a subtree. The entity promoted from the trace's root span (the one with no parent) shows such spans of its own project and trace, so they are visible exactly once, and the waterfall marks them "Parent span is unavailable". Once the parent arrives they nest normally.
- **Span explorer** (`controllers/span_explorer.controller.go`, frontend `/spans`). `POST /api/spans/search` (App auth + project access) pages the spans of a project in a required time range of at most 31 days. Body: `fromDate`, `toDate`, `orderBy` (`start_time desc|asc`, `duration desc|asc`), `serviceName`, `name` (case-insensitive contains), `traceId` (32 hex), `kind` (0-5), `status` (0-2), `minDurationMs`, `maxDurationMs`, `attributeFilters` (at most 10 `{key, value, exclude, contains, exists}` filters on `span_attributes` with the operators of the logs page; a value operator needs a value, since a ClickHouse Map answers `''` for a missing key, and the negated forms keep spans without the key), `pagination`. The response adds `services`, the busiest 100 service names in the range. Validation problems and a search that hits its 15s read limit both answer 422, which the page shows as a warning callout, not an error. The query builder is `shared.OtelSearchQueries` with one small dialect struct per backend; SQLite and DuckDB use it as it is. ClickHouse has its own (`shared.OtelClickHouseSearchQueries`, `OtelClickHouseChartSource`, both over `otelClickHouseMatchingSpans`), because the generic winner sort costs memory for every span in the range (about 633 MB for 4M spans with nothing but keys in it, and with a filter it also carried the attribute map: a day of 4M spans ran out of the search's 1 GB), although a span is stored twice only when an export was retried. It first finds the spans stored more than once by grouping `cityHash64(trace_id, span_id)` (about 135 MB for 4M spans); every other span is its own winner and is filtered as it is read, and only the duplicated spans go through the winner sort, where the filters' verdict and a chart's value are computed per stored version and appended as the last sort keys so ClickHouse computes them before the sort (`TestOtelSpanSearchFiltersTheWinningVersion`, `TestOtelSpanChartAttributeOfTheWinningVersion`). A hash collision only sends a span through the sort, so results stay exact. The filters go in an explicit `PREWHERE`: left alone, ClickHouse moves the hash test ahead of them and hashes every span before a selective filter has removed any (0.5 s became 1.5 s on 4M spans). Measured on 4M spans a day: every search and chart about 137 MB, broad filters about 2 s, selective about 0.8 s. When every span is stored twice (a doubled exporter pipeline), the cost is close to the old winner sort and selective searches take about 2 s per 1M spans. The page is found in two steps: the spans of the page are chosen by what the order reads, and their topology is read afterwards. `POST /api/spans/series` and `POST /api/spans/distribution` chart the same selection (`SpanFilterRequest`, the search body without `orderBy` and `pagination`): the duration in milliseconds, or with `attribute` one numeric span attribute, through `shared.OtelChartSource` (ClickHouse: `OtelClickHouseChartSource`), which reads the same retry winners as the search (so the chart's count equals the table's) and adds an existence filter for an attribute chart. `ChartPanel` reloads when the content of its selection changes, not on every new object, so paging or sorting the table sends no chart request. A duration distribution whose maximum is at least `shared.ChartLogScaleRatio` (20) times its minimum gets log-scale bins (`shared.NiceLogScaleBins`, `scale: "log"`, `binWidth` 0). The charts share the search's 20s limit and 422 answer; they are not agent routes. The page opens the duration chart unless the URL says `chart=none`; `chart=attr.<key>` charts an attribute (`readSpanChart` in `utils/span-explorer.ts`). The span popover of every waterfall links each attribute into the explorer (`spanExplorerHref`). The `searching spans` span of self-monitoring carries the search's shape (`spans.range_seconds`, `spans.order_by`, `spans.*_filter`, `spans.attribute_filter_count`, `spans.total`, `spans.read_limit_hit`), never the filter values. `GET /api/spans/traces/:traceId?at=<RFC 3339>` returns the whole trace (`shared.FindOtelTrace`) and 404s when nothing is recorded within 24 hours of `at`. **It reads every project of the current project's organization**, not only the current one (`organizationProjects` in the controller, one lookup per project, one query): services of one trace usually report to different projects, and organization membership is what grants read access to each. Other organizations of the same user stay out. The response names the projects that hold spans (`projects`), each span keeps its own `projectId`, the page links spans across projects (`buildSpanTree(..., acrossProjects)`), and the popover loads attributes with the span's own project id. Search stays per project. Unlike the detail pages it sends **no attributes**: each span carries only `dbStatement`, a 240 character preview of `db.query.text` (or `db.statement`) that the row label needs, and the page fetches one span's attributes from `GET /api/spans/traces/:traceId/spans/:spanId/attributes?at=` when its popover opens. One query serves both cases of the row cap (`FindTraceOutline` on each backend, ordered by `shared.OtelImportanceOrder`): under `MaxOtelGraphRows` every span comes back, over it the `LIMIT` keeps errors first, then entry points (no parent, SERVER or CONSUMER), then the slowest, and the status is `partial` with reasons `row_limit` and `most_important`. Ordering by duration also tends to keep the path above a span, since a parent usually outlasts its children. The backend gzips the response: `compressResponses` (`cmd/static_assets.go`, wrapping the whole router in `cmd/run.go`) compresses every response of at least 1 KB for a client that accepts gzip, except the ingest routes (`/api/report`, `/api/otel/`, `/api/profiles/ingest`), `/api/runners/`, `/mcp` and `text/event-stream`. 20,000 spans are about 13 MB of JSON and roughly 1 MB gzipped. The sidebar shows Spans and Logs for browser projects (`BROWSER_FRAMEWORKS` in `projects.svelte.ts`) and hides both for mobile projects (`hiddenForMobile` in `app-sidebar.svelte`); Dashboards is shown for every frontend project, browser and mobile, since their performance arrives as client metrics (see "Client metrics" below); the routes themselves still work for links into a trace.
- `GET /api/otel/spans/:traceId/:spanId?at=<RFC 3339>` (App auth + project access) returns one stored span (16 or 32 hex span id) as an OTLP `ExportTraceServiceRequest` protobuf. `at` is required (400 without it) for the same 24 hour rule.
- **Frontend: large traces.** A trace over 500 spans opens with every node that has more than 50 children folded (`initiallyCollapsed` in `utils/span-tree.ts`); smaller traces open fully expanded. A folded row shows a pill with the number of hidden spans and an error marker when one of them failed, and the header has Expand all and Collapse all. The waterfall keeps what was clicked as the difference from that default, so there is no effect to reset. Pages must hold span payloads in `$state.raw`: a deep `$state` proxy over 20,000 spans took four minutes to read in the browser, against 0.4 seconds raw. The payload is only ever replaced, never edited.
- **Frontend.** `span-waterfall.svelte` names the service on each row and colours bars by service once a trace crosses services (one colour per row otherwise), marks error spans and missing parents, renders rows 500 at a time so a 20,000 span trace cannot stall the page, caps the name column to half the visible width on narrow screens, and links to the whole trace in the explorer. The span popover shows service, kind, status and scope (`utils/span-fields.ts`). Span payloads are held in `$state.raw`. The tree is keyed `traceId:spanId` (`utils/span-tree.ts`), and the issue pages build their related entity from the backend's `relatedEntity`.
- `GET /api/health/deep` also reports `spanPartitionTimeFallbacks`: spans whose source start was missing or unrepresentable, so their partition time is the ingest time (`shared.OtelStorageTimes`).
- **Move-over** (`repositories/telemetry/move_over.go`, started by `retention.startMoveOver` when `V2_MOVE_OVER=true`). Copies the legacy tables into the V2 tables inside the backend (an embedded DuckDB file cannot be opened by a second process), UTC days scheduled newest first with configurable concurrency (`V2_MOVE_OVER_WORKERS`, default 1, cap 16), each day keeping table order, recorded in the transactional DB `v2_move_over_days` (migrations `sqlite/0077`, `pg/0143`) so it stops and resumes. The scheduler runs at startup and one hour after each pass ends, including failures; passes do not overlap. `started` is committed before telemetry writes, `done` after all batches succeed, with no main-DB transaction held during the copy. `moved_rows` counts scanned source rows in the current attempt, including already-copied rows skipped during recovery; it resets on resume. Progress and logs update after successful batches roughly every 10s (a slow query or insert can delay this). A failed worker cancels the pass, and all workers are joined before return; separate backend instances are still not coordinated. Finish upgrading old writers first: completed table/date pairs are not revisited. A resumed day skips rows already written. It reads through `LegacyRepository` (one per backend, the old ids parked in the V2 model fields, see `shared/legacy.go`) and writes through the V2 repositories, so the id mapping lives in one place: the trace id comes from the `traceway.otel.trace_id` attribute the old ingest kept, else the old `distributed_trace_id`, else the row id; an old zero padded span UUID becomes its last 16 hex characters; spans and exceptions find their old owner by id, nearest in time, and take its trace; each entity also gets its own span row. Slices are halved when a read comes back full, so no day is sorted, and only a single overfull second is paged by stable full-row order and offset. Operator notes: `docs/pages/server/upgrade-v2-tables.mdx`.

On ClickHouse `spans_v2.span_version` is a materialized SHA-256 fingerprint over length-prefixed protobuf components. All span readers rank by duration, then this fingerprint, so topology never reads payload columns. Parts written before the column existed calculate it on read until merged. The column costs 32 uncompressed bytes per physical row.

Further rules:

- Span search, topology, attributes and export choose one retry version (longest duration, then the stored `span_version` on ClickHouse or the stored protobuf bytes on SQLite/DuckDB), with UTF-8 byte budgets applied in SQL.
- Native report spans are written before projections. OTLP storage returns rejected span identities so their endpoint/task/AI/exception projections and conversation uploads are omitted while reporting partial success.
- HTTP entry-point classification suppresses only an observed local HTTP ancestor, never an absent parent's assumed kind.
- Fallback AI conversation IDs use the dashed UUID spelling.
- Log search accepts `traceId` and optional `spanId`, scoped to the selected project and time window; `distributedTraceId` and `excludeTraceId` selectors return 400. The trace log panel has one paginated list with stale-response protection.
- The move-over pages legacy history by stable full-row ordering and offsets only within overfull one-second slices, so source tables must be immutable while it runs. Recovery checks project, occurrence ID, trace/span IDs and destination-precision timestamps. Rejected canonical rows fail the native/migration facade, so a day cannot be marked complete after silent row rejection.

## Client metrics

Performance metrics of browsers and mobile apps are distributions over a population, never a time series per client. The stored unit is a mergeable histogram per `(project, metric, dimensions, minute)`, so storage grows with dimension combinations and not with users. Design notes: `docs/pages/learn/client-metrics.mdx` (user-facing), `js-client/INTERNAL_DOCS.md` "Performance metrics" (SDK side).

- **Histogram math** (`repositories/telemetry/shared/histogram.go`): base-2 exponential buckets at one fixed scale (`HistogramScale` = 3, 8 buckets per doubling, about 4.5% relative error). `Merge`, `Quantile`, `CountAtOrBelow`, `Sub` (cumulative to delta), `HistogramFromExponential` (a finer OTLP scale is merged down exactly) and `HistogramFromExplicit`. Counts are float64 because sampled clients are weighted by 1/rate. Percentiles are always computed in Go from merged buckets, so the three backends give the same answer; never compute a percentile from percentiles.
- **Storage** (`MetricHistogramRepository`, facade in `telemetry_*.go`): ClickHouse `metric_histograms` (AggregatingMergeTree, `ch/0107`-`0115`; dimension columns `release, env, os, os_major, client, client_major, form_factor, device_class, network, country, view` mapped from dimension keys by `shared.HistogramDimensionColumns`, every other key in the `tags` map; buckets are `SimpleAggregateFunction(sumMap, Tuple(Array(Int32), Array(Float64)))`), rolled up to `_1h` and `_1d` by materialized views, TTL 7 days / 90 days / 2 years, read by range and by how far back the read starts (`histogramTable(from, to)`: a 24 hour SLO backfill chunk three weeks back reads the hour table, since the minute table no longer has it). `country` is set by the server from the request (`GEOIP_COUNTRY_HEADER` or `GEOIP_DB_PATH`, package `app/geoip`), never taken from the client, and is empty when neither is configured. SQLite and DuckDB share `sqlitetypes.HistogramStore` (`sqlite_telemetry/0030`, `duckdb_telemetry/0010`): append-only rows with dimensions and buckets as JSON, merged on read, and the hourly retention pass folds minute rows older than 6h into hour rows (`Compact`: oldest hour first, one metric of one project at a time, each in one transaction that merges exactly the rows its `DELETE ... RETURNING` removed, in 5 minute slices, so there is no row limit and a late row is neither lost nor merged twice; it also runs when retention is disabled). A row carries its grain, and a chart whose bucket is shorter than a row's grain (an hour row on a 15 minute chart, a ClickHouse day row past 60 days) has the row divided evenly over the buckets it covers by `shared.SpreadHistogramPoints`, in `metric_query.controller.go` only: SLOs and alerts read rows as stored. A grouped read keeps the groups with the most observations (`HistogramSeries.Result`), not the first by key. On ClickHouse the plain query runs first and is repeated with a semi-join on the top `maxGroups+1` group keys only when it returned more groups than the cap (`querySeries(..., busiest)`): ranking on every read made grouped metric queries about 45% slower. Under the `telemetry_duckdb` tag the store picks its dialect from the open driver at query time, because tests of other packages open a SQLite telemetry DB under that tag. `metric_exemplars` holds a few sessions per series per hour for poor values, each with the `target` the client attributes the value to when it knows one (`ch/0116`, `sqlite_telemetry/0031`, `duckdb_telemetry/0011`). Counters and ratios go to `metric_points`, one row per series per flush.
- **Aggregator** (`app/clientmetrics`, no gin or repository imports; storage is the `Sink` interface, wired in `services/client_metrics.service.go`): `catalog.go` is the closed list of metric names (`browser.*`, `app.*`) with shape, unit, clamp, per-metric dimensions and rating thresholds (`PerUser` metrics, `browser.user` and `browser.user.affected{issue}`, are counted once per profile per UTC day on the device and take no page dimension; `browser.view.inp`/`browser.view.cls` are per view including SPA route changes; `browser.web_vital.attribution{vital,rating,target,phase}` (phase: INP's largest part, input_delay/processing/presentation) and `browser.long_task.script_time{script}` say what is behind slow values); `dims.go` is the guard (fixed dimension keys, 64-byte values, closed sets, per-project per-day caps, overflow becomes `other`, series budget of 5,000 per metric folding `url.path`, `screen`, `host` first, hard stop at twice the budget; custom metrics: 50 names, 2 dimensions, 50 values, and a data point attribute may not be `country`, a resource dimension or a `custom.*` key, which the server and the resource decide; up to 2 app-defined `custom.<key>` resource dimensions on every metric, 50 values each). What the guard admits is shared: new dimension values and registrations go to the main-DB table `client_metric_guard_entries` (`pg/0167`-`0168`, `sqlite/0089`, `ClientMetricGuardRepository`, `Pipeline.SyncState` after every flush) and are read back by every instance, so a cap is one number per deployment and survives a restart; the series of metrics at half their budget or more are read from storage once a minute (`MetricHistogramRepository.HotSeries`), so the series budget counts what is stored. Between two syncs each instance admits on its own, which is the only overshoot; `aggregator.go` is 64 sharded maps of cells swapped on flush; `pipeline.go` is ingest (`IngestOTLP`, `ObserveEvent`, `AddSeriesHistogram`), the per-IP cap (6,000 observations per project per minute, divided by the live instance count from `slo.Instances`; a histogram is charged its count, a catalog counter its value (the `app.frames.*` counters a second of frames per place, `EventsPerCost`, since a screen that animates renders 60-120 a second), an app's own counter one per point, and a `PerUser` counter is clamped to 1 per point), deduplication of resent payloads (`traceway.batch_id` on every payload, checked when `traceway.retry` is set; drop reason `duplicate`; per instance, so behind a balancer a resend of an upload that did arrive can land on another instance and count twice), clock correction from `traceway.sent_at`, sample weighting from `traceway.sample_rate`, and drop accounting by reason. `route.go` (`NormalizePath`) must stay in step with js-client `core/src/metrics/route.ts`; both test tables are the same. Besides numbers, UUIDs and long hex or token strings, a segment with a percent-encoded ASCII character (`%20`, `%2F`, `%7B`) becomes `:id`; encoded UTF-8 bytes stay. The value is a route template when the view was named, so a `?` that ends an optional parameter before another segment (`/:lang?/about`) is kept (`queryStart`); any other `?` or `#` starts a query or fragment and is cut. Normalization is the fallback: the SDK names a view by `setRoute`, else by the template it reads from the app's router (js-client `frontend/src/otel/route-detect.ts`), and the dashboard itself calls `setRoute(page.route.id)` from the root layout.
- **Ingest** (`otelcontrollers`): `ExportMetrics` sends a `clientlogs.IsClient` project to `exportClientMetrics` (64 KB body cap, delta exponential or explicit histograms and delta monotonic sums only; gauges, cumulative series and names outside the catalog are dropped and counted). Nothing is written per request. `browser_metrics.go` turns the performance events of event-only SDKs (the early 2.0 betas) into single observations of the same cells, skipped when the resource says `traceway.metrics: aggregated` (SDK 2.0.0 and later, which aggregates on the device). Backend projects keep their point path and additionally get their OTLP `Histogram`/`ExponentialHistogram` data written as histograms through `AddSeriesHistogram` (cumulative series are differenced; the first sample is the baseline; the baseline is per instance, so behind a balancer that spreads one exporter over instances use delta temporality; past 50,000 followed series new ones are dropped under reason `memory`). Everything that only goes to memory (`AddSeriesHistogram`, `ObserveEvent`) runs after the storage writes that can answer 503, so a retried export is not counted twice, and on the logs path the idempotent recording reasons are stored before the log records; `.avg` and `.count` are still written for explicit histograms.
- **Registry**: type `histogram` (`models.MetricTypeHistogram`). `EnsureRegisteredWithUnits` upgrades a row still registered as `gauge`. `UpdateRegistry` does not change the type of a histogram.
- **Query**: `metric_query.controller.go` reads the histogram table for histogram metrics; a metric nothing has reported yet with a distribution aggregation (or a catalog distribution) is an empty series, not a 422, so a dashboard can be installed before its data. `POST /api/metrics/exemplars` lists the sessions behind the worst values. Discovery endpoints union both tables.
- **Alerts** (`notifications/metric_histogram.go`, shared by both evaluator files): `metric_threshold` reads histograms first (`histogramMetricSeries`), up to 2 minutes behind now, with `minCount` (default 10; `max` and `min` are observations, not estimates, and apply a minimum only when the rule sets one) and `good_ratio` as a percentage; a percentile (`p50` to `p99`) on a point metric falls back to raw points. a grouped rule (`groupBy`) keeps one row per open alert in `notification_rule_firing` (`pg/0172`-`0174`, `sqlite/0093`-`0095`) and sends an open alert again only once the rule's cooldown has passed since the row's `last_notified_at`, so a restart or a second instance does not repeat it. `metric_release_regression` is a polled rule comparing the newest `service.version` (first seen last within 7 days) with the busiest earlier one, once per release and segment: what was reported is kept in `notification_rule_states.detail` (`pg/0171`, `sqlite/0092`; `NotificationRuleStateRepository.SwapDetail`, a conditional update, so a restart does not repeat a notification and of several instances one notifies), whatever the cooldown. With `groupBy` (at most 2 keys) it compares inside each segment and notifies per segment; without it the earlier release is first weighted to the new release's mix of `device.form_factor` and `os.name` (`mixAdjusted`), so a rollout that reached slower devices first is not reported. A percentile must also be worse by more than chance: the low end of the new release's 95% interval above the high end of the old one's (`Histogram.QuantileInterval`).
- **SLOs**: metric kind with aggregation `distribution` counts events from the buckets (`slo/compute.go` `distributionBuckets`); frontend projects may create it. An SLO is one segment (its tag filters); the sheet's "One SLO per" creates one per value of a dimension (at most 20), each with its own budget.
- **Remote config**: `sdkconfig.MetricsSettings` (`metrics: {enabled, sampleRate, flushSeconds}`), `limits.metrics: "off"` from `ApplyPermission` when the plan drops data.
- **Dashboards**: templates `browser-performance` and `mobile-performance` (default for react-native, flutter, ios, android), both seeded by migrations. Widget types `rating_bar` and `breakdown_table` (`services/dashboards/definition.go`; frontend `rating-bar.svelte`, `breakdown-table.svelte`, helpers in `utils/metric-widgets.ts`). On a frontend project the dashboards page filters by release, OS and, when the deployment resolves countries, country instead of instance. Both templates include user, country, attribution, per-view and script widgets; a `breakdown_table` over a `sum` or `count` source is additive (the group's total is its value and its weight).
- **Observability**: `clientMetrics` block of `/api/health/deep`, `traceway.client_metrics.*` from `monitoring.StartClientMetricsReporter`.
- **Load test**: `testing/shop/traffic/client-metrics-load.mjs` (simulated devices, one forwarded address each; asserts no drops and that requests reached the aggregator). `BenchmarkIngestOTLP` in `app/clientmetrics`.

Mobile SDKs do not send these metrics yet (React Native is still the 1.x design); the backend accepts `app.*` over OTLP from any mobile project.

## Metric rollup repair (ClickHouse)

Background: "Map columns that identify a row (ClickHouse)" in `AGENTS.md`. The repair worker (`METRIC_ROLLUP_REPAIR=true`, opt-in; `clickhouse/metric_rollup_repair.go`, started by `retention.startMetricRollupRepair`; operator docs `docs/pages/server/repair-metric-rollups.mdx`). It covers the last year of `metric_points_1h`, `metric_points_1d`, `metric_histograms_1h` and `metric_histograms_1d`; the minute rollup and the two tables in front of the views expire within 30 days and are left alone, and so are rollup rows older than a year. **Every query against a rollup reads one day** (`rollupRepairOnDay`, `toDate(recorded_at) = toDate(?)`, days as the server counts them from `today()`): clickhouse-go ends a query at its 300 s `ReadTimeout`. The scan goes back from today a day per query, and so do the merges and the count that decides a delete is done; do not add a query over a whole table or partition. A pass runs at startup and, after a failure or a skipped partition, an hour later; the first pass that leaves nothing behind ends the worker. Per partition: the merged copies of the unsorted rows (`tags != mapSort(tags)`) are built in `<table>_tagbuild`, a day per `INSERT`; the table is renamed to `<table>_tagrepair_<partition>_<first day>`, and that name is the only state there is: that the copies are complete, and the first day they cover; `MOVE PARTITION` puts the copies into the rollup at once and leaves the staging table empty, so a repeated move adds nothing; `DELETE IN PARTITION ID` removes the unsorted rows from that first day on (an older unsorted row of the same partition has no merged copy, `TestRepairMetricRollups_ReadsExactlyTheLastYear`) as a mutation that is polled (never `mutations_sync` in one query: the connection has a read timeout) and found in `system.mutations` by two pieces of its command, since the server stores it reformatted, and the count of unsorted rows left decides when it is done; the staging table is dropped last, and only once `moveStaged` (a move, then a count) finds it empty: on ClickHouse Cloud (`SharedMergeTree`) and other replicated tables a read can miss a part another replica has just written, so the counts that decide something end in `rollupRepairConsistent` (`select_sequential_consistency = 1`, no effect on a plain MergeTree) and a staging table that keeps rows after `rollupRepairMoveTries` moves ends the pass and stays (`TestRepairMetricRollups_KeepsAStagingTableThatStillHoldsRows`). `lacksSpace` never skips on object storage, which reports no limit. Every step can be repeated, which `TestRepairMetricRollups_ResumesAfterStoppingAtAnyStep` holds by stopping at each one. The order (move, then delete) means a partition briefly holds a series twice, which doubles `sum` and `count` but leaves averages, extremes, percentiles and rates alone; deleting first would make the series vanish instead. It is safe only while nothing writes unsorted rollup rows, so the pass refuses to start when a view does not contain `mapSort(` (`requireSortedView`). A partition is skipped unless its disk has twice its largest part free (a mutation reserves 1.1 times the part and skips, without an error, a part that does not fit; a delete with no progress for 30 minutes is killed and the pass fails). Several instances may have the variable set: the pass holds the session advisory lock 824737009 on one PostgreSQL connection, and `guard`, asked before every step that changes data, fails once that connection is gone. Progress is one log line per step, `metric rollup repair: <event> key=value ...` (`rollupRepairLog`; events `scan_running`, `table_scanned`, `pass_started`, `batch_merged`, `partition_resumed`, `delete_running`, `partition_done`, `partition_skipped`, `pass_finished`, `pass_failed`), whose pairs are also `rollup_repair.*` attributes of the exported record through `config.LogEvent` (the one logging helper that sets attributes; `traceway.EmitLogFields`), plus the `traceway.rollup_repair.*` metrics and the task `retention.metric_rollup_repair`. A new event or metric goes into the docs page and `capacity-monitoring.mdx` too.
