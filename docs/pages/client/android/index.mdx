# Android Quick Start

Integrate Traceway into your native Android application with the [`com.tracewayapp:traceway`](https://central.sonatype.com/artifact/com.tracewayapp/traceway) library from Maven Central. The SDK is built on the official [OpenTelemetry Java SDK](https://github.com/open-telemetry/opentelemetry-java): exceptions, logs and request spans leave as OTLP/HTTP, performance metrics as OTLP metrics, and the SDK polls Traceway over [OpAMP](https://opentelemetry.io/docs/specs/opamp/) for its collection settings, like the [browser SDK](/client/js-sdk) 2.x, the [Flutter SDK](/client/flutter) 2.x and the [iOS SDK](/client/ios) 2.x. Session replay records the app's views and Jetpack Compose screens as a wireframe that the dashboard plays with its rrweb player.

> **2.0 is a beta.** It needs a Traceway server that accepts Android projects on its OTLP and OpAMP endpoints; there is no fallback to the 1.x `/api/report` protocol. On an older server stay on `com.tracewayapp:traceway:1.0.1`. See [Migrating from 1.x](#migrating-from-1x).

## Features

- Uncaught exceptions on every thread, written to disk before the process ends and sent at once or at the next start; deobfuscated on the server for R8 builds
- OpenTelemetry inside: every record is a log record or span of the official OpenTelemetry Java SDK and leaves as OTLP/HTTP protobuf
- A ring buffer on the device: logs, requests, screens, taps and custom events are uploaded only when something goes wrong
- Remote config over OpAMP: signal modes, sample rates, triggers and captures from the project's **Data Collection** page, or the same settings in the app with `collection`
- Captures on demand, from the dashboard or from a recording trigger on the device (a journey of taps, screens and log lines)
- Wireframe session replay of views and Jetpack Compose screens, with pictures of image views when the image policy allows them
- Taps that name the view: every tap is recorded with a CSS-like selector (`MaterialButton#pay`, `ImageButton[label="Delete"]`) that click steps of recording triggers match
- App performance metrics: start, screen display times, slow and frozen frames, hangs, crashes, sessions, users, memory and requests, aggregated on the device; they fill the project's **Mobile Performance** dashboard
- Network requests as client spans, with W3C `traceparent` propagation to your backend
- Any OpenTelemetry backend: logs, spans and metrics to an OTLP/HTTP receiver, next to Traceway or without it

## Requirements

- Android 5.0 (API 21) or later: `minSdk` 21.
- Core library desugaring when the app's `minSdk` is below 26 (see [Installation](#installation)).
- A Traceway server that accepts Android projects on its OTLP and OpAMP endpoints, or an OTLP/HTTP receiver for [standalone](#standalone-without-a-traceway-server) use.

## Installation

Add the dependency to your app module's `build.gradle.kts`:

```kotlin
dependencies {
    implementation("com.tracewayapp:traceway:2.0.0-beta.1")
}
```

OpenTelemetry Java uses `java.util.function` and `java.time`, so **an app whose `minSdk` is below 26 must enable core library desugaring**, as every app using OpenTelemetry on Android does:

```kotlin
android {
    compileOptions {
        isCoreLibraryDesugaringEnabled = true
    }
}

dependencies {
    coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.1.5")
}
```

The library's manifest declares `INTERNET` and `ACCESS_NETWORK_STATE`; the manifest merger adds both to your app. Its consumer R8 rules ship with it, so a minified build needs no rules of its own.

## Quick start

Initialize the SDK from your `Application.onCreate()`. Every uncaught exception, on every thread, is then captured with the breadcrumbs and the replay of the seconds before it:

```kotlin
import android.app.Application
import com.tracewayapp.traceway.Traceway
import com.tracewayapp.traceway.TracewayOptions

class MyApp : Application() {
    override fun onCreate() {
        super.onCreate()
        Traceway.init(
            application = this,
            connectionString = "your-token@https://traceway.example.com",
            options = TracewayOptions(
                version = BuildConfig.VERSION_NAME,
                screenCapture = true, // wireframe session replay
            ),
        )
    }
}
```

Register the application class in `AndroidManifest.xml`, or `onCreate()` never runs:

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application android:name=".MyApp" ...>
        ...
    </application>
</manifest>
```

The connection string is the project token and the server URL, as the project's **Connection** page shows it; the 1.x form ending in `/api/report` works too. An invalid connection string or `telemetry` setting does not take the app down: `Traceway.init` logs the error (tag `Traceway`) and returns `null`, and the app runs without the SDK. To send telemetry to another OpenTelemetry backend as well, or only there, see [Setups](#setups).

## Manual capture

Every method is a static on `Traceway` and does nothing before `Traceway.init`. From Java they read the same: `Traceway.captureException(e)`, `Traceway.setAttribute("user.id", id)`.

### Errors and messages

```kotlin
// A caught exception, with optional attributes
try {
    riskyOperation()
} catch (e: Exception) {
    Traceway.captureException(e, mapOf("checkout.step" to "pay"))
}

// A message, reported as an issue
Traceway.captureMessage("User completed checkout")

// Send what is ready now (blocks; call it off the main thread)
Traceway.flush()
```

Every exception and message also says where the app was when it happened: `app.screen.name` (the screen on top), `app.screen.route` when a [route template](#naming-screens) is set, `app.screen.previous`, `app.screen.duration_ms` (how long the screen had been shown) and `viewport` (the window's size in dp, `<width>x<height>`). Attributes you pass to `captureException` win over these.

By default, network failures are not reported: `UnknownHostException`, `SocketTimeoutException`, `ConnectException`, `SSLHandshakeException`, `NoRouteToHostException`, `Connection reset`, a timeout (`/timeout/i`) or a 4xx status (`/status code (of )?4\d{2}/`, `/failed: 4\d{2}/`). `ignoreErrors` replaces that list (`null`, the default, keeps it). A `String` matches if it occurs in the first line of the error's `Type: message`, and a `Regex` (or a `java.util.regex.Pattern` from Java) if it finds a match in that line; the stack is never matched. An empty list reports everything. `beforeCapture` sees every exception and message that is not ignored and returns `false` to drop it; a callback that throws is logged in debug and the record is kept. Crashes (uncaught exceptions that end the process) pass through neither and are always reported:

```kotlin
TracewayOptions(
    ignoreErrors = listOf("PaymentDeclinedException", Regex("timeout", RegexOption.IGNORE_CASE)),
    beforeCapture = { captured -> captured.error !is CardDeclinedException },
)
```

`TracewayCapturedError` carries `error`, `type`, `message`, `isMessage`, `attributes` and `stackTrace` (`null` for a message).

### Logs

```kotlin
Traceway.log("Cart loaded")
Traceway.log("Payment retried", TracewayLogLevel.WARN, mapOf("attempt" to "2"))
```

A log line has the level's severity (`TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`; `INFO` by default), the attributes you pass and `log.source` `api`. Every `System.out` and `System.err` line (`println`, `printStackTrace`) is recorded too, as info and error. Calls to `android.util.Log` do not pass through `System.out`: forward them with `Traceway.log`, for example from a Timber tree:

```kotlin
import android.util.Log
import com.tracewayapp.traceway.Traceway
import com.tracewayapp.traceway.TracewayLogLevel
import timber.log.Timber

class TracewayTree : Timber.Tree() {
    override fun log(priority: Int, tag: String?, message: String, t: Throwable?) {
        val level = when (priority) {
            Log.VERBOSE -> TracewayLogLevel.TRACE
            Log.DEBUG -> TracewayLogLevel.DEBUG
            Log.WARN -> TracewayLogLevel.WARN
            Log.ERROR -> TracewayLogLevel.ERROR
            Log.ASSERT -> TracewayLogLevel.FATAL
            else -> TracewayLogLevel.INFO
        }
        Traceway.log(if (tag != null) "$tag: $message" else message, level)
    }
}
```

`captureLogs = false` turns both off. Log lines are the `console` signal: they wait in the ring buffer and go up with an exception, a trigger or a capture. The console's minimum severity (`signals.console.minSeverity`) is `info` by default, so `TRACE` and `DEBUG` lines are dropped unless a rule or `collection` lowers it.

### Actions and events

```kotlin
// A breadcrumb on the session timeline
Traceway.recordAction(category = "cart", name = "add_item", data = mapOf("sku" to "SKU-123", "qty" to 2))

// A named product event; triggers can match it by name
Traceway.track("checkout_failed", mapOf("reason" to "card_declined"))
```

`recordAction` records a `traceway.action` record with its category, name and data. `track` records an event whose `event.name` is the name you give, so a trigger step can match it (`{"key": "event.name", "op": "eq", "value": "checkout_failed"}`). Both are the `custom` signal.

### Attributes and users

```kotlin
Traceway.setAttribute("user.id", user.id)
Traceway.setAttributes(mapOf("plan" to "pro", "tenant" to "acme"))
Traceway.removeAttribute("tenant")
Traceway.clearAttributes()
```

There is no `setUser`: `user.id` is an attribute like any other. Attributes go on every later record (at most 64 keys), and the server matches rules and captures against them; a change is sent with a config poll about 2 seconds later, so a rule that targets it applies soon. `Traceway.currentSessionId` is the session's ID and `Traceway.getInstanceId()` the installation's (`service.instance.id`), the one the dashboard's Capture button targets.

### Interactions

An interaction traces one user action from start to end: a span named after it (`traceway.interaction: true`). Requests made inside its `run`, on the thread that runs it, are its child spans (an OkHttp `enqueue` or a coroutine that moves to another thread is not part of it), and exceptions, messages and logs recorded there carry its trace ID. A failed interaction is sent with its exception, so the issue links to its trace; one that succeeds waits in the buffer like other spans.

```kotlin
val checkout = Traceway.startInteraction("checkout", mapOf("plan" to "pro"))
try {
    checkout.run { api.placeOrder(cart) }
} catch (e: Exception) {
    checkout.captureException(e)
} finally {
    checkout.end()
}
```

`captureException` reports the exception with the interaction's trace and marks the interaction failed; `end(failed = true)` marks it failed without one. `traceId` and `spanId` name its span, and `setAttribute` adds an attribute to it.

## How collection works

Every record is an OpenTelemetry log record or span and belongs to a *signal*. Each signal is in one of three modes: `stream` sends it as soon as it is produced, `buffer` keeps it in a ring buffer on the device (2 MiB / 10 minutes by default) until a trigger or a capture uploads it, and `off` drops it.

| Signal | Source | Default |
|--------|--------|---------|
| `errors` | uncaught exceptions, `captureException` | stream |
| `messages` | `captureMessage` | stream |
| `console` | `System.out` (info) and `System.err` (error) lines, `Traceway.log` | buffer |
| `network` | HTTP requests, as client spans; interactions | buffer |
| `navigation` | activities, AndroidX fragments, `Traceway.recordNavigation` | buffer |
| `userActions` | taps (`browser.user_action.click`) | buffer |
| `custom` | `Traceway.recordAction`, `Traceway.track` | buffer |
| replay | the [wireframe session replay](#session-replay) | buffer |

The built-in trigger fires on every exception: it uploads the buffered breadcrumbs of the last 10 minutes and the replay of the last 30 seconds, at most the frames the replay ring holds (`maxBufferFrames`). An app that never throws sends only its session and control records (`session.start`, `session.end`, `traceway.session.update`, `traceway.config.applied`) and its metrics. Clips are rationed to one per 5 seconds and 20 per session; breadcrumbs are still sent for the exceptions in between.

`recordAllSessions = true` streams every breadcrumb signal and the replay instead. `baselineSampleRate` streams the breadcrumbs of a share of sessions, chosen by session ID.

The ring buffer is saved to disk when the app goes to the background, so a session that goes on after the system killed the app still has its breadcrumbs. Telemetry that failed to send is kept on disk and retried.

The signal names, modes, triggers and limits are the browser, Flutter and iOS SDKs', so one rule can target all of them. See the [settings reference](/learn/remote-config/reference#the-settings-document).

## Remote config

The SDK polls the server over OpAMP (plain HTTP): at start, at the interval the server sets (5 minutes by default, 60 seconds while a capture targets the device), when the app returns to the foreground, and about 2 seconds after `Traceway.setAttribute` or a new session, so a rule targeting an attribute applies soon. It applies the collection settings you define under **Data Collection** in the project's sidebar: signal modes and sample rates, buffer sizes, replay and image settings, metrics settings, extra triggers (for example "flush when `checkout_failed` happens twice in a minute") and on-demand captures of one user or device. See [Remote SDK Config](/learn/remote-config/setup) for a walkthrough.

- The `capture*` options, `screenCapture`, `replayImages` and `sessions` are **ceilings**. Remote settings can lower what is collected but never raise it: with `captureNetwork = false` no rule can turn network capture on, and without `screenCapture = true` nothing is recorded. `sampleRate`, `baselineSampleRate` and `recordAllSessions` are defaults that a rule can change in either direction.
- The last applied settings are cached, so they are in effect from the start of the next launch.
- `remoteConfig = false` never polls. Standalone (no connection string) the SDK never polls either.
- `Traceway.refreshConfig()` polls now.

### Local config

`collection` takes the same settings document a rule holds and lays it over the built-in defaults, so an app can define its own policy and triggers without the server. With `remoteConfig = true` the server's rules apply on top of it; with `remoteConfig = false` it is the whole policy.

```kotlin
TracewayOptions(
    screenCapture = true,
    remoteConfig = false,
    collection = mapOf(
        "signals" to mapOf("network" to mapOf("mode" to "stream")),
        "buffer" to mapOf("maxAgeSeconds" to 300),
        "replay" to mapOf("images" to "always"),
        "triggers" to listOf(
            mapOf(
                "id" to "checkout-failed-twice",
                "steps" to listOf(
                    mapOf(
                        "match" to mapOf("key" to "event.name", "op" to "eq", "value" to "checkout_failed"),
                        "count" to 2,
                        "periodSeconds" to 60,
                    ),
                ),
                "actions" to listOf(
                    mapOf("type" to "capture", "durationSeconds" to 300, "lookbackSeconds" to 120, "replay" to true),
                ),
            ),
        ),
    ),
)
```

A document with an unsupported `schemaVersion` is ignored with a Logcat warning, and the defaults apply; a malformed field is skipped on its own and the rest of the document applies. Triggers merge by `id`; see the [trigger reference](/learn/remote-config/reference#triggers).

## Captures

A capture uploads what the device holds from its lookback window and then streams the selected signals, and the replay when it asks for it, until it ends. Records sent under a capture carry its ID (`traceway.capture.ids`), so the dashboard shows when it is collecting.

- **From the dashboard**: the Capture button on a session or an issue targets one installation (`service.instance.id`), user (`user.id`) or session. The device starts it at its next poll; cancelling it stops the streaming at the poll after that. Each capture's lookback is uploaded once per installation.
- **From a trigger** (a `capture` action): started on the device the moment the trigger fires. It survives app restarts until it ends; firing again only extends it.

A capture that streams replay sends it as consecutive segments; see [Session replay](#session-replay).

### Recording triggers

The dashboard's [recording trigger](/learn/remote-config/trigger-sequences) steps work on Android. The builder labels them **Tap**, **Hover**, **Navigation** and **Log**:

| Step | Matches |
|------|---------|
| `{"event": {"type": "click", "value": "<selector>"}}` | a tap on a view the selector matches, or inside one |
| `{"event": {"type": "hover", "value": "<selector>"}}` | a mouse pointer entering a matching view (ChromeOS, a tablet with a mouse; never a finger or a stylus) |
| `{"event": {"type": "navigation", "value": "/orders/{id}"}}` | arriving at a screen; `{id}` is one non-empty segment |
| `{"event": {"type": "log", "value": "Profile loaded", "mode": "contains"}}` | a console line or a `captureMessage` (`exact` by default) |

Steps match in order, each within its `withinSeconds` of the previous one; progress is kept on disk, so it survives an app restart within the session. When a trigger that asks for replay fires, the session lists it as a recording reason with its sequence.

The step format is the browser SDK's, so the dashboard builds and validates both the same way. What a selector and a route pattern are compared with is different, because an Android app has no DOM and no URL. The two sections below are the whole of that difference.

### Naming views

A click or hover step takes a selector in CSS syntax. When a finger lifts, the SDK hit-tests the point the way Android dispatches touches: it walks the window's views from front to back (elevation, then drawing order), into every visible view whose bounds contain the point after its scroll and transform, and inside a Jetpack Compose view on through the Compose semantics nodes under the point. That gives the chain of elements from the deepest one up to the window. A tap matches when the element under the finger or any element above it matches, the way a browser click matches its target or an ancestor; tapping the `TextView` inside a clickable row matches a selector for the row. A tap is a finger that lifts within the touch slop and before the long-press timeout (`ViewConfiguration.getLongPressTimeout()`), so a long press is not a tap. Hover fires when a mouse pointer enters a matching view, so it never fires on a touch screen.

Each part of the syntax reads one property of a view or Compose node:

| Selector | Browser equivalent | Matches an element that |
|----------|--------------------|-------------------------|
| `MaterialButton` | tag name | is of that class or a subclass of it, by simple name in any case: `Button` matches a `MaterialButton`, `TextView` matches every button. A Compose node's type is its role (`Button`, `Checkbox`, `Switch`, `RadioButton`, `Tab`, `Image`, `DropdownList`) or what it is (`Text`, `TextField`, `Slider`, `ProgressIndicator`). `*` is any element |
| `#pay` | `id` attribute | has `android:id="@+id/pay"` (the id's resource entry name), or `Modifier.testTag("pay")` |
| `.button` | class | has that role: `button`, `link`, `header`, `image`, `textField`, `slider`, `checkbox`, `toggle`, `selected`. A role comes from the view's class (a `Button` is a button, an `EditText` a textField, a `CheckBox` a checkbox, a `Switch` a toggle), its accessibility heading and selected state, a clickable span in its text (`link`), or a Compose node's role and semantics |
| `[key="42"]` | attribute | has the string tag `42` (`android:tag="42"`), or that id or test tag |
| `[identifier="..."]` | attribute | the same values as `key` |
| `[label="Delete"]` | attribute | has that content description or tooltip: its own, else the first one below it along single children (an `ImageButton`'s `contentDescription`, an `Icon`'s in Compose) |
| `[text="Pay"]` | none | shows that text: a `TextView`'s own text (an `EditText` offers its hint, never what was typed), else the texts of up to three views under it joined by a space |
| `[type="com.example.PayButton"]` | none | is of that class, by full or simple name, for a class that cannot be written as a tag |

Only these five attribute names exist. A view has no `data-*` attributes; give it an id, a test tag or a string tag instead.

```xml
<!-- #pay, or MaterialButton#pay; MaterialButton[text="Pay now"] when it has no id -->
<com.google.android.material.button.MaterialButton
    android:id="@+id/pay"
    android:text="Pay now" />

<!-- [key="promo-banner"] -->
<ImageView android:tag="promo-banner" ... />
```

```kotlin
// ImageButton[label="Delete"]
deleteButton.contentDescription = "Delete"

// In Compose: #checkout-form, whatever the composable is
Column(Modifier.testTag("checkout-form")) { ... }

// In Compose: Button[label="Delete"]
IconButton(onClick = remove) { Icon(Icons.Default.Delete, contentDescription = "Delete") }
```

The rules the dashboard and the SDK both apply:

- Attribute values take `=`, `^=` (starts with), `$=` (ends with), `*=` (contains), `~=` (one of its words) and `|=`. Quote a value that is not a plain name: `[key="42"]`, not `[key=42]`.
- A selector is at most 256 characters and cannot contain `:`, `,` or `\`, also inside a quoted value. Pseudo-classes and selector lists are therefore not available, and `[text="Total: 5"]` is refused: match the start instead, `[text^="Total"]`.
- Combinators are descendant (space), child (`>`), adjacent (`+`) and general (`~`) sibling, over the view tree and, inside Compose, the semantics tree. Layout views sit between a screen's container and its controls, so prefer the descendant combinator (`#cart MaterialButton`) to `>`.
- A selector that names text depends on the copy: it stops matching when the wording changes or the app runs in another language. Ids and `testTag`s, the handles Espresso, UI Automator and Maestro use, are the stable choice.
- R8 renames classes in a minified build. A renamed class is named by its nearest superclass that kept its name (a minified `PayButton` reads as `MaterialButton`), and a class inflated from a layout keeps its name. Ids, test tags, roles, labels and text are never renamed.
- `captureUserActions = false` turns taps off, and click and hover steps with them.

You rarely write a selector by hand. Every tap is recorded as `browser.user_action.click` with the selector of the control that handled it (`browser.css_selector`), and the **Actions** list of a session shows it, for example `MaterialButton#pay` or `MaterialButton[text="Pay now"]`. Copy it into a click step as it is: the SDK only records a selector it has checked against the tapped view. The control is the view that handled the tap, the nearest clickable one under the finger (or the Compose node with a click action), else the text or image that was hit. Its name is the most stable one it has, in this order: an id on the control, on a single-child wrapper around it or on a view inside it; its string tag; the shown text (up to 40 characters); the label (up to 60); a role when the class has no usable name; the class with the nearest ancestor id in front (`#cart MaterialButton`); the class alone. The record also carries `app.widget.name`, `app.widget.id`, `app.widget.text`, `app.widget.label`, `app.screen.coordinate.x`, `app.screen.coordinate.y` and `app.screen.name`. The text and label of a [masked](#privacy-masks) view are never sent, and a mask tag (`traceway-mask`, `traceway-blank`) never names a view.

### Naming screens

A navigation step is compared with the path of the screen the user arrives at:

- an activity is `/` and its class name (`/CheckoutActivity`), reported when it resumes;
- an AndroidX fragment that shows a screen is `/` and its class name (`/CartFragment`); `NavHostFragment` and fragments without a view are not screens;
- anything else reports its path itself with `Traceway.recordNavigation(path, action = "push", from = null, route = null)`, where `route` is the route template the path is an instance of, when the router knows it. With Compose Navigation:

```kotlin
navController.addOnDestinationChangedListener { _, destination, arguments ->
    val route = destination.route ?: return@addOnDestinationChangedListener   // "orders/{id}"
    val path = Regex("\\{(\\w+)\\}").replace(route) { m -> arguments?.getString(m.groupValues[1]) ?: m.value }
    Traceway.recordNavigation("/$path", route = "/" + route.replace(Regex("\\{(\\w+)\\}"), ":$1"))
    // path "/orders/8841", route "/orders/:id"
}
```

Matching is case-sensitive and by segment: `/orders/{id}` matches `/orders/42` and not `/orders/42/edit`, and a query string is ignored. Going back arrives at the screen it returns to, so a step for `/HomeActivity` also matches coming back to it. Recorded navigations are `browser.navigation` records whose `url.full` is the path; the **Actions** list of a session shows them. In a minified build activity and fragment classes keep their names when they are declared in the manifest or inflated from a layout; report a stable path yourself for a screen a trigger must match. `captureNavigation = false` turns screens off.

A route template (`/orders/:id`) names a screen the way metrics group it. `Traceway.recordNavigation(path, route = "/orders/:id")`, or `Traceway.setRoute("/orders/:id")` after the navigation, names the current screen's template until the next screen; navigation records then carry it as `app.screen.route`, and so do the exceptions on that screen. Without one, IDs in the path are folded for the metrics (`/orders/8841` becomes `/orders/:id`).

## Session replay

```kotlin
TracewayOptions(screenCapture = true)
```

Session replay on Android is always a wireframe: the SDK records the view tree, never the screen's pixels, and the dashboard plays it with the same rrweb player as a browser session, taps and swipes included. A rule's `replay.captureMode` is for the Flutter SDK and does not apply.

- **Error clip.** An exception uploads the replay of the last 30 seconds (the replay `lookbackSeconds` of the built-in trigger), cut to the `maxBufferFrames` frames the device holds, and links it to the exception. A frame is kept only when the screen changed, so the default 150 frames at the default 10 fps cover at least 15 seconds, and the whole 30 seconds unless the screen changes on every frame.
- **Streaming.** While a capture or a rule streams replay, the session leaves as consecutive segments of up to 10 seconds, each starting with a full snapshot; the session player plays them back to back. An exception during a streaming capture still gets a clip of its own.
- **Background.** While the app is in the background the replay shows a plain "App in the background" screen.
- **Destination.** Replays always go to Traceway, also when `telemetry` sends the other signals elsewhere. Standalone, nothing is recorded.

### Wireframe

After a frame the app drew (at most `fps` times a second, 10 by default, and not at all while nothing changes) the SDK walks the app's windows (activities, dialogs, popups and menus, each where it is on the screen, with the dim behind a dialog) and turns what they show into HTML: boxes with their colors, gradients, borders, corners and elevation shadows, text with its size, weight, color, alignment and line breaks, clips, fades, transforms and scroll positions, as absolutely positioned elements nested the way Android draws them. What changes from one frame to the next becomes an rrweb mutation.

- **Small and cheap.** A clip is tens of kilobytes of JSON, a segment often less. An unchanged view costs no allocation: its node from the previous frame is reused, and the diff skips it. A view whose own code throws while it is read is left out of that frame; the rest of the screen is recorded.
- **Views.** Checkboxes, radio buttons, switches (framework, AppCompat and Material), progress bars, seek bars and rating bars are drawn from their state. Material components (buttons, chips, cards, text fields with their floating labels) keep their shapes and colors, read by drawing a few pixels of their backgrounds.
- **Jetpack Compose.** Compose screens are recorded from their semantics tree: text with its style, buttons, text fields, checkboxes, switches, radio buttons, sliders, progress indicators, selected tabs, icons and images, lists as they scroll, and Compose dialogs and menus, which are windows of their own. Compose does not expose its surface colors: a button with light text (a filled one) takes the theme's primary color, other buttons and fields have a neutral look over the view's own background.
- **Not pixel-exact.** The browser draws text in its own font. Solid colors and shapes are drawn as such and small vector icons as their shape (drawn once, as a mask the icon's color fills); pictures follow the [image policy](#images). `WebView`, `SurfaceView`, `TextureView` and map views are labelled placeholders, and views that draw themselves (charts, custom `onDraw`) a dashed outline.
- **Keyboard.** The on-screen keyboard is a plain box where the keyboard is, never its keys.
- **Typed text.** Text typed into fields is replaced with `*` unless a rule sets `replay.maskAllInputs: false`; password fields always show dots. Hints and labels are not typed text and stay readable.

### Images

Whether the replay shows the pictures of image views is decided by the image policy: the `replay.images` setting of the [collection settings](/learn/remote-config/reference#replay) (`off`, `wifi` or `always`; `wifi` by default) under the `replayImages` option, a ceiling (`TracewayImagePolicy.ALWAYS` by default). The lower of the two applies, in the order `off`, `wifi`, `always`, so `replayImages = TracewayImagePolicy.OFF` keeps every image a placeholder whatever a rule says.

- `wifi` records pictures only on an unmetered network: `ConnectivityManager.isActiveNetworkMetered()` is false, followed live by a network callback. The network is checked when a frame is captured, so a picture captured on Wi‑Fi stays in its clip.
- What is recorded is the bitmap an image view shows (an `ImageView` with a `BitmapDrawable`, a bitmap background), never a screenshot of the window. Jetpack Compose images stay placeholders, because Compose semantics expose no pixels. An image inside a [privacy mask](#privacy-masks) is never recorded.
- A picture is scaled to 1.5 times its displayed size in dp, at most 512 px on its longest side, and encoded as JPEG at quality 0.6 (PNG when it has transparency and is at most 128 px). One still larger than 96 KiB after a second try at half the size is left out. Encoding runs off the main thread, so the first frame shows a placeholder and a later one the picture.
- A session records at most 4 MiB of pictures; after that, placeholders. The bytes count against the session's replay budget like the rest of a segment.
- When the policy does not allow pictures, an image is a placeholder box.

Session records carry `traceway.replay.images` (the policy in effect when the session started) and `traceway.replay.image_bytes`.

### Privacy masks

Masks change the replay only; the user sees no difference.

```kotlin
import android.graphics.Color
import com.tracewayapp.traceway.TracewayMaskMode
import com.tracewayapp.traceway.tracewayMask

// Blur: the layout stays, its text becomes * and its images placeholders
cardNumberView.tracewayMask = TracewayMaskMode.blur()

// Blank: a box of this color, nothing inside it is recorded
profileHeader.tracewayMask = TracewayMaskMode.blank(Color.BLACK)

// No mask
cardNumberView.tracewayMask = null
```

From Java, `Traceway.mask(view, TracewayMaskMode.blur())` (blur when the mode is left out) and `Traceway.unmask(view)`. In XML, with no code, `android:tag="traceway-mask"` (blur) or `android:tag="traceway-blank"` (blank). In Jetpack Compose:

```kotlin
import com.tracewayapp.traceway.TracewayMaskMode
import com.tracewayapp.traceway.compose.tracewayMask

Text(address, Modifier.tracewayMask())
Box(Modifier.tracewayMask(TracewayMaskMode.blank())) { ... }
```

`Modifier.testTag("traceway-mask")` and `"traceway-blank"` work too. A mask covers everything inside the view or composable, and a masked view's text and label are also left out of tap records.

## Network requests

Every OkHttp call through `TracewayOkHttpInterceptor` is recorded as a client span (method, URL, status, duration, byte counts). Add it as an *application* interceptor:

```kotlin
import com.tracewayapp.traceway.network.TracewayOkHttpInterceptor

val client = OkHttpClient.Builder()
    .addInterceptor(TracewayOkHttpInterceptor())
    .build()
```

The SDK's own requests are never recorded.

### Other HTTP clients

Other HTTP stacks record a request with the client's `startRequest(method, url)` and `endRequest(handle, statusCode, requestBytes, responseBytes, error)`:

```kotlin
val handle = Traceway.client?.startRequest("GET", url)
// send the request, adding handle?.traceparent as a `traceparent` header when it is not null
handle?.let { Traceway.client?.endRequest(it, statusCode = 200, requestBytes = null, responseBytes = 512, error = null) }
```

`startRequest` returns `null` when the request is not recorded (network capture off, a request of the SDK's own); `error` names a failure when no response came.

### Connect requests to backend traces

`propagateTraceHeaderUrls` (prefixes) and `propagateTraceHeaderUrlPatterns` (regular expressions) list the URLs whose requests carry a W3C `traceparent` header naming the request's client span, so the backend's spans join the app's trace in Traceway or any OpenTelemetry backend:

```kotlin
TracewayOptions(
    propagateTraceHeaderUrls = listOf("https://api.example.com/"),
    propagateTraceHeaderUrlPatterns = listOf(Regex("^https://[a-z]+\\.example\\.com/")),
)
```

It is empty by default, because a header a server does not expect can break a strict CORS or request-signature check. A request that already carries a `traceparent` keeps it. Requests to Traceway and to the `telemetry` receivers never carry it. The backend must extract `traceparent`, as any OpenTelemetry HTTP instrumentation does; see [distributed tracing](/client/js-sdk/distributed-tracing) for the same mechanism in the browser SDK.

## App performance metrics

The SDK measures the app on the device and uploads the numbers as OTLP metrics: base-2 exponential histograms and counters (delta temporality), one small payload every five minutes and when the app goes to the background. Nothing is sent per observation, and no user, device or session ID is a dimension. The project's **Mobile Performance** dashboard charts them; its ANR and out-of-memory series stay empty for Android, which sends no `app.anr` or `app.oom`.

| Metric | What it measures |
|--------|------------------|
| `app.start.duration` (`start_type` `cold` / `warm` / `hot`) | Cold: from the process start (`Process.getStartElapsedRealtime()`, API 24+; earlier, from SDK init) to the first frame, only when the process was started for an activity. Warm and hot: from the return to the foreground to the next frame; warm when an activity had to be created |
| `app.screen.ttid` (`screen`) | Time to initial display: from the navigation to the first frame of the screen |
| `app.screen.ttfd` (`screen`) | Time to full display: from the navigation until the app calls `Traceway.reportFullyDisplayed()` |
| `app.frames.slow`, `app.frames.frozen` (with `.total`, by `screen`) | `FrameMetrics` on API 24+ (Choreographer below): slow when a frame missed its deadline at the display's refresh rate, frozen at 700 ms or more |
| `app.hang`, `app.hang.duration` (by `screen`) | The main thread ran nothing for 2 s or more while the app was in the foreground |
| `app.crash` | Uncaught exceptions |
| `app.session`, `app.user`, `app.user.affected` (`issue`: `crash`, `hang`, `slow_start`, `frozen_frames`, `failed_request`) | Sessions; users counted once a day per installation, and once a day per problem they met, so no ID leaves the device |
| `app.memory.peak` | The process's peak RSS, once per session |
| `app.request.duration`, `app.request.bytes`, `app.request.failed` (`host`) | Every HTTP request the SDK records |

Screens are route names with IDs folded (`/orders/8841` becomes `/orders/:id`), or the [route template](#naming-screens) when one is set. Resource dimensions are the app version, environment, OS and its major version, form factor (`phone`, `tablet`, `desktop`) and a coarse device class from the RAM.

```kotlin
// The screen has what it loads: ends its time to full display.
Traceway.reportFullyDisplayed()

// App-defined metrics, charted like the built-in ones.
Traceway.metric("checkout.duration", 1234.0, mapOf("plan" to "pro"))
Traceway.count("cart.add")
Traceway.setMetricDimension("experiment", "b") // custom.experiment on every metric
```

An app-defined metric name is lowercase (`[a-z][a-z0-9_.]`, at most 63 characters) and does not start with `app.`, `browser.`, `traceway.` or `custom.`; other names are dropped. A call keeps at most two dimensions, and the server accepts up to 50 app-defined metrics per project.

`captureMetrics = false` turns it all off. A rule's `metrics` section switches metrics off (`enabled`), samples sessions (`sampleRate`; counts are weighted back by the server) or changes the upload interval (`flushSeconds`, 30 to 3600).

## Setups

The connection string and `telemetry` decide where each kind of data goes. The first setup needs nothing beyond the connection string.

### Everything on Traceway

```kotlin
Traceway.init(
    application = this,
    connectionString = "your-token@https://traceway.example.com",
    options = TracewayOptions(serviceName = "shop-app", environment = "production"),
)
```

The app polls Traceway for its collection settings, sends logs, request spans and metrics to Traceway's OTLP endpoints (`/api/otel/v1/logs`, `/api/otel/v1/traces`, `/api/otel/v1/metrics`) and uploads replays to `/api/recordings` on the same host. What it collects is changed on the project's **Data Collection** page; see [Remote config](#remote-config).

### Issues and replays on Traceway, other telemetry elsewhere

Add `telemetry` to send ordinary logs, request spans and metrics to another OTLP/HTTP receiver, such as an OpenTelemetry Collector in front of a Grafana stack:

```kotlin
TracewayOptions(
    serviceName = "shop-app",
    telemetry = TracewayTelemetry(
        url = "https://collector.example.com/otlp",
        headers = mapOf("x-ingest-key" to "app-ingest-key"),
        // Optional overrides are complete signal URLs; no path is appended.
        metrics = TracewayTelemetryEndpoint(url = "https://metrics.example.com/v1/metrics"),
    ),
    collection = mapOf(
        "signals" to mapOf("console" to mapOf("mode" to "stream"), "network" to mapOf("mode" to "stream")),
    ),
)
```

The shared `url` gets `/v1/logs`, `/v1/traces` and `/v1/metrics` appended. Each signal (`logs`, `traces`, `metrics`) can override it with a `TracewayTelemetryEndpoint(url, headers)` whose URL is used as given. Without a shared `url`, the signals you do not list keep their Traceway destination. URLs must use HTTP(S), without embedded credentials, a query or a fragment. Signal headers override the shared `headers` key by key; the Traceway token is never sent to these receivers.

When logs are redirected, exceptions, `captureMessage` issues and the SDK's session and control records still go to Traceway, and only there. Ordinary logs (console lines, `Traceway.log`, screens, taps, `recordAction`, `track`) go to the logs receiver; request spans and metrics use their own destinations. Remote config and replays keep using the connection string. Both destinations carry `session.id` for correlation. Failed batches are queued on disk per destination.

The receiver must accept OTLP/HTTP with protobuf bodies (`application/x-protobuf`, gzip). Any key built into the app can be read out of it: use an ingestion key that can only write, or a collector that holds the backend credentials.

### Standalone, without a Traceway server

```kotlin
Traceway.init(
    application = this,
    options = TracewayOptions(
        serviceName = "shop-app",
        telemetry = TracewayTelemetry(url = "https://collector.example.com/otlp"),
        collection = mapOf("signals" to mapOf("console" to mapOf("mode" to "stream"))),
    ),
)
```

No Traceway server, account or token is required. `telemetry` must have a shared `url` or all three signal endpoints. Standalone mode turns off remote config, replay uploads and session records, whatever the options say. Exceptions are ordinary OTLP log records with the event name `exception`, and messages `traceway.message`.

## Options

`TracewayOptions` accepts the following parameters. The `capture*` options, `screenCapture`, `replayImages` and `sessions` are ceilings: remote settings can lower what is collected but never raise it.

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `sampleRate` | `Double` | `1.0` | Share of exceptions and messages that are reported (0.0 to 1.0) |
| `debug` | `Boolean` | `false` | Log what the SDK does to Logcat (tag `Traceway`) |
| `version` | `String` | `""` | App version, sent as `service.version` (`unknown` when empty) |
| `serviceName` | `String?` | application id | Sent as `service.name` |
| `environment` | `String?` | none | Sent as `deployment.environment.name` |
| `attributes` | `Map<String, String>` | `{}` | Attributes attached to every record, also used for remote-config targeting |
| `screenCapture` | `Boolean` | `false` | Record a [wireframe session replay](#session-replay): the last seconds go up with an exception, and captures can stream it |
| `replayImages` | `TracewayImagePolicy` | `ALWAYS` | Most the replay records of image views: `OFF`, `WIFI` (unmetered networks only) or `ALWAYS`; the `replay.images` setting (`wifi` by default) can lower it (see [Images](#images)) |
| `fps` | `Int` | `10` | Most wireframe frames captured per second (1 to 30); frames are taken only after the app drew |
| `maxBufferFrames` | `Int` | `150` | Wireframe frames held on the device (at least 2); the upper bound of every clip |
| `persistToDisk` | `Boolean` | `true` | Keep SDK state and undelivered telemetry on disk across restarts |
| `captureLogs` | `Boolean` | `true` | Capture `System.out` / `System.err` and `Traceway.log` |
| `captureNetwork` | `Boolean` | `true` | Record HTTP calls made through `TracewayOkHttpInterceptor` (or `startRequest` / `endRequest`) |
| `captureNavigation` | `Boolean` | `true` | Record activity and fragment screens and `Traceway.recordNavigation` |
| `captureUserActions` | `Boolean` | `true` | Record taps with the selector of the view, and feed taps and hovers to recording triggers |
| `captureMetrics` | `Boolean` | `true` | Measure [app performance](#app-performance-metrics) and upload it as metrics |
| `metricDimensions` | `Map<String, String>` | `{}` | Up to two app-defined dimensions on every metric (`custom.<key>`) |
| `recordAllSessions` | `Boolean` | `false` | Stream breadcrumbs and the replay all the time instead of keeping them for errors |
| `collection` | `Map<String, Any?>?` | none | Local collection settings, the same document as a remote-config rule (see [Local config](#local-config)) |
| `sessions` | `Boolean` | `true` | Send session records (`session.start` / `session.end`); the session ID exists either way |
| `baselineSampleRate` | `Double` | `0.0` | Share of sessions whose breadcrumbs are sent continuously, not only around errors |
| `remoteConfig` | `Boolean` | `true` | Poll the server for collection settings over OpAMP |
| `exportDelayMs` | `Long` | `1000` | How long finished records wait to be sent as one batch (at least 50 ms) |
| `telemetry` | `TracewayTelemetry?` | none | Send logs, spans and metrics to another OTLP/HTTP receiver (see [Setups](#setups)) |
| `propagateTraceHeaderUrls` | `List<String>` | `[]` | URL prefixes whose requests carry a W3C `traceparent` header (see [Connect requests to backend traces](#connect-requests-to-backend-traces)) |
| `ignoreErrors` | `List<Any>?` | `null` (the network-noise defaults) | `String`s and `Regex`es matched against the first line `Type: message`; a list replaces the defaults (see [Errors and messages](#errors-and-messages)) |
| `beforeCapture` | `((TracewayCapturedError) -> Boolean)?` | none | Return `false` to drop an exception or message |
| `legacyConnectionString` | `String?` | none | The connection string a 1.x build used, to deliver its unsent reports (see [Migrating from 1.x](#migrating-from-1x)) |
| `proguardUuid` | `String?` | none | The R8 build UUID, `BuildConfig.TRACEWAY_PROGUARD_UUID` from the [symbols plugin](/symbolicator/android) |
| `propagateTraceHeaderUrlPatterns` | `List<Regex>` | `[]` | Like `propagateTraceHeaderUrls`, as regular expressions |

## Crashes and symbolication

Every uncaught exception, on every thread, reaches the SDK through the default `UncaughtExceptionHandler`. The exception, its breadcrumbs and its replay clip are written to disk before the handler that was installed before (normally the platform's) ends the process. On any thread but the main one the SDK then tries to send them, holding the crashing thread for at most 2.5 seconds in all; a crash on the main thread is not sent then, so the frozen screen does not wait. What is left goes at the next start. The crash is never swallowed.

Release builds run R8, which renames classes and methods and rewrites line numbers. Traceway reverses a crash with the build's `mapping.txt`, matched by the ProGuard UUID the SDK sends as the `app.debug.proguard_uuid` resource attribute of every record. The `com.tracewayapp.symbols` Gradle plugin injects a UUID into `BuildConfig.TRACEWAY_PROGUARD_UUID` and uploads the mapping (`upload<Variant>TracewaySymbols`, or after `assemble<Variant>` with `autoUpload = true`). The UUID is derived from the module path, the variant, `versionName` and `versionCode` unless you set `proguardUuid` in the plugin's `traceway { }` block, so bump the version for each release. Pass the UUID to the SDK:

```kotlin
Traceway.init(
    application = this,
    connectionString = "your-token@https://traceway.example.com",
    options = TracewayOptions(
        version = BuildConfig.VERSION_NAME,
        proguardUuid = BuildConfig.TRACEWAY_PROGUARD_UUID,
    ),
)
```

Exceptions sent as log events and as span events are both retraced, and the issue shows the original classes, methods and lines. Plugin setup and the upload API are in [Android symbolication](/symbolicator/android). Symbolication happens on Traceway, so exceptions sent only to another backend in [standalone mode](#standalone-without-a-traceway-server) keep their obfuscated traces.

## What gets captured automatically

After `Traceway.init`, with no further code:

- **Uncaught exceptions** on every thread (see [Crashes and symbolication](#crashes-and-symbolication)).
- **Sessions**: a new one after 15 minutes without activity, and at the latest after an hour.
- **Logs**: every `System.out` / `System.err` line.
- **Screens**: activities and AndroidX fragments; other routers through `Traceway.recordNavigation`.
- **Taps**: every tap in the app's activity windows, with the selector, class, ID, shown text and label of the view, and the screen. Dialogs and popups (Compose ones included) have windows of their own, and taps there are not recorded.
- **Network**: OkHttp requests through `TracewayOkHttpInterceptor`.
- **App performance metrics**.

Breadcrumbs (logs, screens, taps, requests, actions) wait in the ring buffer and show on the session timeline next to the exception that flushed them.

### Disabling channels

Each channel can be turned off in `TracewayOptions`. No remote setting can turn it back on:

```kotlin
TracewayOptions(
    captureLogs = false,        // System.out / System.err, Traceway.log
    captureNetwork = false,     // OkHttp interceptor, startRequest / endRequest
    captureNavigation = false,  // screens
    captureUserActions = false, // taps
    captureMetrics = false,     // app performance metrics
)
```

## Platform support

| Platform | Error Tracking | Session Replay | Metrics |
|----------|---------------|----------------|---------|
| Android (API 21+) | Yes | Wireframe (views and Jetpack Compose) | Yes |

Below API 26, enable core library desugaring (see [Installation](#installation)). For Flutter apps, use the [Flutter SDK](/client/flutter) instead.

### Platform differences

The API has the names of the [browser](/client/js-sdk), [Flutter](/client/flutter) and [iOS](/client/ios) SDKs. Where Android differs, it is for these reasons:

- **Start**: `Traceway.init(application, connectionString, options)` takes the `Application`, which the SDK needs to follow activities and fragments, record taps and the wireframe, keep its files and read the network state. It returns the `TracewayClient`, or `null` when the settings are invalid (logged, not thrown); `Traceway.init(application, options)` starts standalone. Flutter starts with `Traceway.run`, iOS with `Traceway.initialize`.
- **Masks** belong to views: `view.tracewayMask` in Kotlin, `Traceway.mask(view, mode)` / `Traceway.unmask(view)` from Java (an extension property reads poorly there), `Modifier.tracewayMask(mode)` in Compose. The markers that need no code are `android:tag` and Compose `testTag` values (`traceway-mask`, `traceway-blank`), where the browser uses CSS classes and Flutter a `ValueKey`. `TracewayMaskMode.blank(color)` takes an ARGB `Int`.
- **Blocking, in milliseconds**: `flush(timeoutMs)` and `shutdown(timeoutMs)` (10 s by default) block the calling thread instead of returning a promise or future: call them off the main thread. iOS takes seconds (`flush(timeout:)`).
- **Properties and Java**: `Traceway.currentSessionId` is a property, as in Flutter and iOS (`getCurrentSessionId()` from Java, a function in the browser); `getInstanceId()` is a method, as in the browser and Flutter (iOS: `instanceId`). Every method is a `@JvmStatic` on `Traceway`, with Java overloads for the optional parameters.
- **Enum constants in Kotlin case**: `TracewayLogLevel.WARN` (`"warn"` in the browser, `.warn` in Flutter and iOS), `TracewayImagePolicy.WIFI` for the setting `replay.images: "wifi"`.
- **Throwables carry their stack**: `captureException(error, attributes)` has no stack trace parameter (Flutter's has one), and `log(message, level, attributes)` takes no error.
- **Navigation**: activities and AndroidX fragments are reported without code; Compose Navigation and other routers call `recordNavigation(path, action, from, route)`, positional in that order from Java (Flutter takes them by name).
- **Requests** are recorded by `TracewayOkHttpInterceptor` on the app's `OkHttpClient`, or with `Traceway.client?.startRequest` / `endRequest` for another HTTP stack; nothing is patched.
- **Options**: `TracewayOptions` is a Kotlin constructor; pass its parameters by name. `proguardUuid` and `propagateTraceHeaderUrlPatterns` exist only on Android.

## Migrating from 1.x

- **Server**: 2.0 sends OTLP to `/api/otel/v1/logs`, `/api/otel/v1/traces` and `/api/otel/v1/metrics`, polls `/api/otel/v1/opamp` and uploads replays to `/api/recordings`. There is no fallback to the 1.x `/api/report` protocol.
- **Connection string**: unchanged. `token@https://host/api/report` still works, as does `token@https://host`. It is optional now: without it the SDK runs [standalone](#standalone-without-a-traceway-server).
- **Unsent 1.x reports**: set `TracewayOptions(legacyConnectionString = previousConnectionString)` to the connection string the old build used. Reports 1.x left on the device are delivered to that project's `/api/report` and expire after 12 hours, the 1.x default. Without it they expire on the device.
- **Desugaring**: an app with `minSdk` below 26 must enable core library desugaring.
- **Behaviour**: logs and actions are no longer limited to the last 10 seconds and no longer travel inside the report. They are buffered for up to 10 minutes and sent as their own records with an exception. `screenCapture = true` now records a wireframe session replay.
- **Removed options**: `debounceMs`, `retryDelayMs`, `maxPendingExceptions`, `maxLocalFiles`, `localFileMaxAgeHours`, `eventsWindowMs`, `eventsMaxCount`, `capturePixelRatio`. `fps` and `maxBufferFrames` now apply to the wireframe replay.
- **Removed API**: `TracewayClient.addException`, `loadPendingFromDisk`, `setDeviceAttributes`, `bufferedLogs`, `bufferedActions`, `pendingExceptionCount` and the other test accessors, `recordNetworkEvent`, `recordNavigationEvent`, the `ReportSender` interface and the 1.x event and report models. Use `captureException`, `Traceway.setAttribute`, `startRequest` / `endRequest`, `recordNavigation` and `flush()`.
- **Changed API**: `Traceway.init` returns `TracewayClient?` (null when the settings are invalid). `TracewayClient.flush(timeoutMs)` takes a non-null timeout (10 s by default). `TracewayOptions` lists its parameters in the order the other SDKs do: pass them by name.
- **Renamed during the 2.0 beta**: `Traceway.recordLog(message, severity)` is `Traceway.log(message, level, attributes)` with `TracewayLogLevel`. The old name still works and is deprecated.
- **New API**: `Traceway.log`, `track`, `setAttribute(s)`, `removeAttribute`, `clearAttributes`, `recordNavigation`, `setRoute`, `startInteraction`, `reportFullyDisplayed`, `metric`, `count`, `setMetricDimension`, `mask` / `unmask`, `refreshConfig`, `shutdown`, `getInstanceId`, `currentSessionId`; `View.tracewayMask`, `Modifier.tracewayMask()`; `TracewayLogLevel`, `TracewayInteraction`, `TracewayCapturedError`, `TracewayImagePolicy`, `TracewayTelemetry`, `TracewayTelemetryEndpoint`, `TracewayMaskMode`; the options `replayImages`, `ignoreErrors` and `beforeCapture`.
- **Issues regroup once**: the stack trace now reaches the server as the OpenTelemetry `exception.*` attributes, so the first 2.0 occurrence of an issue may start a new group.

## Testing

```kotlin
// Send a test error
Traceway.captureException(RuntimeException("Test error from Traceway integration"))
Traceway.flush()
```

Or throw one (`throw RuntimeException("Test error")`) and open the app again: the crash is sent at once or at the next start. The issue shows its stack trace, the breadcrumbs before it and, with `screenCapture = true`, the replay of the last seconds. `debug = true` logs every upload to Logcat under the tag `Traceway`.
