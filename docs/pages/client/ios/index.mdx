# iOS Quick Start

Integrate Traceway into your iOS app with the [`traceway-ios`](https://github.com/tracewayapp/traceway-ios) Swift package. The SDK is built on the official OpenTelemetry Swift SDK ([`opentelemetry-swift`](https://github.com/open-telemetry/opentelemetry-swift)): crashes, errors, logs and request spans leave as OTLP/HTTP, performance metrics as OTLP metrics, and the SDK polls Traceway over [OpAMP](https://opentelemetry.io/docs/specs/opamp/) for its collection settings, like the [browser SDK](/client/js-sdk) 2.x, the [Flutter SDK](/client/flutter) 2.x and the [Android SDK](/client/android) 2.x. Session replay records the view hierarchy as a wireframe that the dashboard plays with its rrweb player.

> **2.0 is a beta.** It needs a Traceway server that accepts iOS projects on its OTLP and OpAMP endpoints; there is no fallback to the 1.x `/api/report` protocol. On an older server stay on 0.1.x. See [Migrating from 1.x](#migrating-from-1x).

## Features

- Uncaught `NSException`s and fatal signals (Swift traps, `fatalError`, bad memory access), symbolicated on the server from your uploaded dSYMs
- OpenTelemetry inside: every record is a log record or span made with `opentelemetry-swift` and leaves through its OTLP/HTTP exporters
- A ring buffer on the device: logs, requests, screens, taps and custom events are uploaded only when something goes wrong
- Remote config over OpAMP: signal modes, sample rates, triggers and captures from the project's **Data Collection** page, or the same settings in the app with `collection:`
- Captures on demand, from the dashboard or from a recording trigger on the device (a journey of taps, screens and log lines)
- Wireframe session replay of UIKit and SwiftUI screens, with pictures of image views when the image policy allows them
- Taps that name the view: every tap is recorded with a CSS-like selector (`UIButton#pay`, `UIButton[label="Delete"]`) that click steps of recording triggers match
- App performance metrics: start, screen display times, slow and frozen frames, hangs, crashes, sessions, users, memory and requests, aggregated on the device; they fill the project's **Mobile Performance** dashboard
- Network requests as client spans with the official URLSession instrumentation, and W3C `traceparent` propagation to your backend
- Any OpenTelemetry backend: logs, spans and metrics to an OTLP/HTTP receiver, next to Traceway or without it

## Requirements

- iOS 13.0 or later.
- Xcode 26.4 or later (Swift 6.3). The OpenTelemetry Swift packages need Swift 6, and the `swift-log` release SwiftPM resolves for them needs the Swift 6.3 compiler.
- A Traceway server that accepts iOS projects on its OTLP and OpAMP endpoints, or an OTLP/HTTP receiver for [standalone](#standalone-without-a-traceway-server) use.

## Installation

Install with Swift Package Manager. In Xcode, choose **File > Add Package Dependencies**, enter the repository URL and ask for `2.0.0-beta.1` or later:

```
https://github.com/tracewayapp/traceway-ios.git
```

Or add it to your `Package.swift`. SwiftPM only offers a prerelease to a requirement that names one:

```swift
dependencies: [
    .package(url: "https://github.com/tracewayapp/traceway-ios.git", from: "2.0.0-beta.1"),
],
```

The package identity is `traceway-ios` and the library product is `Traceway`, so a target needs the explicit form:

```swift
.target(
    name: "MyApp",
    dependencies: [.product(name: "Traceway", package: "traceway-ios")]
),
```

The package brings in `opentelemetry-swift-core`, `opentelemetry-swift` and `swift-protobuf`. SwiftPM also resolves, but does not build, the gRPC and NIO packages `opentelemetry-swift` declares.

## Quick start

Start the SDK as early as possible, so it is installed before any code that might crash. In SwiftUI, do it in your `App` initializer:

```swift
import SwiftUI
import Traceway

@main
struct MyApp: App {
    init() {
        Traceway.initialize(
            connectionString: "your-token@https://traceway.example.com",
            options: TracewayOptions(
                version: "1.0.0",
                screenCapture: true
            )
        )
    }

    var body: some Scene {
        WindowGroup { ContentView() }
    }
}
```

In UIKit, do it in `application(_:didFinishLaunchingWithOptions:)`:

```swift
func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
) -> Bool {
    Traceway.initialize(
        connectionString: "your-token@https://traceway.example.com",
        options: TracewayOptions(version: "1.0.0", screenCapture: true)
    )
    return true
}
```

The connection string is the project token and the server URL, as the project's **Connection** page shows it. The 1.x form ending in `/api/report` works too; every endpoint is derived from it. An invalid connection string or `telemetry` setting does not take the app down: `Traceway.initialize` returns `nil`, logs why, and the app runs without the SDK. To send telemetry to another OpenTelemetry backend as well, or only there, see [Setups](#setups).

## Manual capture

Every call is a static on `Traceway` and does nothing before `Traceway.initialize`.

### Errors and messages

```swift
import Traceway

// Any Swift error, NSError included
do {
    try checkout()
} catch {
    Traceway.captureException(error, attributes: ["order": order.id])
}

// A message, reported as an issue
Traceway.captureMessage("User completed onboarding")

// Send what is ready now (seconds; nil waits until done)
Traceway.flush(timeout: 5)
```

Every exception and message also says where the app was when it happened: `app.screen.name` (the screen on top), `app.screen.route` when a [route template](#naming-screens) is set, `app.screen.previous`, `app.screen.duration_ms` (how long the screen had been shown) and `viewport` (the window's size in points, `<width>x<height>`). Attributes you pass to `captureException` win over these.

By default, network failures are not reported: the `NSURLErrorDomain` errors -1001 (timed out), -1003 (cannot find host), -1004 (cannot connect to host), -1005 (network connection lost) and -1009 (not connected to the internet), "The network connection was lost", "The Internet connection appears to be offline", a timeout (`/timeout/i`) or a 4xx status (`/status code (of )?4\d{2}/`, `/failed: 4\d{2}/`). `ignoreErrors` replaces that list (`nil`, the default, keeps it; the list is `TracewayOptions.defaultIgnoreErrors`). Each entry is a `TracewayErrorPattern`: a string literal (or `.contains(_:)`) matches if it occurs in the first line of the error's `Type: message`, and `.regex(_:)`, which takes an `NSRegularExpression` or a pattern string, if it finds a match in that line; the stack is never matched. An empty list reports everything. `beforeCapture` sees every exception and message that is not ignored and returns `false` to drop it; a callback that throws is logged in debug and the record is kept. Crashes skip both filters and are always reported: uncaught `NSException`s and fatal signals end the process, as on Android.

```swift
TracewayOptions(
    beforeCapture: { captured in !(captured.error is CardDeclinedError) }
)
```

`TracewayCapturedError` carries `error` (`nil` for a message), `type`, `message`, `isMessage`, `attributes` and `stackTrace` (`nil` for a message).

### Logs

```swift
Traceway.log("Loaded 12 items")
Traceway.log("Payment retried", level: .warn, attributes: ["attempt": "2"])
```

A log line has the level's severity (`TracewayLogLevel`: `.trace`, `.debug`, `.info`, `.warn`, `.error`, `.fatal`; `.info` by default), the attributes you pass and `log.source` `api`. The console's `minSeverity` setting (`info` by default) drops lines below it, so `.trace` and `.debug` lines are kept only when a rule or `collection` lowers it. `print`, `NSLog` and `os_log` output is not captured: call `Traceway.log` where a line should reach the timeline. `captureLogs: false` turns logs off. Log lines are the `console` signal: they wait in the ring buffer and go up with an exception, a trigger or a capture.

### Actions and events

```swift
// A breadcrumb on the session timeline
Traceway.recordAction(category: "cart", name: "add_item", data: ["sku": "SKU-123", "qty": 2])

// A named product event; triggers can match it by name
Traceway.track("checkout_failed", attributes: ["reason": "card_declined"])
```

`recordAction` records a `traceway.action` record with its category, name and data. `track` records an event whose `event.name` is the name you give, so a trigger step can match it (`{"key": "event.name", "op": "eq", "value": "checkout_failed"}`). Both are the `custom` signal, and so are spans you make with `Traceway.tracer`, the SDK's OpenTelemetry tracer.

### Attributes and users

```swift
Traceway.setAttribute("user.id", user.id)
Traceway.setAttributes(["plan": "pro", "tenant": "acme"])
Traceway.removeAttribute("tenant")
Traceway.clearAttributes()
```

There is no `setUser`: `user.id` is an attribute like any other. Attributes go on every later record (at most 64 keys), and the server matches rules and captures against them; a change is sent with a config poll about 2 seconds later, so a rule that targets it applies soon. `Traceway.currentSessionId` is the session's ID and `Traceway.instanceId` the installation's (`service.instance.id`), the one the dashboard's Capture button targets. When the app has not set up OpenTelemetry itself, Traceway's providers also become the global ones (`OpenTelemetry.instance`), so instrumentation that uses them joins the session.

### Interactions

An interaction traces one user action from start to end: a span named after it (`traceway.interaction: true`). Requests made inside its `run` are its child spans, and exceptions, messages and logs recorded there carry its trace ID. The span is the `custom` signal: it ends after the exception that marks it failed, so it is not part of that exception's upload, and like any span it waits in the ring buffer until a later trigger or capture uploads it.

```swift
let checkout = Traceway.startInteraction("checkout", attributes: ["plan": "pro"])
defer { checkout.end() }
do {
    try checkout.run { try api.placeOrder(cart) }
} catch {
    checkout.captureException(error)
}
```

`captureException` reports the error with the interaction's trace and marks the interaction failed; `end(failed: true)` marks it failed without one. `traceId` and `spanId` name its span, and `setAttribute` adds an attribute to it.

## How collection works

Every record is an OpenTelemetry log record or span and belongs to a *signal*. Each signal is in one of three modes: `stream` sends it as soon as it is produced, `buffer` keeps it in a ring buffer on the device (2 MiB / 10 minutes by default) until a trigger or a capture uploads it, and `off` drops it.

| Signal | Source | Default |
|--------|--------|---------|
| `errors` | crashes, uncaught `NSException`s, `Traceway.captureException` | stream |
| `messages` | `Traceway.captureMessage` | stream |
| `console` | `Traceway.log` | buffer |
| `network` | URLSession requests (client spans) | buffer |
| `navigation` | view controllers that appear, `.tracewayScreen`, `Traceway.recordNavigation` | buffer |
| `userActions` | taps (`browser.user_action.click`) | buffer |
| `custom` | `Traceway.recordAction`, `Traceway.track`, your own spans | buffer |
| replay | the [wireframe session replay](#session-replay) | buffer |

The built-in trigger fires on every exception: it uploads the buffered breadcrumbs of the last 10 minutes and the replay of the last 30 seconds, at most the frames the replay ring holds (`maxBufferFrames`). An app that never throws sends only its session and control records (`session.start`, `session.end`, `traceway.session.update`, `traceway.config.applied`) and its metrics. Clips are rationed to one per 5 seconds and 20 per session; breadcrumbs are still sent for the exceptions in between.

`recordAllSessions: true` streams every breadcrumb signal and the replay instead. `baselineSampleRate` streams the breadcrumbs of a share of sessions, chosen by session ID.

The ring buffer is saved to disk when the app goes to the background and at shutdown, and restored when the same session goes on after a restart, so a session that continues after the system killed the app still has its breadcrumbs. Exceptions are written to disk before they are sent, and telemetry that failed to send is kept on disk and retried.

The signal names, modes, triggers and limits are the browser, Flutter and Android SDKs', so one rule can target all of them. See the [settings reference](/learn/remote-config/reference#the-settings-document).

## Remote config

The SDK polls the server over OpAMP (plain HTTP, protobuf): at start, at the interval the server sets (5 minutes by default, 60 seconds while a capture targets the device), when the app returns to the foreground, and about 2 seconds after `Traceway.setAttribute` or a new session, so a rule targeting an attribute applies soon. It applies the collection settings you define under **Data Collection** in the project's sidebar: signal modes and sample rates, buffer sizes, replay and image settings, metrics settings, extra triggers (for example "flush when `checkout_failed` happens twice in a minute") and on-demand captures of one user or device. See [Remote SDK Config](/learn/remote-config/setup) for a walkthrough.

- The `capture*` options, `screenCapture`, `replayImages` and `sessions` are **ceilings**. Remote settings can lower what is collected but never raise it: with `captureNetwork: false` no rule can turn network capture on, and without `screenCapture: true` nothing is recorded. `sampleRate`, `baselineSampleRate` and `recordAllSessions` are defaults: a rule can change them in either direction.
- The last applied settings are cached, so they are in effect from the first moment of the next start.
- Set `remoteConfig: false` to never poll. Standalone (no connection string) the SDK never polls either.
- `Traceway.refreshConfig()` polls now.

### Local config

`collection` takes the same settings document a rule holds and lays it over the built-in defaults, so an app can define its own policy and triggers without the server. With `remoteConfig: true` the server's rules apply on top of it; with `remoteConfig: false` it is the whole policy.

```swift
Traceway.initialize(
    connectionString: "your-token@https://traceway.example.com",
    options: TracewayOptions(
        screenCapture: true,
        collection: [
            "signals": ["network": ["mode": "stream"]],
            "buffer": ["maxAgeSeconds": 300],
            "replay": ["images": "always"],
            "triggers": [[
                "id": "checkout-failed-twice",
                "steps": [[
                    "match": ["key": "event.name", "op": "eq", "value": "checkout_failed"],
                    "count": 2, "periodSeconds": 60,
                ]],
                "actions": [[
                    "type": "capture", "durationSeconds": 300, "lookbackSeconds": 120, "replay": true,
                ]],
            ]],
        ],
        remoteConfig: false
    )
)
```

Values must be JSON types (strings, numbers, booleans, arrays and dictionaries). A document that is not an object, or names another `schemaVersion`, is ignored with a console warning, and the defaults apply; in a valid one, unknown fields and malformed values are skipped one by one. Triggers merge by `id`; see the [trigger reference](/learn/remote-config/reference#triggers).

## Captures

A capture uploads what the device holds from its lookback window and then streams the selected signals, and the replay when it asks for it, until it ends. Records sent while a capture from the dashboard runs carry its ID (`traceway.capture.ids`), so the dashboard shows when it is collecting.

- **From the dashboard**: the Capture button on a session or an issue targets one installation (`service.instance.id`), user (`user.id`) or session. The device starts it at its next poll; cancelling it stops the streaming at the poll after that.
- **From a trigger** (a `capture` action): started on the device the moment the trigger fires. It survives app restarts until it ends; firing again only extends it.

A capture that streams replay sends it as consecutive segments; see [Session replay](#session-replay).

### Recording triggers

The dashboard's [recording trigger](/learn/remote-config/trigger-sequences) steps work on iOS. The builder labels them **Tap**, **Navigation** and **Log**:

| Step | Matches |
|------|---------|
| `{"event": {"type": "click", "value": "<selector>"}}` | a tap on a view the selector matches, or inside one |
| `{"event": {"type": "navigation", "value": "/users/{id}"}}` | arriving at a screen; `{id}` is one non-empty segment |
| `{"event": {"type": "log", "value": "Profile loaded", "mode": "contains"}}` | a `Traceway.log` line or a `captureMessage` (`exact` by default) |

A `hover` step never matches: a touch screen has no hover. Steps match in order, each within its `withinSeconds` of the previous one; progress survives an app restart within the session. When a trigger that asks for replay fires, the session lists it as a recording reason with its sequence.

The step format is the browser SDK's, so the dashboard builds and validates both the same way. What a selector and a route pattern are compared with is different, because an iOS app has no DOM and no URL. The two sections below are the whole of that difference.

### Naming views

A click step takes a selector in CSS syntax. When a finger lifts, the SDK finds the view it touched: the view UIKit's hit-testing returns, and below it the topmost visible subview under the finger, because labels and image views do not take touches but are what a user sees and taps. It takes the chain from that view up to its window and runs the selector over the chain. A tap matches when the view under the finger or any of its superviews matches, the way a browser click matches its target or an ancestor. A tap is a finger that lifts within 10 points of where it went down and before 500 ms, the long-press duration, so a long press is not a tap.

Each part of the syntax reads one property of a view:

| Selector | Browser equivalent | Matches a view that |
|----------|--------------------|---------------------|
| `UIButton`, `CheckoutButton` | tag name | is of that class. The module and generic arguments are left out (`Shop.CheckoutButton<Int>` is `CheckoutButton`), and case is ignored; `*` is any view |
| `#checkout` | `id` attribute | has `accessibilityIdentifier = "checkout"` |
| `.button` | class | has that role, from its accessibility traits or its class: `button`, `link`, `header`, `image` (also any `UIImageView`), `textField` (`UITextField`, `UITextView`, the search field trait), `slider` (`UISlider`, the adjustable trait), `toggle` (`UISwitch`, the toggle button trait on iOS 17), `selected` |
| `[key="42"]` | attribute | has `tag = 42` |
| `[identifier="..."]` | attribute | has that `accessibilityIdentifier` |
| `[label="Delete"]` | attribute | has that `accessibilityLabel`: its own, else the first one directly below it, as long as each view down there has a single subview (an icon button's image view) |
| `[text="Pay"]` | none | shows that text: a label's text or a button's title, else the text of up to three labels under it, joined by a space. Never the content of a text field or text view |
| `[type="_Private"]` | none | is of a class that cannot be written as a tag |

No other attribute names exist except `id`, which is the same as `#` (`[id="pay"]` is `#pay`). A view has no `data-*` attributes; give it an `accessibilityIdentifier` instead.

```swift
// #pay, or UIButton#pay
payButton.accessibilityIdentifier = "pay"

// UIButton[label="Delete"]
deleteButton.accessibilityLabel = "Delete"

// UIButton[text="Pay now"], when nothing better exists
payButton.setTitle("Pay now", for: .normal)

// #cart UIButton: any button inside the view identified as cart
cartView.accessibilityIdentifier = "cart"
```

The rules the dashboard and the SDK both apply:

- Attribute values take `=`, `^=` (starts with), `$=` (ends with), `*=` (contains), `~=` (one of its words) and `|=`. Quote a value that is not a plain name: `[key="42"]`, not `[key=42]`.
- A selector is at most 256 characters and cannot contain `:`, `,` or `\`, also inside a quoted value. Pseudo-classes and selector lists are therefore not available, and `[text="Total: 5"]` is refused: match the start instead, `[text^="Total"]`.
- Combinators are descendant (space), child (`>`), adjacent (`+`) and general (`~`) sibling, over the view hierarchy: siblings are subviews of the same superview, in their order. A `UIButton` holds its title in a label and, with a configuration, background views, so use the descendant combinator (`#cart UIButton`) rather than `>` across them.
- A selector that names text depends on the copy: it stops matching when the wording changes or the app runs in another language. `accessibilityIdentifier`s, the handles UI tests already use, are the stable choice.
- **SwiftUI** draws its controls without views of their own. A tap on a SwiftUI button finds the hosting view, so a selector cannot name one SwiftUI control, and `.accessibilityIdentifier` on a SwiftUI view is not read. Target SwiftUI journeys with navigation steps (`.tracewayScreen`) and log steps instead. UIKit views inside SwiftUI (`UIViewRepresentable`) are views like any other.
- `captureUserActions: false` turns taps off, and click steps with them.

You rarely write a selector by hand. Every tap is recorded as `browser.user_action.click` with the selector of the view that handled it (`browser.css_selector`), and the **Actions** list of a session shows it, for example `UIButton#pay` or `UIButton[text="Pay now"]`. Copy it into a click step as it is: the SDK only records a selector it has checked against the tapped view. The view that handled the tap is the nearest control above the finger (a `UIControl`, a table or collection view cell, or a view with its own tap or long-press gesture recognizer; a view controller's root view does not count), else the nearest label or image view, else the view under the finger. Its selector is the first of these that exists and matches: an `accessibilityIdentifier` (its own, a wrapper's up to six levels above, or one inside it), its `tag`, the text it shows (up to 40 characters), its label, a role, the class with the nearest identified superview in front (`#cart UIButton`), and the class alone. The record also carries `app.widget.name` (the class), `app.widget.id`, `app.widget.text`, `app.widget.label`, `app.screen.coordinate.x`, `app.screen.coordinate.y` and `app.screen.name`. The text and the label of a view inside a [privacy mask](#privacy-masks), or of a secure text field, are never sent, and a mask identifier (`traceway-mask`, `traceway-blank`) never names a view.

### Naming screens

A navigation step is compared with the path of the screen the user arrives at. The SDK records a screen each time a view controller appears, and the app can report screens no view controller names:

| In the app | Reported path | A step that matches |
|------------|---------------|---------------------|
| `CheckoutViewController` appears | `/CheckoutViewController` | `/CheckoutViewController` |
| `UIHostingController(rootView: ProfileView())` appears | `/ProfileView` | `/ProfileView` |
| `OrderView(order: order).tracewayScreen("/orders/\(order.id)")` | `/orders/8841` | `/orders/{id}` |
| `Traceway.recordNavigation("/orders/8841?tab=items")` | `/orders/8841?tab=items` | `/orders/{id}` |

Navigation, tab, split and page view controllers are containers, not screens, and neither are child view controllers embedded in another screen or the system's own controllers (alerts, the keyboard's). A SwiftUI app that navigates inside one hosting controller (`NavigationStack`) reports one screen unless its views call `.tracewayScreen`, which records the path each time the view appears. A router of your own reports its screens with `Traceway.recordNavigation(path, action: "push", from: nil, route: nil)`; `action` is the kind of change, `from` the screen it left and `route` the route template the path is an instance of, when the router knows it.

How a pattern is compared:

- Only the path counts. A query string and a fragment are dropped before matching, and a pattern cannot contain `?`, `#` or `*`.
- A pattern starts with `/` and must have the same number of segments as the path. `/users/{id}` does not match `/users/42/edit`.
- `{name}` stands for exactly one non-empty segment and must be the whole segment. Every other segment compares as written, case-sensitively.
- `captureNavigation: false` turns navigation off, and navigation steps with it.

The same path is shown on each navigation row of the session timeline.

A route template (`/orders/:id`) names a screen the way it should be grouped. `Traceway.recordNavigation(path, route: "/orders/:id")`, or `Traceway.setRoute("/orders/:id")` after the navigation, names the current screen's template until the next screen; a navigation reported with `route` carries it as `app.screen.route`, and so do the exceptions and messages on that screen.

## Session replay

```swift
TracewayOptions(screenCapture: true)
```

Session replay on iOS is always a wireframe: the SDK records the view hierarchy, never the screen's pixels, and the dashboard plays it with the same rrweb player as a browser session, taps and drags included. A rule's `replay.captureMode` is for the Flutter SDK and does not apply.

- **Error clip.** An exception uploads the replay of the last 30 seconds (the replay `lookbackSeconds` of the built-in trigger), cut to the `maxBufferFrames` frames the device holds, and links it to the exception. A frame is kept only when the screen changed, so the default 150 frames at the default 4 fps cover at least 37 seconds, so the clip holds the whole 30 seconds.
- **Streaming.** While a capture or a rule streams replay, the session leaves as consecutive segments of up to 10 seconds, each starting with a full snapshot; the session player plays them back to back. An exception during a streaming capture still gets a clip of its own.
- **Background.** While the app is in the background the replay shows a plain "App in the background" screen.
- **Destination.** Replays always go to Traceway, also when `telemetry` sends the other signals elsewhere. Standalone, nothing is recorded.

### Wireframe

Up to `fps` times a second (4 by default) the SDK walks the app's windows and turns what they show into HTML: views with their background colors, gradients, corners, borders, shadows, opacity, clipping, transforms and scroll positions; labels with their font size, weight, style and color, alignment, line breaking, and rich text runs; buttons, text fields and text views; and switches, sliders, segmented controls, steppers, progress views, page controls and activity indicators drawn from their state. SF Symbols and template images keep their shape, monochrome symbols in their tint and palette or multicolor symbols in their own colors. iOS 26's Liquid Glass bars, buttons, alerts and sheets are drawn as frosted shapes. What changes from one frame to the next becomes an rrweb mutation, and a frame is kept only when the screen changed.

- **Small and cheap.** A segment is a few kilobytes of JSON, and the walk runs on the main thread only to read properties UIKit already holds.
- **Not pixel-exact.** Text is drawn in the browser's system font. Pictures follow the [image policy](#images). Views that draw themselves in `draw(_:)` are dashed outlines, and web views, maps, `AVPlayer` views, camera and Metal views are labeled placeholders.
- **SwiftUI** draws most of its content without views of its own. Its colors, shapes, gradients and symbols are recorded from its layers, and UIKit controls it hosts (a `Toggle`'s switch) as UIKit. Its text is readable only through accessibility, which iOS fills in while an assistive technology such as VoiceOver runs. Otherwise each `Text` is a neutral bar where its lines are, the way masked text would be.
- **Keyboard.** The on-screen keyboard is a plain box where the keyboard is, never its keys.
- **Typed text.** Text typed into fields is replaced with `*` unless a rule sets `replay.maskAllInputs: false`; secure fields always show bullets.

### Images

Whether the replay shows the pictures of image views is decided by the image policy: the `replay.images` setting of the [collection settings](/learn/remote-config/reference#replay) (`off`, `wifi` or `always`; `wifi` by default) under the `replayImages` option, a ceiling (`.always` by default). The lower of the two applies, in the order `off`, `wifi`, `always`, so `replayImages: .off` keeps every image a placeholder whatever a rule says.

- `wifi` records pictures only on an unmetered network: an `NWPathMonitor` path that is satisfied and neither expensive nor constrained, so cellular, a personal hotspot and Low Data Mode count as metered. The network is checked when a frame is captured, so a picture captured on Wi‑Fi stays in its clip.
- What is recorded is the image a `UIImageView` shows, and the photo contents of image layers (SwiftUI's images among them), never a screenshot of the window. An image inside a [privacy mask](#privacy-masks) is never recorded.
- A picture is scaled to 1.5 times its displayed size in points, at most 512 px on its longest side, and encoded as JPEG at quality 0.6 (PNG when it has transparency and is at most 128 px). One still larger than 96 KiB after a second try at half the size is left out. Encoding runs off the main thread, so the first frame shows a placeholder and a later one the picture.
- A session records at most 4 MiB of pictures; after that, placeholders. The bytes count against the session's replay budget (50 MiB and 10,000 rrweb events) like the rest of a segment.
- When the policy does not allow pictures, an image is a placeholder box. SF Symbols and template images keep their shape either way.

Session records carry `traceway.replay.images` (the policy in effect when the session started) and `traceway.replay.image_bytes`.

### Privacy masks

Masks hide content in the replay only; the app itself shows no change. The text and the label of a masked view are also left out of recorded taps.

```swift
// UIKit
cardNumberLabel.tracewayMask = .blank()                 // a black box; nothing inside is recorded
profileView.tracewayMask = .blur                        // the layout stays; text becomes *, images placeholders
balanceView.tracewayMask = .blank(color: .systemGray5)  // a box of another color
cardNumberLabel.tracewayMask = nil                      // no mask

// SwiftUI
Text(card.number).tracewayMask(.blank(color: .gray))
ProfileView().tracewayMask()                            // .blur
```

A UIKit view whose `accessibilityIdentifier` is `"traceway-mask"` is masked like `.blur`, and one whose identifier is `"traceway-blank"` like `.blank()`, with no other code; Interface Builder sets it too. SwiftUI's `.accessibilityIdentifier` cannot be read from the view hierarchy, so a SwiftUI view is masked with the `.tracewayMask(_:)` modifier. A SwiftUI mask covers whatever is drawn under its frame, so it also hides SwiftUI content that has no view of its own.

`tracewayPrivacyMask`, the name of the property and the modifier in earlier 2.0 beta builds, is a deprecated alias of `tracewayMask`.

## Network requests

Every URLSession request is recorded as a client span (method, URL, status, duration, `error.type`) by the official `URLSessionInstrumentation` of `opentelemetry-swift`, with the stable HTTP semantic conventions (`http.request.method`, `url.full`, `http.response.status_code`). The SDK's own requests are never recorded.

### Connect requests to backend traces

`propagateTraceHeaderUrls` lists the URL prefixes whose requests carry a W3C `traceparent` header naming the request's client span, so the backend's spans join the app's trace in Traceway or any OpenTelemetry backend:

```swift
TracewayOptions(propagateTraceHeaderUrls: ["https://api.example.com/"])
```

It is empty by default, because a header a server does not expect can break a strict CORS or request-signature check. Requests to Traceway and to the `telemetry` receivers never carry it. The backend must extract `traceparent`, as any OpenTelemetry HTTP instrumentation does; see [distributed tracing](/client/js-sdk/distributed-tracing) for the same mechanism in the browser SDK.

## App performance metrics

The SDK measures the app on the device and uploads the numbers as OTLP metrics: base-2 exponential histograms and counters (delta temporality), one small payload every five minutes and when the app goes to the background. Nothing is sent per observation, and no user, device or session ID is a dimension. The names, dimensions and thresholds are the [Android](/client/android#app-performance-metrics) and [Flutter](/client/flutter#app-performance-metrics) SDKs', so the project's **Mobile Performance** dashboard and SLOs read them the same way. iOS sends no `app.anr` or `app.oom`, so that dashboard's ANR and out-of-memory series stay empty for an iOS project.

| Metric | What it measures |
|--------|------------------|
| `app.start.duration` (`start_type` `cold` / `warm` / `hot`) | Cold: from the process start (from `Traceway.initialize` when iOS prewarmed the process) to the first frame drawn while the app is active, only when the process was launched to show its UI. Warm: the first return of a process launched in the background, or a return that reconnects a scene. Hot: from any other return to the foreground to the next frame |
| `app.screen.ttid` (`screen`) | Time to initial display: from the moment a view controller begins to load (`viewDidLoad`, or `viewWillAppear` for a view loaded before) to the first frame after `viewDidAppear`; for `recordNavigation` and `.tracewayScreen`, from the call |
| `app.screen.ttfd` (`screen`) | Time to full display: from the same start until the app calls `Traceway.reportFullyDisplayed()` |
| `app.frames.slow`, `app.frames.frozen` (with their `.total` counts, by `screen`) | A `CADisplayLink` in the foreground: slow when a frame took more than one and a half frame durations, frozen at 700 ms or more |
| `app.hang`, `app.hang.duration` | The main thread ran nothing for 2 s or more while the app was in the foreground; not while a debugger is attached unless `reportHangsInDebug` is set |
| `app.crash` | Uncaught `NSException`s, and fatal signals counted at the next start |
| `app.session`, `app.user`, `app.user.affected` (`issue`) | Sessions; users counted once a day per installation, and once a day per problem they met, so no ID leaves the device |
| `app.memory.peak` | The process's peak physical footprint (`task_vm_info`, what the system's memory limit counts), once per session |
| `app.request.duration`, `app.request.bytes`, `app.request.failed` (`host`) | Every URLSession request the SDK records |

Screens are paths with IDs folded (`/orders/8841` becomes `/orders/:id`), or the [route template](#naming-screens) when one is set. Resource dimensions are the app version, environment, OS and its major version, form factor (`phone`, `tablet`, `desktop`) and a coarse device class from the RAM.

```swift
// The screen has what it loads: ends its time to full display.
Traceway.reportFullyDisplayed()

// App-defined metrics, charted like the built-in ones.
Traceway.metric("checkout.duration", value: 1234, dimensions: ["plan": "pro"])
Traceway.count("cart.add")
Traceway.setMetricDimension("experiment", "b") // custom.experiment on every metric
```

`captureMetrics: false` turns it all off. A rule's `metrics` section switches metrics off (`enabled`), samples sessions (`sampleRate`; counts are weighted back by the server) or changes the upload interval (`flushSeconds`, 30 to 3600).

## Setups

The connection string and `telemetry` decide where each kind of data goes. The first setup needs nothing beyond the connection string.

### Everything on Traceway

```swift
Traceway.initialize(
    connectionString: "your-token@https://traceway.example.com",
    options: TracewayOptions(serviceName: "shop-app", environment: "production")
)
```

The app polls Traceway for its collection settings, sends logs, request spans and metrics to Traceway's OTLP endpoints (`/api/otel/v1/logs`, `/api/otel/v1/traces`, `/api/otel/v1/metrics`), and uploads replays to `/api/recordings` on the same host. What it collects is changed on the project's **Data Collection** page; see [Remote config](#remote-config).

### Issues and replays on Traceway, other telemetry elsewhere

Add `telemetry` to send ordinary logs, request spans and metrics to another OTLP/HTTP receiver, such as an OpenTelemetry Collector in front of a Grafana stack:

```swift
Traceway.initialize(
    connectionString: "your-token@https://traceway.example.com",
    options: TracewayOptions(
        serviceName: "shop-app",
        collection: ["signals": ["console": ["mode": "stream"], "network": ["mode": "stream"]]],
        telemetry: TracewayTelemetry(
            url: "https://collector.example.com/otlp",
            headers: ["x-ingest-key": "app-ingest-key"]
        )
    )
)
```

A shared `url` gets `/v1/logs`, `/v1/traces` and `/v1/metrics` appended. Each signal (`logs`, `traces`, `metrics`) can override it with a `TracewayTelemetryEndpoint(url:headers:)` whose URL is used as given; without a shared `url`, the signals you do not list keep their Traceway destination. URLs must use HTTP(S), without embedded credentials, a query or a fragment. Signal headers override the shared `headers` key by key; Traceway's token is never sent to the receiver.

When logs are redirected, exceptions, messages and the SDK's session and control records (`session.start`, `session.end`, `traceway.session.update`, fired triggers, started captures, applied config) still go to Traceway, and only there. Ordinary logs (`Traceway.log`, navigation, taps, `recordAction`, `track`) go to the logs receiver; request spans and metrics use their own destinations. Remote config and replays keep using the connection string. Both destinations carry `session.id` for correlation. Batches that failed are kept on disk per destination and sent again later.

The receiver must accept OTLP/HTTP with protobuf bodies (`application/x-protobuf`, gzip). Any key built into the app can be read out of it: use an ingestion key that can only write, or a collector that holds the backend credentials.

### Standalone, without a Traceway server

```swift
Traceway.initialize(
    connectionString: nil,
    options: TracewayOptions(
        serviceName: "shop-app",
        collection: ["signals": ["console": ["mode": "stream"], "network": ["mode": "stream"]]],
        telemetry: TracewayTelemetry(url: "https://collector.example.com/otlp")
    )
)
```

No Traceway server, account or token is required. `telemetry` must have a shared `url` or all three signal endpoints. Standalone mode turns off remote config, replay uploads and session records, whatever the options say. Exceptions are ordinary OTLP log records with the event name `exception` (messages carry `traceway.message`), sent to your collector, and the built-in exception trigger still uploads the buffered breadcrumbs.

## Options

`TracewayOptions` accepts the following parameters. The `capture*` options, `screenCapture`, `replayImages` and `sessions` are ceilings: remote settings can lower what is collected but never raise it.

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `sampleRate` | `Double` | `1.0` | Share of exceptions and messages that are reported (0.0 to 1.0) |
| `debug` | `Bool` | `false` | Log SDK activity with `NSLog` |
| `version` | `String` | bundle version | App version, sent as `service.version` |
| `serviceName` | `String?` | bundle identifier | Sent as `service.name` |
| `environment` | `String?` | none | Sent as `deployment.environment.name` |
| `attributes` | `[String: String]` | `[:]` | Attributes attached to every record, also used for remote-config targeting |
| `screenCapture` | `Bool` | `false` | Record a [wireframe session replay](#session-replay): the last seconds go up with an exception, and captures can stream it |
| `replayImages` | `TracewayImagePolicy` | `.always` | Most the replay records of image views: `.off`, `.wifi` (unmetered networks only) or `.always`; the `replay.images` setting (`wifi` by default) can lower it (see [Images](#images)) |
| `fps` | `Int` | `4` | Most wireframe frames captured per second (1 to 15); a frame is kept only when the screen changed |
| `maxBufferFrames` | `Int` | `150` | Frames in the replay ring; the upper bound of every clip |
| `persistToDisk` | `Bool` | `true` | Keep SDK state (instance id, last remote config, session, ring buffer) and undelivered telemetry on disk; record hard crashes |
| `captureLogs` | `Bool` | `true` | Record `Traceway.log` lines |
| `captureNetwork` | `Bool` | `true` | Record every URLSession request as a client span |
| `captureNavigation` | `Bool` | `true` | Record screens (view controllers, `.tracewayScreen`, `Traceway.recordNavigation`) |
| `captureUserActions` | `Bool` | `true` | Record taps with the selector of the view, and feed them to recording triggers |
| `captureMetrics` | `Bool` | `true` | Measure and upload the [app performance metrics](#app-performance-metrics). A ceiling for metrics |
| `metricDimensions` | `[String: String]` | `[:]` | Up to two app-defined dimensions on every metric, sent as `custom.<key>` |
| `recordAllSessions` | `Bool` | `false` | Stream breadcrumbs and the replay all the time instead of keeping them for errors |
| `collection` | `[String: Any]?` | none | Local collection settings, the same document as a remote-config rule (see [Local config](#local-config)) |
| `sessions` | `Bool` | `true` | Send session records (`session.start` / `session.end`); the session ID exists either way |
| `baselineSampleRate` | `Double` | `0` | Share of sessions whose breadcrumbs are sent continuously, not only around errors |
| `remoteConfig` | `Bool` | `true` | Poll the server for collection settings over OpAMP |
| `exportDelayMs` | `Int` | `1000` | How long finished records wait to be sent as one batch |
| `telemetry` | `TracewayTelemetry?` | none | Send logs, spans and metrics to another OTLP/HTTP receiver (see [Setups](#setups)) |
| `propagateTraceHeaderUrls` | `[String]` | `[]` | URL prefixes whose requests carry a W3C `traceparent` header (see [Connect requests to backend traces](#connect-requests-to-backend-traces)) |
| `ignoreErrors` | `[TracewayErrorPattern]?` | `nil` (`TracewayOptions.defaultIgnoreErrors`) | String literals (substrings) and `.regex(_:)` patterns matched against the first line `Type: message`; a list replaces the defaults (see [Errors and messages](#errors-and-messages)) |
| `beforeCapture` | `((TracewayCapturedError) throws -> Bool)?` | `nil` | Return `false` to drop an exception or message; one that throws keeps it |
| `reportHangsInDebug` | `Bool` | `false` | Report hangs (`app.hang`) while a debugger is attached too |

## Crashes and symbolication

After `Traceway.initialize(...)` the SDK records:

- **Uncaught `NSException`s**, the Objective-C and UIKit exceptions that escape to the top of the stack: written to disk on the crashing thread and sent for up to two seconds before the app ends.
- **Fatal signals**: Swift runtime traps such as force-unwrapping `nil`, an out-of-bounds index, `fatalError()` and integer overflow, and bad memory access (`SIGTRAP`, `SIGILL`, `SIGABRT`, `SIGSEGV`, `SIGBUS`, `SIGFPE`). An async-signal-safe handler writes them to disk, and they are reported on the **next launch**, with the session they happened in.

A release build ships stripped, so crash traces arrive as bare image offsets with no function names or line numbers: they carry the binary images' UUIDs and offsets. Upload the build's `.dSYM` and Traceway symbolicates those traces on the server, turning each frame into `function (file:line:col)`, for errors and crashes alike.

The SDK ships an uploader script. Add an Xcode **Run Script** build phase that invokes it:

```sh
"$SRCROOT/path/to/Scripts/upload_symbols.sh"
```

The script no-ops on non-Release builds and when the token is unset, so it is safe to leave in place. Set two environment variables for the phase:

- `TRACEWAY_UPLOAD_TOKEN`: your project's **upload token** from the dashboard, the same one used for JavaScript source maps. It is **not** the runtime token in your connection string.
- `TRACEWAY_URL`: your Traceway base URL (or `/api/report` URL); the script derives the upload URL from it.

See [iOS symbolication](/symbolicator/ios) for the full reference: the script flags, the raw HTTP upload contract for CI without Xcode, and how a non-symbolicated frame resolves into source. Symbolication happens on Traceway, so exceptions sent only to another backend in [standalone mode](#standalone-without-a-traceway-server) keep their raw traces.

## What gets captured automatically

After `Traceway.initialize(...)`, with no further code:

- **Crashes**: uncaught `NSException`s and fatal signals (see [Crashes and symbolication](#crashes-and-symbolication)).
- **Sessions**: a new one after 15 minutes without activity, and at the latest after an hour.
- **Screens**: view controllers that appear; SwiftUI screens through `.tracewayScreen`.
- **Taps**: every tap, with the selector, class, identifier, shown text and label of the view, and the screen (`browser.user_action.click`, with the OpenTelemetry `app.widget.*` and `app.screen.*` attributes).
- **Network**: every URLSession request.
- **App performance metrics**.

Breadcrumbs (logs, screens, taps, requests, actions) wait in the ring buffer and show on the session timeline next to the exception that flushed them. `Traceway.log` lines are recorded only when the app calls it.

### Disabling channels

Each channel can be turned off in `TracewayOptions`. No remote setting can turn it back on:

```swift
TracewayOptions(
    captureLogs: false,         // Traceway.log
    captureNetwork: false,      // URLSession requests
    captureNavigation: false,   // screens
    captureUserActions: false,  // taps
    captureMetrics: false       // app performance metrics
)
```

## Platform support

| Platform | Error Tracking | Session Replay | Metrics |
|----------|---------------|----------------|---------|
| iOS 13+ (iPhone, iPad) | Yes | Wireframe (UIKit and SwiftUI) | Yes |

The package is built with Swift 6.3 (Xcode 26.4 or later). For Flutter apps, use the [Flutter SDK](/client/flutter) instead.

### Platform differences

The API has the names of the [browser](/client/js-sdk), [Flutter](/client/flutter) and [Android](/client/android) SDKs. Where iOS differs, it is for these reasons:

- **Start**: `Traceway.initialize(connectionString:options:)` instead of `init`, because Swift reserves `Traceway.init(…)` for initializers: a static method cannot be called that way. It returns `nil` when the settings are invalid (logged, not thrown). `Traceway.start`, the name in 0.1.x and in earlier 2.0 beta builds, is a deprecated alias. Flutter starts with `Traceway.run`, Android with `Traceway.init`.
- **Masks** belong to views: `UIView.tracewayMask` in UIKit and the `.tracewayMask(_:)` modifier in SwiftUI. The marker that needs no code is a UIKit view's `accessibilityIdentifier` (`"traceway-mask"`, `"traceway-blank"`), where the browser uses CSS classes, Flutter a `ValueKey` and Android `android:tag` / `testTag`. The mask colors are `UIColor`s.
- **Seconds**: `flush(timeout:)` takes seconds, the Swift idiom (`nil` waits until done); the browser, Flutter and Android take milliseconds.
- **Properties**: `Traceway.instanceId` and `Traceway.currentSessionId` are properties (`getInstanceId()` and a `currentSessionId()` function in the browser; `getInstanceId()` on Flutter and Android).
- **Argument labels**: `recordNavigation(_:action:from:route:)`, `log(_:level:attributes:)`, `captureException(_:attributes:)` and `metric(_:value:dimensions:)` take Swift labels, with defaults for the optional ones.
- **Navigation**: view controllers that appear are reported without code; SwiftUI screens call `.tracewayScreen(_:)`, and other routers `recordNavigation`.
- **Selectors name views**: classes, `accessibilityIdentifier`s, `tag`s, accessibility labels and traits (see [Naming views](#naming-views)). SwiftUI controls have no views of their own, so a selector cannot name one, and iOS has no hover.

## Migrating from 1.x

- **Server**: 2.0 sends OTLP to `/api/otel/v1/logs`, `/api/otel/v1/traces` and `/api/otel/v1/metrics`, polls `/api/otel/v1/opamp` and uploads replays to `/api/recordings`. There is no fallback to the 1.x `/api/report` protocol.
- **Requirements**: Xcode 26.4 (Swift 6.3) or later, for the OpenTelemetry Swift packages.
- **Connection string**: unchanged. `token@https://host/api/report` still works; the bare server URL works too. It is now optional: without it the SDK runs [standalone](#standalone-without-a-traceway-server).
- **Unsent reports**: 1.x reports younger than 12 hours, and crashes 1.x recorded, are sent once over OTLP on the first 2.0 start.
- **Behaviour**: exceptions are OpenTelemetry `exception` log events (`exception.type`, `exception.message`, `exception.stacktrace`), so issues regroup once after the upgrade. Breadcrumbs and session replay are new.
- **Removed options**: `debounceMs`, `retryDelayMs`, `maxPendingExceptions`, `maxLocalFiles` and `localFileMaxAgeHours`.
- **Renamed API**: `capture(_:)` and `capture(error:)` are `captureException(_:attributes:)`, and `capture(message:)` is `captureMessage(_:attributes:)`. In the 2.0 beta, `log(_:severity:)` became `log(_:level:attributes:)` with `TracewayLogLevel` (was `TracewayLogSeverity`), and `sessionId` became `currentSessionId`; `Traceway.start` became `Traceway.initialize(connectionString:options:)` (Swift reserves `Traceway.init`), and `tracewayPrivacyMask` became `tracewayMask`. The old names still work and are deprecated. `flush(timeout:)` is unchanged.
- **New API**: `log`, `track`, `recordAction`, `recordNavigation`, `setRoute`, `startInteraction`, `setAttribute(s)`, `removeAttribute`, `clearAttributes`, `reportFullyDisplayed`, `metric`, `count`, `setMetricDimension`, `shutdown`, `refreshConfig`, `instanceId`, `currentSessionId`, `tracer`, `tracewayMask` and `.tracewayScreen`, and the options `serviceName`, `environment`, `attributes`, `screenCapture`, `replayImages`, `fps`, `maxBufferFrames`, `capture*`, `metricDimensions`, `recordAllSessions`, `baselineSampleRate`, `sessions`, `remoteConfig`, `collection`, `exportDelayMs`, `propagateTraceHeaderUrls`, `telemetry`, `ignoreErrors`, `beforeCapture` and `reportHangsInDebug`.

## Testing

Start with a caught error. It uploads immediately and works with the Xcode debugger attached:

```swift
import SwiftUI
import Traceway

struct TestError: Error {}

struct TracewayTestView: View {
    var body: some View {
        Button("Send Test Error") {
            Traceway.captureException(TestError())
            Traceway.flush(timeout: 5)
        }
    }
}
```

Tap it and check your Traceway dashboard: the error appears on the Issues page within a few seconds, with its breadcrumbs and, with `screenCapture: true`, the replay.

To verify **hard-crash** capture as well, add a second button:

```swift
Button("Force Crash") {
    fatalError("Test crash from Traceway integration")
}
```

This one does nothing while you run from Xcode: when the debugger is attached, lldb catches the signal first, so the SDK's handler never runs. Test it **without** the debugger: install once from Xcode, stop the debugger, launch the app from the home screen, tap the button, then relaunch and watch the report upload on the next launch.
