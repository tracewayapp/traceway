# Exceptions

Capture JavaScript errors and exceptions with full stack traces.

## captureException

Capture an error with its stack trace:

```javascript
import { captureException } from "@tracewayapp/frontend";

try {
  riskyOperation();
} catch (error) {
  captureException(error);
}
```

The SDK extracts the error type, message, and stack trace automatically. A call made before `init()` does nothing, and a value the SDK cannot read never throws into your code.

## captureExceptionWithAttributes

Capture an error with additional metadata:

```javascript
import { captureExceptionWithAttributes } from "@tracewayapp/frontend";

try {
  processOrder(orderId);
} catch (error) {
  captureExceptionWithAttributes(error, {
    orderId: String(orderId),
    userId: String(currentUser.id),
    action: "checkout",
  });
}
```

Attributes appear as tags in the Traceway dashboard, making it easier to filter and debug issues. Attribute values are strings, so convert numbers and booleans as above.

## Screen Context

Every exception also says where the page was when it happened, with the keys the Android and iOS SDKs use:

| Attribute                | Value                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `app.screen.name`        | The screen's route template (`setRoute`, the app's router, or `recordNavigation`'s `route`), else its path (`/orders/42`) |
| `app.screen.route`       | The route template, when one is known                                                                                     |
| `app.screen.previous`    | The name of the screen before                                                                                             |
| `app.screen.duration_ms` | How long the screen had been shown                                                                                        |
| `viewport`               | The window's size in CSS pixels, `1280x720`                                                                               |

Attributes you pass yourself win over these. Name your routes so that two orders are one screen, `/orders/:id`, and not two paths; see [Screens and navigation](/client/js-sdk#screens-and-navigation).

In the 2.x SDK, `captureException(error, attributes)` takes the same second argument, and the two functions are identical. In 1.x only `captureExceptionWithAttributes` takes attributes; the `{ distributedTraceId }` option both functions had in 1.x no longer exists in 2.x (see [Distributed Tracing](/client/js-sdk/distributed-tracing)).

## Attribute Best Practices

**Do include:**

- User identifiers (anonymized if needed)
- Request/transaction IDs
- Feature flags or A/B test variants
- Relevant business context (order ID, product ID, etc.)

**Avoid including:**

- Sensitive data (passwords, tokens, PII)
- Large objects or arrays
- Circular references

## Error Types

The SDK handles various JavaScript error types:

```javascript
// Standard Error
captureException(new Error("Something went wrong"));

// TypeError
captureException(new TypeError("Cannot read property 'x' of undefined"));

// Custom errors
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}
captureException(new ValidationError("Invalid email format"));
```

With the 2.x SDK, the type shown in Traceway is the error's `name` property, so set `this.name` as above: it is a string, and minifiers leave it alone. The 1.x SDK reads the **class name** instead, not `this.name`. Minifiers rename classes, so with 1.x a production build shows the issue above as `r: Invalid email format` rather than `ValidationError: Invalid email format`. Either way, put anything you need to search or group on into the message or into attributes.

## Non-Error Values

Pass real `Error` objects. Anything else arrives with no useful stack trace. The 2.x SDK wraps a string as `new Error(string)` and any other value as `new Error(JSON.stringify(value))`, so the issue type is `Error`. The 1.x SDK reads only the value's class name and its `message` property, so it loses more:

```javascript
// 2.x: "Error: Something went wrong". 1.x: the message is lost, stored as "String: undefined".
captureException("Something went wrong");

// 2.x: "Error: {"code":500,"message":"Server error"}". 1.x: "Object: Server error", the `code` field is dropped.
captureException({ code: 500, message: "Server error" });
```

Wrap the value in an `Error` instead, and pass the extra fields as attributes:

```javascript
import { captureExceptionWithAttributes } from "@tracewayapp/frontend";

captureExceptionWithAttributes(new Error("Server error"), { code: "500" });
```

## Filters and Limits

Manual captures pass through the same filters as automatic ones: an error matching [`ignoreErrors`](/client/js-sdk/initialization#error-filtering) is dropped, and [`beforeCapture`](/client/js-sdk/initialization#beforecapture-callback) can drop it. Its argument carries the value you passed as `error`, so `beforeCapture: (captured) => !(captured.error instanceof ValidationError)` drops one class of errors. The default patterns ignore network failures, timeouts and 4xx responses, so `captureException(new Error("Request timeout"))` is not reported unless you change `ignoreErrors`.

The 2.x SDK also protects against error storms. The same error (type, message and stack) captured again within one second is suppressed, and a running client reports at most 60 errors in a rolling minute. The next reported error carries the number suppressed as `traceway.error.suppressed_count`. Tune both with the [`errorLimits`](/client/js-sdk/initialization#production-collection-policy) option.

## Errors Inside an Interaction

`startInteraction(name, attributes?)` returns a `TracewayInteraction` whose `captureException(error, attributes?)` captures the error as part of that interaction's trace and marks the interaction as failed. See [Distributed Tracing](/client/js-sdk/distributed-tracing#trace-an-entire-interaction-explicitly).

## React Error Boundaries

For React applications, use the `@tracewayapp/react` package. Its `<TracewayProvider>` itself acts as an error boundary: render-time exceptions are captured automatically and re-thrown so the app behaves exactly as without Traceway. See the [React documentation](/client/react) for setup, or the [Error Boundary page](/client/react/error-boundary) if you need a custom fallback UI for a specific subtree.
