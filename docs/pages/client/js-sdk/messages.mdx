# Messages

Send custom log messages to Traceway for tracking non-error events.

## captureMessage

Send a simple text message:

```javascript
import { captureMessage } from "@tracewayapp/frontend";

// Track important events
captureMessage("User completed onboarding");

// Track business metrics
captureMessage("Payment processed successfully");

// Track navigation
captureMessage("User visited pricing page");
```

Every message becomes an issue, and messages are grouped by their exact text: two messages that differ in one character are two issues. Keep the text constant and put the variable parts in attributes.

## Attributes

In the 2.x SDK `captureMessage` takes an optional second argument with string attributes, shown on the issue like the attributes of an exception:

```javascript
captureMessage("Payment processed successfully", {
  provider: "stripe",
  amount: String(order.total),
});
```

The 1.x SDK takes the message only. Global attributes set with `setAttribute` are attached in both versions.

## Use Cases

### User Actions

```javascript
function handlePurchase(product) {
  captureMessage(`Purchase: ${product.name}`);
  // ... process purchase
}
```

### Feature Usage

```javascript
function enableBetaFeature(featureName) {
  captureMessage(`Beta feature enabled: ${featureName}`);
  // ... enable feature
}
```

### Debugging Production Issues

```javascript
function processData(data) {
  if (data.items.length > 1000) {
    // The count goes in an attribute (2.x), so every occurrence stays one issue
    captureMessage("Large dataset processed", {
      items: String(data.items.length),
    });
  }
  // ... process data
}
```

## Messages vs Exceptions

| Use `captureMessage` when | Use `captureException` when |
|---------------------------|----------------------------|
| Tracking user actions | An error occurred |
| Logging business events | Catching exceptions |
| Debugging production flows | Something unexpected happened |
| Monitoring feature usage | Operation failed |

## Best Practices

1. **Be concise**: Messages should be short and descriptive
2. **Include context**: Add relevant identifiers when helpful
3. **Avoid sensitive data**: Never include passwords, tokens, or PII
4. **Use sparingly**: Messages add overhead; don't log every action
5. **Mind the error filters**: `ignoreErrors` patterns and `beforeCapture` apply to messages too, so with the default patterns a text containing "timeout" or "Failed to fetch" is dropped. See [Error Filtering](/client/js-sdk/initialization#error-filtering)

Messages are sent right away and each one is an issue occurrence. For an event that should only appear as a breadcrumb on the session timeline, use `recordAction(category, name, data)`; the 2.x SDK also has `track(name, attributes)` for named events a trigger can match. In 2.x both are buffered on the device by default.

## Viewing Messages

Messages appear in the Traceway dashboard alongside exceptions. You can filter by message type to see only messages or only exceptions.
