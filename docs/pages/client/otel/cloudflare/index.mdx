# Cloudflare Workers

Cloudflare Workers has built-in observability that exports **traces and logs** over OTLP. No SDK and no code changes are needed in your Worker. You create a destination in the Cloudflare dashboard, point it at Traceway, and enable it in your `wrangler.jsonc`.

Create the Traceway project with framework **OpenTelemetry**, then copy its project token from the **Connection** page. You need that token twice below.

**Metrics are not part of this path.** Cloudflare states that exporting Worker infrastructure metrics and custom metrics over OpenTelemetry is not available yet, and the destination form only offers Traces and Logs. Metric dashboards stay empty for a Workers-only project. To get metrics into the same project, run the [Traceway OTel Agent](/learn/otel-agent) on a host you control, or send them from a backend service you instrument yourself.

## Traces

### Step 1: Create a traces destination in the Cloudflare dashboard

In the Cloudflare dashboard, open **Observability → Destinations** and select **Add destination**.

![Cloudflare Observability Destinations](/cloudflare-destinations.png)

Fill in the following fields:

- **Destination Type**: Traces
- **OTLP Traces Endpoint**: `https://cloud.tracewayapp.com/api/otel/v1/traces` (or your self-hosted equivalent)
- **Destination Name**: `traceway-traces`
- **Custom Headers**: `Authorization` = `Bearer <project_token>`

Replace `<project_token>` with your project token from the project's **Connection** page in the Traceway dashboard. The header value is the word `Bearer`, a space, then the token.

![Add Destination form](/cloudflare-add-destination.png)

The destination name is yours to choose (the screenshot above uses `traceway`). Whatever you pick has to match the `wrangler.jsonc` value in the next step exactly.

### Step 2: Enable traces in wrangler.jsonc

Add the `observability.traces` configuration to your `wrangler.jsonc`, referencing the destination name you created above:

```jsonc
{
  "observability": {
    "traces": {
      "enabled": true,
      "destinations": ["traceway-traces"],
      "head_sampling_rate": 1,
      "persist": false
    }
  }
}
```

- `head_sampling_rate` is a number between `0` and `1` and controls what fraction of requests are traced. `1` traces every request. Lower this value to sample fewer invocations.
- `persist` defaults to `true`, which keeps a copy in the Cloudflare dashboard on top of exporting it. Set it to `false` when Traceway is your only destination. Keep it `true` if you still want to query the data in Cloudflare.

### Endpoint names and route templates

Cloudflare's automatic tracing puts `url.path`, `url.full` and `http.request.method` on the invocation span. By default the invocation span lacks the route template from your application’s router. Traceway uses `http.route` when it is there and falls back to `url.path`, so you get one endpoint row per distinct URL:

```
GET /orders/8f21c0
GET /orders/a934bb
GET /orders/c710de
```

instead of a single `GET /orders/:id`. For a Worker serving a handful of fixed paths that is fine. For a Worker with dynamic path segments, a Hono or itty-router app for example, the Endpoints page fills with one-hit rows, per-endpoint P50 and P95 stop meaning anything, and endpoint-scoped notification rules never match.

Once your router matches a route, set its template on the invocation span before starting any child spans. At that point `tracing.getActiveSpan()` gives you the invocation span. [Workers custom spans](https://developers.cloudflare.com/workers/observability/traces/custom-spans/)

```ts
import { tracing } from "cloudflare:workers";

export default {
  async fetch(request: Request): Promise<Response> {
    const match = /^\/orders\/([^/]+)$/.exec(new URL(request.url).pathname);
    if (!match) return new Response("Not found", { status: 404 });
    tracing.getActiveSpan()?.setAttribute("http.route", "/orders/:id");
    return Response.json({ id: match[1] });
  },
};
```

Traceway groups GET requests matching this route under `GET /orders/:id`.

## Logs

Logs work like traces. Create a second destination in the dashboard, add a second block to `wrangler.jsonc`, and redeploy. No Worker code changes.

### Step 1: Create a logs destination in the Cloudflare dashboard

Back on the **Destinations** tab, click **+ Add Destination** a second time and fill in:

- **Destination Type**: Logs
- **OTLP Logs Endpoint**: `https://cloud.tracewayapp.com/api/otel/v1/logs` (or your self-hosted equivalent)
- **Destination Name**: `traceway-logs`
- **Custom Headers**: `Authorization` = `Bearer <project_token>`

Use the same project token as the traces destination.

### Step 2: Enable logs in wrangler.jsonc

Add the `observability.logs` block alongside `observability.traces`:

```jsonc
{
  "observability": {
    "traces": {
      "enabled": true,
      "destinations": ["traceway-traces"],
      "head_sampling_rate": 1,
      "persist": false
    },
    "logs": {
      "enabled": true,
      "destinations": ["traceway-logs"],
      "head_sampling_rate": 1,
      "persist": false
    }
  }
}
```

`head_sampling_rate` and `persist` mean the same thing in both blocks. `persist` is easy to miss on the traces block: leave it out there and you keep paying for Cloudflare-side trace storage you did not ask for.

When both traces and logs are enabled, each log carries the `trace_id` and `span_id` of the request that produced it, so Traceway shows those logs on the matching trace detail page automatically. Anything you `console.log` in your Worker lands in **Logs**, with the Worker's name as the service.

See [OTel Logs](/client/otel/logs) for the full OTLP logs mapping and severity reference.

## Errors: an uncaught exception does not become an Issue on its own

When your Worker throws, Cloudflare returns an error response and records the failure. It does not attach an OTel exception to the span. The invocation span arrives with `cloudflare.outcome` set to `exception`, so you see the failed request on the Endpoints page, and the error text arrives in **Logs**. Nothing reaches **Issues**, so there is no grouped issue and no stack trace.

To get an Issue with a stack trace, catch the error yourself and put the three OTel exception attributes on a span. Traceway turns any span carrying `exception.type`, `exception.message` or `exception.stacktrace` into an issue, grouped by the normalized stack trace:

```ts
import { tracing } from "cloudflare:workers";

async function handle(request: Request): Promise<Response> {
  if (new URL(request.url).pathname === "/boom") {
    throw new Error("payment gateway timeout");
  }
  return new Response("ok");
}

export default {
  async fetch(request: Request): Promise<Response> {
    try {
      return await handle(request);
    } catch (err) {
      const e = err instanceof Error ? err : new Error(String(err));
      tracing.enterSpan("uncaught error", (span) => {
        span.setAttribute("exception.type", e.name);
        span.setAttribute("exception.message", e.message);
        span.setAttribute("exception.stacktrace", e.stack ?? "");
      });
      return new Response("Internal Server Error", { status: 500 });
    }
  },
};
```

Deploy that and request `/boom`. You get an HTTP 500, an endpoint row with status 500, and an Issue titled `Error: payment gateway timeout` with the frames from `e.stack`.

The frames point into your bundled Worker, not your sources. Cloudflare sets `telemetry.sdk.language` to `javascript`, so Traceway runs these traces through JavaScript symbolication once you upload your Worker's source maps. See [JavaScript symbolication](/symbolicator/javascript).

## Cron, queue, and email handlers

Cloudflare also traces scheduled, queue and email handlers. Look for their invocation spans in **Spans**. A CONSUMER span additionally appears in **Tasks**, and an exception event can create an Issue on any span.

If you need reliable task rows for background work, do the work in a service you instrument with an OTel SDK, where you can set the span kind to `CONSUMER` yourself.

## What Traceway shows

Cloudflare stamps its own attributes on the spans it exports and Traceway maps them for you. Nothing to configure:

| Cloudflare attribute | Traceway field |
|---|---|
| `service.name` (your Worker's name) | **Server Name** on endpoints, tasks and issues |
| `cloudflare.script_version.id` | **App Version**, using the part after the last `-`, so you can filter issues to a single deployment |
| `telemetry.sdk.language` = `javascript` | turns on JavaScript source-map symbolication for stack traces |

Cloudflare's [known limitations](https://developers.cloudflare.com/workers/observability/traces/known-limitations/) note that `service.name` is not on every span yet, so a span here and there can arrive with no server name. Cloudflare also warns that span and attribute names are not final during the beta, so re-check this table when the beta ends.

Cloudflare also puts `cloudflare.colo`, `cloudflare.ray_id`, `cloudflare.outcome`, `cloudflare.cpu_time_ms`, `cloudflare.wall_time_ms` and `faas.trigger` on the invocation span. Those arrive as attributes on the endpoint and are visible on the trace detail page. `cloudflare.ray_id` is the useful one: it lets you go from a Cloudflare support ticket straight to the matching Traceway trace.

## Deploy

Observability config only takes effect on a new deployment, so deploy your Worker:

```bash
npx wrangler deploy
```

## Verify

Send a few requests to your Worker, wait about a minute, then open Traceway:

1. **Endpoints**: look for the route template you set, or the raw path when no template was supplied.
2. **Logs**: filter by your Worker's name in the Service field. Anything you `console.log` shows up here.
3. Open an endpoint, then a single trace. The log lines from that request are attached to it, because Cloudflare stamps the trace and span ids onto the exported log records.

Nothing showing up? Work through these in order:

- **Did you redeploy?** The observability config only applies to a new deployment.
- **Do the names match?** The strings in `destinations` must be identical to the destination names in the dashboard.
- **Is the header right?** The custom header value is `Bearer <project_token>`: the word `Bearer`, a space, then the token. A wrong token is rejected at the Traceway end. Cloudflare does show it: on the **Destinations** tab the destination's status reads **Error** instead of **Last: n minutes ago**.
