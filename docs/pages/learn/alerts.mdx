# Alerts

import { Callout } from "nextra/components";

Alerts tell you when something in your application needs attention: a new error, a latency spike, a metric over its limit, a service that stopped reporting. You choose where the notification goes (email, Slack, a webhook, a GitHub issue, Pushover, Telegram, or a page to whoever is [on call](/learn/on-call)) and which condition sends it.

Setting it up takes two steps in the dashboard. First you create a **channel**, which is where notifications are delivered. Then you create a **rule**, which is the condition that sends one. Each rule sends to exactly one channel, and one channel can serve many rules.

Channels and rules belong to a project. To create or change them you need write access to that project, which is every role except `readonly`.

## Step 1: Create a channel

A rule has nowhere to send its notification until a channel exists, so the channel comes first.

1. Open the project and click **Alerts** in the sidebar. The page opens on the **Channels** tab.
2. Click **New Channel**.
3. Enter a **Name** and pick the **Type**. The fields below change with the type. Email only needs **Recipients**, up to 10 addresses. What the other types need is listed under [Channels](#channels).
4. Click **New Channel**.

<img src="/alerts/new-channel-email.png" alt="The Alerts page of the checkout-api project with the New Channel dialog open: Name is Operations email, Type is Email, and Recipients holds ops@acme.dev with an Add Recipient button below it" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

The channel is now in the list. The three icons at the end of its row are **Test**, **Edit** and **Delete**. Deleting a channel also deletes every rule attached to it.

<img src="/alerts/channels-list.png" alt="The Channels tab listing two channels, #checkout-alerts of type Slack and Operations email of type Email, both enabled, each with Test, Edit and Delete icons" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

## Step 2: Create a rule

A rule watches one condition in this project and notifies its channel when the condition is met.

1. Switch to the **Rules** tab and click **New Rule**.
2. Enter a **Name**. It is included in every notification, so say what is wrong: "Checkout p95 above 1 second".
3. Pick the **Channel** you created in step 1.
4. Pick the **Rule Type**. The dialog describes the selected type and shows its settings under **Rule Configuration**. **New Issue** is a good first rule: it needs no settings and tells you about every error you have not seen before. All types are described under [Rule types](#rule-types).
5. Check the numbers under **Rule Configuration**. The form opens with general starting values, so set the threshold and the lookback you want.
6. Leave **Cooldown (minutes)** at 15 and **Severity** at **Auto (default)** for now. [Cooldown and snooze](#cooldown-and-snooze) and [Severity](#severity) explain both.
7. Click **New Rule**.

<img src="/alerts/new-rule.png" alt="The New Rule dialog: Name is Checkout p95 above 1 second, Channel is Operations email, Rule Type is Endpoint P95, and under Rule Configuration the Endpoint is POST /api/checkout, Threshold (ms) is 1000 and Lookback (minutes) is 10. Cooldown is 15 minutes and Severity is Auto (default)" style={{ maxWidth: '420px', width: '100%', height: 'auto', marginTop: '16px' }} />

The rule is on as soon as you save it. The icons at the end of its row are **Snooze**, **Disable**, **Edit** and **Delete**.

## Check that it works

Send a test through the channel so you know the destination is right before a real alert depends on it.

1. On the **Channels** tab, click the **Test** icon (the paper plane) on the channel's row.
2. Click **Send Test**.

<img src="/alerts/test-channel.png" alt="The Test Channel dialog asking whether to send a test notification to Operations email, with Cancel and Send Test buttons" style={{ maxWidth: '480px', width: '100%', height: 'auto', marginTop: '16px' }} />

A message titled "Traceway Test Notification" arrives at the destination. In an email the subject line is "[INFO] Traceway Test Notification". If the destination refuses it, the dialog stays open and shows the reason, for example `Test notification failed: Slack returned status 404`.

<Callout type="warning">
  Testing an **Escalation policy** channel is not a dry run. It opens a real [page](/learn/on-call) and notifies whoever is on call. Resolve the test page on the On-Call page when you are done.

A test proves the channel, not the rule, and it is not recorded. Once a rule fires for real, the notification is listed on the **History** tab with its delivery status:

## Channels

Traceway supports the following channel types:

| Type | What it does | What it needs |
|------|--------------|---------------|
| Email | Sends an email to one or more recipients | 1 to 10 email addresses |
| Slack | Posts a message to a Slack channel through an incoming webhook | Webhook URL |
| Webhook | Sends an HTTP request with a JSON payload to any URL | URL, optional headers, optional HMAC secret |
| GitHub | Creates a GitHub issue in a repository | Personal access token, repository owner and name, optional labels |
| Pushover | Sends a push notification to your mobile devices | User Key, App Token |
| Telegram | Sends a message through a Telegram bot to a user or group chat | Bot Token, Chat ID |
| Escalation policy | Opens an on-call [page](/learn/on-call) and runs the policy's escalation chain until somebody acknowledges, instead of sending a message | An escalation policy |

### Setting up email

Add one or more recipient addresses. Traceway sends the email to every listed recipient when a rule fires.

On a self-hosted instance the server has to be able to send mail: set `SMTP_ENABLED=true` together with the other `SMTP_` settings. Without them the email is written to the server log and never delivered.

### Setting up Slack

To send alerts to a Slack channel, you need an **Incoming Webhook URL**:

1. Go to [api.slack.com/apps](https://api.slack.com/apps) and click **Create New App**
2. Choose **From scratch**, give it a name (e.g. "Traceway Alerts"), and select your workspace
3. In the app settings, navigate to **Incoming Webhooks** and toggle it **on**
4. Click **Add New Webhook to Workspace**, select the channel you want alerts posted to, and click **Allow**
5. Copy the **Webhook URL**. It will look like `https://hooks.slack.com/services/T.../B.../xxx`

Then create the channel in Traceway with **Type** set to **Slack**:

| Field | Required | Description |
|-------|----------|-------------|
| Webhook URL | Yes | The URL you copied from Slack |
| Channel Override | No | Post to a different channel than the webhook default (e.g. `#incidents`) |
| Username | No | Override the bot display name (defaults to your Slack app name) |

<img src="/channel-slack.png" alt="Slack channel configuration dialog" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

### Setting up GitHub

To create GitHub issues from alerts, you need a **Personal Access Token** with issue permissions:

1. Go to [GitHub Settings → Developer settings → Personal access tokens → Fine-grained tokens](https://github.com/settings/tokens?type=beta)
2. Click **Generate new token**
3. Under **Resource owner**, select the account or organization that owns the target repository. If your organization doesn't appear, an org admin needs to enable fine-grained tokens under **Organization Settings → Third-party access → Personal access tokens → Settings**
4. Set a descriptive name (e.g. "Traceway Alerts") and choose an expiration
5. Under **Repository access**, select **Only select repositories** and choose the repo where issues should be created
6. Under **Permissions → Repository permissions**, set **Issues** to **Read and write**
7. Click **Generate token** and copy it; you won't be able to see it again

Then create the channel in Traceway with **Type** set to **GitHub**:

| Field | Required | Description |
|-------|----------|-------------|
| Personal Access Token | Yes | The fine-grained token you generated |
| Repository Owner | Yes | The user or organization that owns the repository, e.g. `my-org` |
| Repository Name | Yes | The repository name, e.g. `backend` |
| Labels | No | Comma-separated labels to apply to created issues, e.g. `bug, traceway` |

<img src="/channel-github.png" alt="GitHub channel configuration dialog" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

Issues opened by this channel can start an AI coding agent in the repository's own GitHub Actions, which investigates the exception with the traceway CLI and opens a pull request or comments its analysis. See [Auto-Fix](/learn/auto-fix).

### Setting up Telegram

To send alerts to Telegram, you need a **Bot Token** and a **Chat ID**:

1. Open Telegram and start a chat with [@BotFather](https://t.me/BotFather). Send `/newbot` and follow the prompts to give your bot a name and username. BotFather will reply with a **Bot Token** in the form `123456789:ABCdefGhIJKlmNoPQRstuVwxyZ`. Copy it.
2. Open a chat with your new bot and send it `/start` so it is allowed to message you.
3. Create a private channel in Telegram for the alerts.
4. Open the channel's settings → **Administrators** → **Add Admin**, search for your bot's username, and add it with permission to post messages.
5. Forward any message from the channel to [@userinfobot](https://t.me/userinfobot); it will reply with the channel's **Chat ID** (a negative number, e.g. `-1001234567890`). Copy it including the minus sign.

Then create the channel in Traceway with **Type** set to **Telegram**:

| Field | Required | Description |
|-------|----------|-------------|
| Bot Token | Yes | The token BotFather gave you |
| Chat ID | Yes | The destination channel ID (e.g. `-1001234567890`) |

### Setting up Pushover

You need the **User Key** of your Pushover account and the **App Token** of a Pushover application you created for Traceway. Then create the channel in Traceway with **Type** set to **Pushover**:

| Field | Required | Description |
|-------|----------|-------------|
| User Key | Yes | Your Pushover user key |
| App Token | Yes | The API token of your Pushover application |
| Device | No | Send to one device only. Empty sends to all of them |
| Priority | No | **Normal**, **High** or **Emergency**. Emergency repeats the notification until it is acknowledged and adds **Retry Interval** (at least 30 seconds), **Expiry** (at most 10800 seconds) and an optional **Callback URL** |
| Sound | No | A Pushover sound name, e.g. `bugle` |
| Enable HTML formatting | No | Lets Pushover render HTML in the message |
| Time to Live | No | Seconds after which the notification disappears from the device. 0 keeps it |

### Webhook payload

A webhook channel takes a **URL**, a **Method** (`POST` or `PUT`), an optional **Secret** and optional **Headers** that are sent with every request.

<img src="/channel-webhook.png" alt="Webhook channel configuration dialog" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

When a rule fires, Traceway sends a JSON request with the following fields:

| Field | Description |
|-------|-------------|
| `subject` | Alert title |
| `body` | Alert details |
| `severity` | `info`, `warning`, or `critical` |
| `ruleType` | The rule type that triggered the alert |
| `ruleName` | The name you gave the rule |
| `url` | Deep link to the relevant dashboard page. Absolute when the server sets `APP_BASE_URL`, otherwise a path such as `/issues/<hash>` relative to your dashboard origin |
| `timestamp` | When the alert fired (ISO 8601) |

If you set a **Secret**, each request includes an `X-Traceway-Signature` header containing `sha256=<hex>`, the HMAC of the request body, which you can use to verify that the request came from Traceway. A response with status 400 or higher counts as a failed delivery.

### Paging with an escalation policy

Pick the type **Escalation policy** and select a policy. A rule that sends to this channel opens an on-call page and escalates it until somebody acknowledges, instead of sending one message. Policies are created on the On-Call page first. See [On-Call](/learn/on-call).

## Rule types

Every rule has a name, one channel, a cooldown, a severity, and the settings of its type. Rules only evaluate the data of their own project. Frontend projects support New Issue, Metric Threshold and Release Regression (the last two over their [client metrics](/learn/client-metrics#alerts-and-slos)) and the two SLO rule types; all other types monitor backend telemetry.

| Rule | Fires When | Evaluation |
|------|-----------|------------|
| [New Issue](#new-issue) | A never-before-seen error appears | On ingest |
| [Error Regression](#error-regression) | A resolved (archived) error reappears | On ingest |
| [Error Rate](#error-rate) | The 5xx rate across all endpoints exceeds a percentage | Polled |
| [Error Count](#error-count) | Total errors in a window reach a count | Polled |
| [Endpoint Error Rate](#endpoint-error-rate) | One endpoint's 5xx rate exceeds a percentage | Polled |
| [Endpoint P95 / P99](#endpoint-p95--p99) | Latency percentile exceeds a millisecond threshold | Polled |
| [Apdex Drop](#apdex-drop) | The Apdex score falls below a threshold | Polled |
| [Throughput Drop](#throughput-drop) | Request volume drops versus the preceding baseline | Polled |
| [Impact Score](#impact-score-critical--high--medium) | An endpoint newly crosses an impact level | Polled |
| [Task Duration](#task-duration) | A background task's P95 duration exceeds a threshold | Polled |
| [Task Failure Rate](#task-failure-rate) | The share of failed task executions exceeds a percentage | Polled |
| [Metric Threshold](#metric-threshold) | An aggregated metric violates a comparison | Polled |
| [Release Regression](/learn/client-metrics#alerts-and-slos) | A metric of the newest release is worse than the earlier release by more than an allowed percentage | Polled |
| [No Data](#no-data) | No telemetry received for a configured duration | Polled |
| [AI Trace Cost](#ai-trace-cost) | A single AI trace exceeds a cost threshold | On ingest |
| [AI Conversation Cost](#ai-conversation-cost) | A conversation's cumulative 24-hour cost exceeds a threshold | On ingest |
| [AI Flagged Content](#ai-flagged-content) | An AI conversation matches a flagged content term | On ingest |
| [Monitor Down](#monitor-down) | A monitor crosses its failure threshold | On state change |
| [SLO Burn Rate](#slo-burn-rate) | An SLO burns its error budget faster than a threshold over both a long and a short window | Polled |
| [SLO Budget Consumed](#slo-budget-consumed) | An SLO has consumed at least a share of its window's error budget | Polled |

The option tables below use the labels of the **New Rule** form. **Default** is the usual starting value for that rule type. The form itself opens with the same starting numbers for every type (a 5 minute lookback, for example), so compare them with this column before you save. When you create a rule with the CLI or the API, set every threshold in its `config` yourself. The server only fills in an omitted window (lookback, silence, baseline), Min Executions and the Impact Score Min Requests. It does not fill in a threshold, and the two SLO rule types are refused without their settings.

### New Issue

Fires the first time an error with a given [fingerprint](/learn/issues#fingerprinting) is seen. Errors are grouped by a normalized stack trace hash, so the same logical error reported many times produces a single alert rather than one per occurrence. If you archive an issue and it occurs again, that first re-occurrence counts as new and fires the rule.

The notification includes the error type, stack trace, app version, server name, the endpoint or task it occurred on, and a deep link to the issue.

| Option | Default | Description |
|--------|---------|-------------|
| Ignore Patterns | empty | Comma-separated, case-insensitive substring matches against the error type, e.g. `*timeout*, *context canceled*`. Matching errors never alert. |

The cooldown applies per error, not per rule: two different new errors arriving a minute apart both alert, but the same error will not alert again until its cooldown expires.

### Error Regression

Fires when an error whose issue was archived (resolved) occurs again. Regressions are detected by the same [grouping](/learn/issues#fingerprinting), so the alert means the same failure is back, not that a similar-looking one appeared. Use this to catch fixes that did not stick. The cooldown applies per error. There is no extra configuration.

### Error Rate

Fires when the percentage of requests returning a 5xx status across all endpoints exceeds the threshold within the lookback window.

| Option | Default | Description |
|--------|---------|-------------|
| Threshold (%) | 5 | Error rate that triggers the alert |
| Lookback (minutes) | 5 | Window the rate is computed over |
| Min Requests | 10 | Minimum requests in the window; below this the rule never fires, which avoids noise from a single failed request in quiet periods |

### Error Count

Fires when the total number of errors recorded in the lookback window reaches the threshold. Captured messages (log-style events without an exception) are not counted.

| Option | Default | Description |
|--------|---------|-------------|
| Threshold Count | 100 | Number of errors that triggers the alert |
| Lookback (minutes) | 60 | Window the count is computed over |

### Endpoint Error Rate

Like Error Rate, but scoped to a single endpoint.

| Option | Default | Description |
|--------|---------|-------------|
| Endpoint | | The endpoint to monitor, e.g. `GET /api/users`. It has to be one exact endpoint: the `*` the form starts with matches nothing for this rule type |
| Threshold (%) | 2 | Error rate that triggers the alert |
| Lookback (minutes) | 10 | Window the rate is computed over |
| Min Requests | 20 | Minimum requests in the window before the rule can fire |

### Endpoint P95 / P99

Fires when the P95 (or P99) response time over the lookback window exceeds the threshold. Two separate rule types so you can alert on each percentile independently.

| Option | Default | Description |
|--------|---------|-------------|
| Endpoint | `*` | A specific endpoint, or the default for all endpoints combined |
| Threshold (ms) | 500 | Latency that triggers the alert |
| Lookback (minutes) | 5 | Window the percentile is computed over |

### Apdex Drop

Fires when the Apdex score over the lookback window falls below the threshold. Traceway computes Apdex with fixed bands: requests up to 750 ms are satisfied, up to 1500 ms are tolerating, and anything slower or returning 5xx is bad. The score is `(satisfied + tolerating / 2) / total`, so 1.0 is perfect and anything below roughly 0.85 means users are noticing.

| Option | Default | Description |
|--------|---------|-------------|
| Apdex Threshold | 0.85 | Score below which the alert fires |
| Lookback (minutes) | 15 | Window the score is computed over |
| Min Requests | 50 | Minimum requests in the window before the rule can fire |

### Throughput Drop

Fires when request volume in the lookback window drops by more than the configured percentage compared to the baseline window that immediately precedes it. The baseline count is normalized to the lookback length, so a 15-minute window is compared against the expected 15-minute share of a 60-minute baseline. If the baseline window has no traffic at all, the rule does not fire.

| Option | Default | Description |
|--------|---------|-------------|
| Drop (%) | 50 | Drop versus the normalized baseline that triggers the alert |
| Lookback (minutes) | 15 | The current window being measured |
| Baseline Window (minutes) | 60 | The preceding window used as the baseline |

### Impact Score (Critical / High / Medium)

Fires when an endpoint's impact score crosses into the configured level. The impact score is a 0 to 1 rating computed over the trailing 24 hours as the worst of five components: Apdex degradation, server error rate, P99 latency, client error rate, and error volume. Medium starts at 0.25, High at 0.50, and Critical at 0.75. Streaming endpoints are excluded.

These rules are transition-based: they fire once when an endpoint newly enters the level, not continuously while it stays there. The endpoint alerts again only if it drops out of the level and later crosses back in. After a server restart the first evaluation establishes a baseline without firing.

The notification names the endpoint, its score, and the dominant reason (for example a P99 of 9.2 s, or a 12% server error rate).

| Option | Default | Description |
|--------|---------|-------------|
| Min Requests | 50 | Endpoints with fewer requests in 24 hours are ignored |

### Task Duration

Fires when the P95 duration of background task executions over the lookback window exceeds the threshold.

| Option | Default | Description |
|--------|---------|-------------|
| Task Name | `*` | A specific task, or the default for all tasks combined |
| Threshold (ms) | 30000 | P95 duration that triggers the alert |
| Lookback (minutes) | 30 | Window the percentile is computed over |

### Task Failure Rate

Fires when the percentage of task executions that recorded an error exceeds the threshold. An execution counts as failed when at least one exception was captured during it, so one execution with three errors counts once.

| Option | Default | Description |
|--------|---------|-------------|
| Task Name | `*` | A specific task, or the default for all tasks combined |
| Threshold (%) | 10 | Failure rate that triggers the alert |
| Lookback (minutes) | 60 | Window the rate is computed over |
| Min Executions | 5 | Minimum executions in the window before the rule can fire |

### Metric Threshold

Fires when an aggregated [metric](/learn/metrics) value violates the configured comparison over the lookback window. Works for both system metrics (`cpu.used_pcnt`, `mem.used`, ...) and custom metrics. If the window contains no data points the rule does not fire; pair it with a No Data rule if you also want to know when the metric stops reporting.

| Option | Default | Description |
|--------|---------|-------------|
| Metric Name | | The metric to monitor |
| Operator | gt | One of `gt`, `gte`, `lt`, `lte`, `eq` |
| Threshold Value | 90 | The value compared against the aggregate |
| Aggregation | avg | One of `avg`, `max`, `min`, `sum`, `count`, `p50`, `p75`, `p90`, `p95`, `p99`, `last` (most recent value). A distribution metric, such as a [client metric](/learn/client-metrics#alerts-and-slos), also takes `good_ratio`, as a percentage |
| Good At Or Under | the metric's own limit | Only with `good_ratio`: the value up to which an observation counts as good, e.g. 2500 for LCP |
| Lookback (minutes) | 5 | Window the aggregate is computed over |
| Minimum Observations | 10 | Distribution metrics only: a series with fewer observations in the window is not judged |
| Tag Filters | | Optional `key=value` pairs, comma-separated. Only points whose tags match every pair count. Up to 20 |
| Group By Tags | | Optional tag keys, comma-separated. Each combination of their values is evaluated as its own series. Up to 5 |

Without tag filters the aggregation spans every series of the metric name. Use a filter to watch one slice, such as `outcome=failed` or `host.name=web-1`. For metrics tagged per host, per disk, or per table, an `avg` can hide one bad series behind healthy ones. Prefer `max` (or `min` for lower-is-bad metrics) so the worst series drives the alert.

Over the API the filters are the `tags` object of the rule config, for example `"tags": {"outcome": "failed"}`. An empty key or value answers 422.

#### Alerting per series

Set Group By Tags to alert on each series separately, for example `site_id` for a gauge reported once per gateway. The aggregate is then computed per combination of the listed tags, and every series that breaches sends its own notification naming it:

```
[HS API] Metric radius.accounting_freshness_seconds{site_id=RUINS}
is 22166.00 (threshold: gt 900.00)
```

A point without one of the tags falls into a series where that value reads `(empty)`. Tag filters still apply first, so `tags` and `groupBy` combine.

The cooldown is kept per series instead of per rule. A series that keeps breaching is notified again once its cooldown has passed, and a second series that starts breaching meanwhile is notified right away. On an escalation channel each series opens its own page. One evaluation sends at most 50 series notifications, worst first. Any further breaching series are summarized in a single "N more series" notice. At most 5,000 series are evaluated. Point metrics are read in tag value order. Distribution metrics keep the busiest groups when the scan is truncated. The per-series cooldowns are held in memory, so after a backend restart a series that is still breaching is notified again.

Once a notified series is back within the threshold, the rule sends an Info recovery notice naming it. On an escalation channel it resolves that series' page instead:

```
[HS API] Metric radius.accounting_freshness_seconds{site_id=RUINS}
recovered: 120.00 (threshold: gt 900.00)
```

A recovery leaves the series' cooldown counting from its last alert. For a distribution metric, a series that reports fewer observations than its configured minimum stays open until there is enough data to judge it.

If a series is missing for an hour while others still report, the rule closes its alert with a "stopped reporting" notice or resolves its escalation page. A whole-metric outage keeps all alerts open. An incomplete scan also keeps missing series open because they may be outside the results.

The "N more series" summary gets one recovery when a complete scan finds data and every reported series can be judged within the threshold. Series that appeared only in the summary receive no individual recovery. Each evaluation closes up to 50 individual alerts plus the summary. Firing state survives a backend restart. On upgrade, existing open and acknowledged pages for grouped metric rules are tracked for recovery. For chat and email, tracking starts with the first alert sent by the upgraded backend. Changing the rule's type, channel or condition, disabling it, or deleting it resolves its series pages and clears the firing state without sending recovery notices.

Over the API the keys are the `groupBy` array of the rule config, for example `"groupBy": ["site_id"]`. An empty or repeated key answers 422.

### No Data

Fires when no telemetry of the selected kind has been received for the configured number of minutes. Use it to detect a stopped service, a broken deploy, or a misconfigured SDK rather than an application-level problem.

| Option | Default | Description |
|--------|---------|-------------|
| Data Type | any | One of `any`, `endpoints`, `exceptions`, `metrics`, `tasks`. `any` fires only when all four kinds are silent |
| Silence (minutes) | 10 | How long the data must be absent before the alert fires |

### AI Trace Cost

Fires when a single [AI trace](/learn/ai-tracing) exceeds a cost threshold, catching runaway agent loops or unexpectedly expensive calls as they are ingested rather than at the end of the month.

| Option | Default | Description |
|--------|---------|-------------|
| Trace Name | `*` | A specific trace name, or the default for all traces |
| Cost Threshold ($) | 0.5 | Cost in USD a single trace must reach to trigger the alert |

The cooldown applies per trace name, so two different expensive workflows alert independently.

### AI Conversation Cost

Fires when the cumulative cost of a single [AI conversation](/learn/ai-tracing) over the last 24 hours crosses the threshold. Where AI Trace Cost catches one expensive call, this catches sessions that get expensive gradually: a runaway agent loop of cheap calls, or a user hammering an assistant.

| Option | Default | Description |
|--------|---------|-------------|
| Cost Threshold ($) | 5 | Cumulative cost in USD a conversation must reach within 24 hours to trigger the alert |

The cooldown applies per conversation, so one noisy conversation alerts once per cooldown window while a second conversation crossing the threshold still alerts immediately.

### AI Flagged Content

Fires when an [AI conversation](/learn/ai-tracing#content-flagging) matches a flagged content term. Matching happens at ingest against the language packs selected in the project's AI settings plus your custom terms, so the alert carries the matched terms.

| Option | Default | Description |
|--------|---------|-------------|
| Only These Terms | all | Optional comma-separated list to narrow the rule to specific terms; empty fires on any flagged match |

### Monitor Down

Fires when a [monitor](/learn/monitors) transitions to down, which happens only after its configured number of consecutive failures, and sends a recovery notice when it comes back up. One rule covers every monitor in the project; the alert names the monitor and carries the last probe error. The recovery notice is always Info, whatever severity the rule sets, and is green in Slack.

There are no rule-specific options. Pointing the rule at an escalation channel opens an [on-call page](/learn/on-call) instead of sending a message: the page deduplicates per monitor, re-fires never restart its escalation clock, and recovery resolves it automatically.

### SLO Burn Rate

Fires when an [SLO](/learn/slos) spends its error budget faster than the threshold over both the long and the short window, and sends a recovery notice once either window drops below it. Both windows must burn: the short one keeps a burn that already ended from paging, the long one keeps a one-minute blip from paging. The short window also ends the alert soon after the burn stops, so the Long preset does not stay firing for days. The rule fires once when the condition starts and again only after it cleared, so it never re-pages every poll. The recovery notice is always Info.

| Option | Default | Description |
|--------|---------|-------------|
| SLO | required | The SLO to watch |
| Long window (minutes) | 60 | Lookback of the long window |
| Short window (minutes) | 5 | Lookback of the short window; must be shorter than the long one. On a metric SLO with longer slices, both windows are rounded up to whole slices |
| Burn rate threshold (x) | 14.4 | Multiple of the rate that spends the budget exactly over the SLO window |

The form offers three presets: Fast (14.4x over 1h / 5m, pages when 2% of a 30-day budget burns in an hour), Slow (6x over 6h / 30m) and Long (1x over 3d / 6h). Pointing the rule at an escalation channel opens an [on-call page](/learn/on-call) that the recovery resolves automatically.

### SLO Budget Consumed

Fires when an [SLO](/learn/slos) has consumed at least the configured share of its window's error budget, and sends a recovery notice when the budget climbs back above the line. Like SLO Burn Rate it fires on the transition only.

| Option | Default | Description |
|--------|---------|-------------|
| SLO | required | The SLO to watch |
| Budget consumed (%) | 80 | Share of the error budget that has to be gone |

## Cooldown and snooze

**Cooldown** prevents a rule from firing repeatedly for the same ongoing condition. The default is 15 minutes, configurable per rule.

- For polled rules the cooldown is rule-wide: after a notification is delivered, the rule is not evaluated again until the cooldown expires. SLO rules keep being evaluated, so their recovery notice is sent at once; the cooldown only holds back a new fire, and a recovery notice does not restart it. Metric Threshold rules with Group By Tags keep their cooldown per series instead, so they are also evaluated on every poll.
- For on-ingest rules the cooldown is per condition: per error hash for New Issue and Error Regression, per trace name for AI Trace Cost. Different errors can alert back-to-back; the same error cannot.
- For Monitor Down the cooldown is per monitor and ends when the monitor recovers. Every new outage alerts, however soon it follows the last one; the failure threshold on the monitor is what damps a flapping check.

Rule-level cooldowns are persisted with the notification history, so a server restart does not cause every rule to re-fire. Per-error cooldown state is held in memory and resets on restart, meaning an already-alerted error can alert once more after a restart. Changing a rule's type, channel or condition resets its cooldown and per-error state so the new configuration takes effect immediately. Renaming it or changing its cooldown or severity keeps them.

**Snooze** mutes a rule for a set time and then turns it back on by itself. Use it during deployments, maintenance windows, or known incidents. On the **Rules** tab, click the **Snooze** icon (the clock) on the rule's row and pick a duration. **Clear snooze** ends it early.

<img src="/alerts/snooze-rule.png" alt="The Snooze Rule dialog with the durations 30 minutes, 1 hour, 4 hours, 8 hours and 24 hours, a Clear snooze link and a Cancel button" style={{ maxWidth: '300px', width: '100%', height: 'auto', marginTop: '16px' }} />

A snoozed rule shows **Snoozed** in the Status column and sends no notifications. Recovery cleanup still runs: an on-call page that a Monitor Down rule already opened still resolves when the monitor recovers.

To turn a rule off until somebody turns it back on, use the **Disable** icon next to it. The rule then shows **Off**.

## Severity

Each rule has a **Severity** setting that controls the severity attached to its notifications. The default is **Auto**, which derives severity from how badly the condition is violated:

| Rule | Auto Severity |
|------|--------------|
| New Issue | Critical |
| Error Regression | Critical |
| No Data | Critical |
| Error Rate | Warning; Critical at twice the threshold |
| Error Count | Warning; Critical at five times the threshold |
| Endpoint Error Rate | Warning; Critical at twice the threshold |
| Endpoint P95 / P99 | Warning |
| Apdex Drop | Warning; Critical when Apdex falls below 0.5 |
| Throughput Drop | Warning; Critical at an 80% drop or more |
| Impact Score Critical | Critical |
| Impact Score High | Warning |
| Impact Score Medium | Info |
| Task Duration | Warning |
| Task Failure Rate | Warning; Critical at twice the threshold |
| Metric Threshold | Warning; Critical when the value deviates from the threshold by more than 20%; the recovery notice of a series is Info |
| AI Trace Cost | Warning; Critical at three times the threshold |
| Monitor Down | Critical; the recovery notice is Info |
| SLO Burn Rate | Warning; Critical when the long window burns at twice the threshold; the recovery notice is Info |
| SLO Budget Consumed | Warning; Critical once the whole budget is consumed; the recovery notice is Info |

You can override the automatic severity by setting it explicitly on a rule to **Critical**, **Warning**, or **Info**. This is useful when you want a normally-warning condition to page as critical, or to downgrade noisy rules to info.

## History

Every notification a rule sends is recorded on the **History** tab of the Alerts page. The tab shows the last 7 days by default, and you can search it and change the time range. Each entry shows:

| Column | Description |
|--------|-------------|
| Severity | Critical, Warning, or Info |
| Rule | The name of the rule that fired |
| Subject | Alert title summarizing the condition. It links to the dashboard page the alert is about |
| Channel | The channel the notification went through |
| Status | **Sent**, **Failed**, or **Deduped** when the alert was folded into an on-call page that was already open |
| Sent At | When the notification was sent |

A delivery that fails is retried, up to 5 attempts, before it is recorded as **Failed**.

## Evaluation model and cost

Rules are evaluated in one of three ways:

- **On ingest** (New Issue, Error Regression, AI Trace Cost, AI Conversation Cost, AI Flagged Content): evaluated immediately as reports arrive, so alerts fire within seconds of the triggering event.
- **On state change** (Monitor Down): fires the moment a probe result flips the monitor's up/down state, independent of any poll interval.
- **Polled** (everything else): a background loop evaluates all enabled polled rules on an interval. The default is every 60 seconds; self-hosted deployments can tune it with `NOTIFICATION_POLL_SECONDS` (minimum 5). Detection latency for polled rules is at most one poll interval.

Each rule type has a different evaluation cost against the telemetry database. This matters mostly for self-hosted deployments with many rules or high data volume:

| Rule | Work per evaluation | Relative cost |
|------|--------------------|---------------|
| AI Trace Cost | In-memory check of the ingested batch, no queries | Minimal |
| AI Flagged Content | In-memory check of flags set at ingest, no queries | Minimal |
| Monitor Down | In-memory on the state transition, no queries | Minimal |
| AI Conversation Cost | One 24-hour cost sum per conversation in the batch | Low |
| New Issue | 1 to 3 indexed lookups per distinct new error in the batch | Low |
| Error Regression | 1 indexed lookup per distinct error in the batch | Low |
| Error Rate | One aggregate over the lookback window | Low |
| Error Count | One count over the lookback window | Low |
| Endpoint Error Rate | One aggregate over one endpoint's window | Low |
| Endpoint P95 / P99 | One percentile over the lookback window | Low |
| Apdex Drop | One aggregate over the lookback window | Low |
| Metric Threshold | One aggregate over one metric's window | Low |
| No Data | One freshness check per data type, up to four for `any` | Low |
| Task Duration | One percentile over the lookback window | Low |
| Throughput Drop | Two counts: lookback plus baseline window | Low |
| Task Failure Rate | Two queries joining tasks and exceptions over the window | Moderate |
| Impact Score | One scan of the trailing 24 hours of requests | Highest |
| SLO Burn Rate | Two sums over the SLO's precomputed buckets, no raw telemetry | Minimal |
| SLO Budget Consumed | One sum over the SLO's precomputed buckets | Minimal |

Cost-relevant behavior:

- Rules that are snoozed or still in cooldown are skipped entirely, including their queries. Longer cooldowns directly reduce evaluation load. SLO rules are the exception: they are evaluated during their cooldown so a recovery notice is never delayed, which costs little since they only read precomputed buckets. Metric Threshold rules with Group By Tags are evaluated on every poll too, because their cooldown is kept per series.
- The three Impact Score levels share one 24-hour scan per project per poll cycle through a 30-second cache, so adding all three costs the same as adding one.
- On-ingest rules deduplicate per error hash, so a busy error stops generating lookups once it has alerted until its cooldown expires.
- Polled query cost scales with the lookback window. The defaults keep windows short; a 24-hour lookback on a high-traffic project costs proportionally more.
- In SQLite mode percentile rules (Endpoint P95/P99, Task Duration, Metric Threshold with `p95`/`p99`) load the window's values into memory to compute the percentile, so prefer short lookback windows on busy projects.

## Configure alerting with the CLI or MCP

Everything above can also be done from a terminal or by an AI agent. Reading works with the [`traceway` CLI](/learn/cli). Changing anything needs `traceway-write` and the organization's Agent Access switch, both described in [Agent Write Access](/learn/agent-write-access).

Create the channel before the rule, because the rule refers to the channel by the `id` that `channels create` returns:

```json filename="channel.json"
{
  "name": "Operations email",
  "channelType": "email",
  "config": { "recipients": ["ops@example.com"] },
  "enabled": true
}
```

```json filename="rule.json"
{
  "name": "Slow orders",
  "channelId": 12,
  "ruleType": "endpoint_p95_threshold",
  "config": {
    "endpoint": "GET /api/orders",
    "thresholdMs": 1000,
    "lookbackMinutes": 10
  },
  "cooldownMinutes": 15,
  "severity": "warning"
}
```

```bash
# Look at what exists
traceway-write channels list
traceway-write alerts list

# Create a channel, then a rule that uses its id
traceway-write channels validate create --file channel.json
traceway-write channels create --file channel.json --yes
traceway-write alerts validate create --file rule.json
traceway-write alerts create --file rule.json --yes

# Change or remove
traceway-write channels update <id> --file channel.json --yes
traceway-write alerts update <id> --file rule.json --yes
traceway-write alerts delete <id> --yes
traceway-write channels delete <id> --yes

# Mute, turn off and on, test
traceway-write alerts snooze <id> --minutes 60 --yes   # 0 clears the snooze
traceway-write alerts disable <id> --yes               # and: alerts enable <id>
traceway-write channels test <id> --yes

# Delivery history
traceway-write notification-history list --file query.json
```

Replace the example ids and endpoint names with your own. A few things to know:

- **`validate` runs offline** and only checks the shape of the file. The server checks the channel settings, the references and your permissions when you create or update.
- **`update` sends the complete document**, not a patch. Start from the current version in `channels list` or `alerts list`.
- **Rule `severity`** is an empty string for automatic, or `info`, `warning`, `critical`. Whether a rule is enabled or snoozed is not part of the document: use `alerts enable`, `disable` and `snooze`.
- **Channel `enabled`** is optional. It is true by default on create and keeps its value when you leave it out of an update. The rules of a disabled channel are not evaluated.
- **`channels delete` also deletes the rules attached to the channel.** `alerts delete` removes one rule for good; snooze it if you only want it quiet for a while.
- **`channels test` sends a real notification**, and on an escalation channel it opens a real page. Saving or validating a channel does not test delivery.
- **`notification-history list`** takes a query file such as `{"pagination":{"page":1,"pageSize":20}}`, with optional `search`, `fromDate` and `toDate`.

The write MCP server offers the same actions as tools. Pass `project_id`, the `id` of an existing record, and the JSON document as `data`. The two rule state tools take a plain field instead of `data`: `duration_minutes` to snooze (0 clears it) and `enabled` to turn a rule on or off.

| What | Tools |
|------|-------|
| Channels | `list_notification_channels`, `create_notification_channel`, `update_notification_channel`, `delete_notification_channel`, `test_notification_channel` |
| Rules | `list_notification_rules`, `create_notification_rule`, `update_notification_rule`, `delete_notification_rule`, `snooze_notification_rule`, `set_notification_rule_enabled` |
| History | `list_notification_history` |

The write skill's **alert-configuration.md**, also served as `traceway://knowledge/alert-configuration`, lists every channel's fields and every rule type's JSON config. Channel configuration contains credentials: use a secure secret mechanism and do not commit or echo them.

## When no notification arrives

| What you see | Cause | Fix |
|---|---|---|
| The Test dialog shows `Test notification failed: ...` | The destination refused the message. The rest of the line is its answer, such as "Slack returned status 404" | Correct the channel with **Edit** and test again |
| On a self-hosted instance the email test succeeds, or the History tab shows **Sent**, but no email arrives | The server has no SMTP configured and wrote the email to its log | Configure SMTP on the server, see [Setting up email](#setting-up-email) |
| The Test dialog shows `A test page for this channel is still open. Resolve it before testing again.` | An earlier test of this escalation channel is still paging | Resolve that page on the On-Call page |
| The condition is met, but the History tab has no entry | The rule is **Snoozed** or **Off**, it is still in its cooldown, or its window had fewer requests than **Min Requests** | Check the Status column on the **Rules** tab and the rule's settings |
| The History tab shows **Failed** | Every delivery attempt was refused | Test the channel to see the reason |
| The History tab shows **Deduped** | The rule sends to an escalation channel and its page was already open | Nothing. The open page already covers it |
