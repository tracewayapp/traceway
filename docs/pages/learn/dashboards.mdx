# Dashboards

Dashboards visualize your metrics as tabs of chart widgets. A dashboard belongs to your **organization**, not to a single project: you build it once and apply it to any number of projects, and edits show up everywhere it is applied. Every dashboard is a plain JSON document underneath, so you can edit, export, import, and version-control them as code.

<img src="/dashboards/dashboards-page.png" alt="The Dashboards page" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

## Frontend dashboards

React, Vue, Svelte and jQuery projects receive **Web Performance** immediately when created. It includes LCP, INP and CLS, rating shares, page and release breakdowns, route timings, blocking time, request metrics and user-impact counts. Existing browser projects receive missing defaults through a one-time migration; custom dashboards remain intact. See the [RUM walkthrough](/learn/rum) for the workflow and fresh screenshots.

Flutter projects receive **Flutter Performance** when created, and Android and iOS projects **Mobile Performance**. Both chart the `app.*` [client metrics](/learn/client-metrics) of the 2.x SDKs: app start, screen display times, slow and frozen frames, hangs, crashes, sessions, users, peak memory and requests. Mobile Performance also charts ANRs and out-of-memory kills (`app.anr`, `app.oom`), which the Android and iOS SDKs report. React Native projects have no Dashboards page.

Client projects filter by release, OS and country, rather than backend instance. Use a **Rating Bar** for experience quality and a **Breakdown Table** for whole-window comparisons; line charts show the trend. Show observation counts beside percentiles.

## The Dashboards page

Each tab on the Dashboards page is one dashboard applied to the current project. A project with no dashboards yet shows a single **Browse Dashboards & Templates** button that opens the command palette described below. The active tab's menu holds everything you can do with a dashboard:

<img src="/dashboards/dashboards-menu.png" alt="Dashboard menu" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

- **Rename Dashboard**: names are unique within the organization
- **Edit as JSON**: edit the whole dashboard as one document
- **Export JSON**: download the dashboard for versioning or sharing
- **Share Dashboard**: copy a read-only link to this dashboard for the current project, time range and filters
- **Apply to Projects**: choose which projects show this dashboard
- **Remove from this Project**: unassign it here; it stays available everywhere else
- **Delete Dashboard**: remove it from every project, permanently

## Share and embed a dashboard

A shared dashboard is a read-only page at `/embed/dashboard` that opens without a Traceway account, directly or inside an iframe. It shows the dashboard's name, the time range and its widgets. The signed link controls the project, reporting timeframe, filters and access deadline.

### Share a link

Select the project and filters, then choose **Share Dashboard** from the active dashboard tab’s menu. You need write access to the project.

1. Under **Share for**, enter the number of days the link should work, from 1 to 90. The default is one day.
2. Under **Timeframe**, choose **Last 30 minutes**, **Last 6 hours**, **Last 24 hours**, **Last 42 hours** (default), **Last 7 days**, or **Last 30 days**.
3. Choose **Generate Link**. Check **Expires at**, shown in your local timezone, then choose **Copy Link**.

For example, share for **3 days** with **Last 7 days**. Each time someone opens the link during those three days, every widget shows the same seven-day window ending at that open time. Opening the link again moves the window forward and keeps the original expiry.

### Issue a link from your backend

To show KPIs inside your own application, such as a customer admin panel, issue a fresh link each time your application has authorized a viewer. The share dialog shows the exact endpoint for the current dashboard and project.

An AI agent can add this to your codebase for you: the `traceway-setup` and `traceway-write` skills and the MCP resource `traceway://knowledge/dashboard-embedding` carry the same steps. To try a dashboard and filter before writing code, `traceway-write dashboards embed <id> --tag account_id=acme --yes` (or the `create_dashboard_embed` MCP tool) issues one link.

```http
POST /api/dashboards/{dashboardId}/embed-token?projectId={projectId}&timeframe=7d
```

Use the dashboard's **numeric ID** and the project's **UUID**. The dashboard must already be applied to that project. Create a **Read only** personal access token in **Account > Personal Access Tokens** and keep it on your backend. Issuing a link changes nothing, so it needs neither a write token nor **Allow agent writes**, and a read token can be created without an expiry. Its owner needs write access to the project: a `readonly` member cannot share a dashboard. A write token works too.

Use the optional `timeframe` query parameter to choose how much history every widget displays. Omit it for the **last 42 hours**. Use a positive whole number followed by `m` (minutes), `h` (hours) or `d` (24-hour days), up to 731 days. For example, `timeframe=30m`, `timeframe=42h` and `timeframe=7d` show the last half hour, 42 hours and week respectively. The `last` prefix is also accepted, as in `timeframe=last42h`.

By default, backend-issued links expire after five minutes and resolve the timeframe at issuance. Supply a custom expiry to resolve the relative timeframe when each viewer opens the link. Traceway pins all widgets on that page to the same window. An explicit `from` and `to` always stays fixed.

Optionally add `&theme=light` or `&theme=dark` to this request. Traceway includes that choice in the returned iframe URL. Dark is the default.

The JSON body is optional and takes these fields.

| Field | Meaning |
| --- | --- |
| `from`, `to` | RFC 3339 timestamps of the window to show. Send both for a fixed interval such as a reporting week, and omit `timeframe`. Use the same timestamps on renewal to keep the same interval. |
| `expiresInDays` | Whole days from issuance, from 1 to 90, measured on the Traceway server. For a three-day link, send `{"expiresInDays":3}`. |
| `expiresAt` | Alternatively, supply an absolute future RFC 3339 timestamp at most 90 days away. Send only one expiry field. The returned `expiresAt` is the enforced deadline in UTC, to the second. |
| `tagFilters` | Tag values every widget is limited to, such as `{"account_id": "acme"}`. At most 20, each with a non-empty tag and value. They apply to every widget source and win over a filter the dashboard saved on the same tag. |

Each KPI in this example carries an `account_id` tag. The backend takes the dashboard and project from its configuration and the account from the authorized viewer's session. This keeps a customer from selecting another account through a browser parameter.

```js
// Inside your application's authenticated account-KPIs route.
if (!viewer.accountId) throw new Error('An account is required');
const url = new URL(`/api/dashboards/${dashboardId}/embed-token`, tracewayOrigin);
url.searchParams.set('projectId', projectId);
url.searchParams.set('theme', 'light');
url.searchParams.set('timeframe', '7d');
const response = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.TRACEWAY_WRITE_TOKEN}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ tagFilters: { account_id: String(viewer.accountId) } })
});
if (!response.ok) throw new Error(`Traceway returned ${response.status}`);
const { embedPath, expiresInSeconds } = await response.json();
return Response.json(
  { src: new URL(embedPath, tracewayOrigin).href, expiresInSeconds },
  { headers: { 'Cache-Control': 'no-store' } }
);
```

A successful request returns **201 Created** with these fields.

| Field | Meaning |
| --- | --- |
| `embedPath` | Ready-to-use path in the form `/embed/dashboard?dashboard=<uuid>#token=<jwt>`. Resolve it against the Traceway origin that the viewer's browser can reach. |
| `expiresInSeconds` | How long the link still works. Use it to schedule the renewal, since it does not depend on your clock matching Traceway's. |
| `expiresAt` | The same moment as a UTC timestamp. |
| `token` | The signed JWT that grants read access to this view. It is already part of `embedPath`. |
| `dashboardUuid` | Stable identifier of this dashboard in this project, also already part of `embedPath`. The same dashboard applied to a second project has a different one there. |

### Display and renew the iframe

Add an iframe such as `<iframe id="account-kpis" title="Account KPIs"></iframe>` to your admin panel. If your backend serves the example above at `/account/kpis/embed`, the browser sets the source when the panel opens and again shortly before each link expires.

```js
async function showAccountKpis() {
  const response = await fetch('/account/kpis/embed');
  if (!response.ok) throw new Error('Could not load account KPIs');
  const { src, expiresInSeconds } = await response.json();
  document.querySelector('#account-kpis').src = src;
  setTimeout(showAccountKpis, (expiresInSeconds - 30) * 1000);
}
showAccountKpis();
```

A renewed link for the same dashboard replaces what is on screen without a blank frame, and the charts move to the new link's time range. You can also change the theme on an existing link without requesting a new token. Set `theme` in the query before the fragment, for example `/embed/dashboard?dashboard=<uuid>&theme=dark#token=<jwt>`.

Traceway reads the JWT from the URL fragment, which browsers do not send to servers or include in the `Referer` header, and validates it on every request for the dashboard or its widgets. Neither backend stores an embed session. A link cannot be revoked on its own before it expires, which is why no link lasts longer than 90 days; removing the dashboard from the project stops every link for that project at once.

The page receives each widget's title and display settings only. Traceway runs the queries itself, so the filters saved on a widget never reach the viewer's browser. A metric's name is shown where the chart uses it as a series label; give the source a label to show that instead.

Reads of a shared dashboard are limited per client address: 60 opens and 600 widget reads a minute. Past that Traceway answers **429** with a `Retry-After` header.

### When something goes wrong

| Symptom | Cause |
| --- | --- |
| Issuance returns **403** | The token's owner is a `readonly` member or cannot reach the project in `projectId`. |
| Issuance returns **404** | The dashboard is not applied to the project in `projectId`. |
| Issuance returns **422** | Check the error message. Common causes include a malformed or repeated `timeframe`, mixing `timeframe` with timestamps, a missing or reversed range boundary, a window over 731 days, an expiry that is past, conflicting or more than 90 days away, or an empty tag filter. |
| The iframe says the link is invalid or has expired | Request a fresh link for the authorized viewer. |
| Widgets say they could not load | Too many reads from one address in a minute (**429**). They load again on the next open or renewal. |
| The iframe says the dashboard is no longer shared | The dashboard was removed from the project or deleted. |
| The frame stays empty | The `src` must be the `/embed/dashboard` URL built from `embedPath`. The rest of the Traceway dashboard refuses to load inside an iframe. |

## Filtering by instance

The instance picker in the dashboard header narrows every widget on the page to one reporting machine. It lists the `server_name` values seen in the selected time range, so it stays in step with what is actually reporting rather than with a static list.

The scope is applied as an extra tag filter on each widget's queries, on top of whatever filters the widget already has. Nothing is saved to the dashboard, so it does not change what teammates see; it lives in the URL as `?server=<name>` and survives time-range changes, which makes the filtered view shareable.

With **All instances** selected a widget shows whatever its sources define. The **OTelemetry Server Agent** template groups every widget by `server_name`, so its charts draw one line per server until you narrow the picker to one; a widget of your own does the same once you set its **Group By** to `server_name`.

This is where a row on the organization's [Servers page](/learn/organization-overview#servers) leads. Selecting a server there opens its project's dashboards already scoped to that machine over the last 30 minutes, jumping straight to the **OTelemetry Server Agent** tab when the project has it installed. Clear the picker to go back to the whole project.

## Counters, rates and inverted values

Host metrics such as `system.network.io` and `system.disk.io` are cumulative counters: the value only ever grows. Charted as an average they climb forever, so give such a source the **rate** aggregation. Each series (every distinct tag set, so a counter per device or direction stays on its own) is differenced against its previous sample, resets are dropped, and the result is a per-second rate with a matching unit: bytes become `B/s`, packets become packets per second. A rate keeps the same reach as any other aggregation. On ClickHouse a range over six hours reads the minute rollup and one over three days reads the hourly rollup, so buckets there are at least an hour wide.

A source can also be **inverted**, which charts 1 − value. The OTel agent reports `system.cpu.utilization` per state, and the `idle` state inverted is the busy share; that is how the Server Agent template draws CPU. The template's other widgets carry the matching filters (state `used` for memory and filesystem usage, `ESTABLISHED` TCP for open connections) so a widget never averages unrelated states together. `system.filesystem.utilization` has no state, one series per mount, so its widget charts the fullest writable mount (`mode=rw`): read-only mounts such as snap images always read as full.

Dashboards installed from the Server Agent template before these sources existed are upgraded once at startup: a widget that still carries the original plain average takes the template's current sources for its metric, and so does a Filesystem Utilization widget that still filters on state `used`, which matched no data. A widget you have edited is left as it is.

## Dashboards as code

Every dashboard is a single JSON document. Widget order in the array is the display order, and each widget carries its own config:

```json
{
  "schemaVersion": 1,
  "name": "Server",
  "widgets": [
    {
      "id": "w_6f8d9c6d",
      "title": "CPU Utilization",
      "widgetType": "line_chart",
      "config": {
        "sources": [
          { "type": "metric", "name": "system.cpu.utilization", "aggregation": "avg" }
        ]
      }
    }
  ]
}
```

**Edit as JSON** gives you the document in place, validated on save:

<img src="/dashboards/dashboards-edit-json.png" alt="Edit as JSON" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

**Export/Import** round-trips the same document. Import accepts a single dashboard or a whole-organization bundle, and the API supports an upsert mode that matches dashboards by name, so a CI job can keep dashboards in sync from files in your repository:

```bash
traceway-write dashboards validate --file system.dashboard.json
traceway-write dashboards import --file system.dashboard.json --mode upsert --yes
```

This requires [agent write access](/learn/agent-write-access).

Widget `id`s are server-generated stable strings; keep them when editing so homepage stars survive, or omit them and they are regenerated.

Paste any Grafana dashboard JSON export and Traceway converts it on a best-effort basis: `timeseries`/`graph` panels become line charts, `stat` becomes a single value, `gauge` stays a gauge, and Prometheus queries are unwrapped into metric sources (metric name, exact label matchers, `by (...)` grouping, aggregation).

## Widgets

| Type | Best For |
| --- | --- |
| Line Chart | Trends over time (CPU usage, request rate) |
| Area Chart | Volume over time with filled area |
| Stacked Area | Composition of a total across series |
| Bar Chart | Compare the latest bucket of each source/group |
| Single Value | Current or aggregated value at a glance |
| Gauge | A value against thresholds |
| Table | Latest, minimum, maximum and average of the first series |
| Rating Bar | Share of good, needs-improvement and poor experiences of a web vital over the range |
| Breakdown Table | The slowest pages, hosts or releases over the range, busiest first, with their counts |

Each widget has one or more **sources**: a metric name (auto-discovered from your project), an aggregation (`avg`, `min`, `max`, `sum`, `count`, `last`, `rate`, and for a distribution metric such as a web vital or an OpenTelemetry histogram also `p50`, `p75`, `p90`, `p95`, `p99` and `good_ratio`), optional tag filters, and an optional group-by that splits the chart into one series per tag value. Multiple sources overlay on the same chart.

## Starring widgets

The star on any widget pins it to that project's homepage, where you can resize and reorder your starred set. Stars are per project, so each project curates its own homepage even when dashboards are shared.


## Build dashboards with the CLI or an AI agent

Ask an agent with the `traceway-write` skill to inspect your instrumented codebase and build charts for its important operations. The skill's separate `dashboard-building.md` guide explains all nine chart types, counter/gauge/histogram semantics, JSON configuration and verification. The same guide is available from the write MCP server as `traceway://knowledge/dashboard-building`.

Start by confirming which metrics actually arrived:

```bash
traceway-write metrics discover --since 24h --output json
traceway-write metrics discover --name jobs.completed --key outcome --since 24h --output json
traceway-write metrics query --name jobs.completed --aggregation rate --group-by outcome --since 24h --output json
traceway-write dashboards library --output json
```

Replace the example names with names found in your application and discovery results. Inspect metric declarations, recording sites, units, attributes and exporter configuration. Spans and logs do not automatically create metrics. Match each chart to a question: incoming work, completions, failures, dependency latency or capacity. Use `rate` for cumulative counters, `max` or `last` for backlog/saturation, and bounded groups such as queue, outcome or instance. Delta values need different treatment; `count` counts stored samples, not events. For latency percentiles, query a histogram by its instrument name. Explicit-bucket backend histograms also expose `.avg` and `.count` series. Metric widgets do not support arbitrary formulas.

Use line charts for trends, stacked areas for additive contributions with matching units, and gauges only where capacity is known. Single values and gauges reduce only the first series, so avoid grouping them. Tables also summarize only the first series. An empty query means no observations, not zero failures.

Save an importable dashboard document as shown above, then validate and import it:

```bash
traceway-write dashboards validate --file system.dashboard.json
traceway-write dashboards import --file system.dashboard.json --yes --output json
traceway-write dashboards list --output json
traceway-write dashboards export 42 --output json > system.saved.json
```

Use the returned dashboard ID instead of `42`. Validation runs offline without credentials and rejects malformed documents, unsupported schema versions/chart types/aggregations, missing metric sources and oversized widget configurations. Import runs the same validation before sending a write. The backend still checks authorization and persistence constraints; neither validation nor a successful import proves that a metric has data.

The default `create` mode makes a new dashboard, suffixes duplicate names with ` (imported)`, and applies it to the selected project. It is not idempotent: list dashboards before retrying after an ambiguous timeout. `upsert` matches names case-insensitively across the selected project's organization and replaces the entire definition and description. Every assigned project sees the edit. Inspect `dashboards library` for `appliedProjectIds`, export the original, preserve unrelated widgets and widget IDs, and re-export before saving if someone else may have edited it. Upsert has no concurrent-edit check. Restore an earlier export with another upsert if needed.

Agent imports use only the selected project's organization and apply to that project; body overrides of `organizationId` or `applyToProjectIds` are refused. Deleting dashboards or removing assignments still uses the UI.

### MCP workflow

Both MCP servers offer `discover_metrics`, `query_metrics`, `list_dashboards`, `dashboard_library` and `export_dashboard`. Only `/mcp/write` and `traceway-write mcp` expose `import_dashboards`. Pass the document as an object in `data`, not as a JSON string:

```json
{
  "project_id": "<project-uuid>",
  "mode": "create",
  "data": {
    "schemaVersion": 1,
    "name": "Worker backlog",
    "widgets": [{
      "id": "queue_depth",
      "title": "Peak queue depth",
      "widgetType": "line_chart",
      "config": {
        "sources": [{"type": "metric", "name": "jobs.queue.depth", "aggregation": "max"}]
      }
    }]
  }
}
```

`data` can also be a bundle with `schemaVersion: 1` and a `dashboards` array. MCP uses the same validation and backend permission checks as CLI imports. After saving, export the returned ID and query each source with its exact aggregation, filters and grouping. Report any absent data or truncated groups rather than claiming the dashboard is verified.
