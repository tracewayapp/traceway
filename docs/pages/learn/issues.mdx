# Issues

Issues capture problems in your application: exceptions, panics, and explicitly sent messages.

<img src="/issues.png" alt="Issues Dashboard" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

## What Creates an Issue

An issue is created when:

- A **panic** or **unhandled exception** occurs during a traced request or task
- An **error** is reported to the client SDK during request handling
- Your code explicitly captures an exception or message through the client SDK
- A browser or app SDK catches an uncaught error or a crash, or an app SDK reports a native crash, an ANR, an app hang or a watchdog termination (see [Issues from Apps](#issues-from-apps))

## Errors vs Messages

Traceway captures two kinds of issues:

- **Errors**: Runtime exceptions with stack traces (panics, captured errors)
- **Messages**: Explicitly captured strings sent through the client SDK

Both appear in the Issues list with full context and attributes.

## Issues from Apps

The browser, Flutter, Android and iOS SDKs report uncaught errors and crashes as errors, with the breadcrumbs and the replay clip of the seconds before them. The Android and iOS SDKs also report what went wrong outside the app's own code, as issues of four types:

| Issue type | Platforms | What happened |
|---|---|---|
| `NativeCrash` | Android 11 and later, iOS 14 and later | A crash in native code. On Android it is read from the system's record of how the process ended, with the signal, the abort message and the crashing thread's frames (Android 12 and later). On iOS it is a crash MetricKit saw that the SDK's own signal handler could not record |
| `ApplicationNotResponding` | Android 11 and later | Android ended the app as not responding. The stack is the main thread's, from the ANR dump |
| `AppHang` | Android, iOS | The main thread was blocked for 2 seconds or more (`appHangThresholdMs`) while the app was in the foreground, with the stack it was stuck in. The message says how long: `Main thread blocked for 3.2 s` |
| `WatchdogTermination` | iOS | The system ended the app because it did not answer in time (`0x8badf00d`), as MetricKit reported it |

- `NativeCrash`, `ApplicationNotResponding` and `WatchdogTermination` are reported at the next start of the app, under the app version that crashed and, when the SDK knows it, with the session the run was in. That session's breadcrumbs and replay belong to the earlier run, not to the run that sends the issue.
- An `AppHang` is reported when the main thread runs again. A hang the app did not survive is reported at the next start with `app.hang.fatal = true`; on Android, when the system recorded that run as an ANR, the ANR is the issue instead. The issue page shows an **App Hang** section with how long the main thread was blocked and whether the app was terminated during the hang.
- `captureExitReasons` (the three exit types) and `captureAppHangs` turn them off; both are on by default. Hangs in the background or under a debugger are not reported.
- The Flutter SDK reports Dart errors only. A native crash in a plugin or the engine ends the process before Dart runs, and no stack can be taken from a blocked UI isolate, so Flutter reports hangs as the `app.hang` [metric](/learn/client-metrics) only. Add the Android and iOS SDKs to the host apps to get these four types.
- Each SDK also counts these events as [client metrics](/learn/client-metrics): `app.crash`, `app.anr`, `app.hang` and `app.oom` (an out-of-memory kill is a count, never an issue).

These four types are grouped by their type and their top five frames from the app's own code, not by the whole trace, because the system frames below them and the addresses inside them differ from one install or OS build to the next. See [Fingerprinting](#fingerprinting).

### Screen Context

Exceptions and messages from the browser, Flutter, Android and iOS SDKs say where the user was. The issue page shows them in a **Screen** section (**Page** in a browser project):

| Attribute | Shown as | Value |
|---|---|---|
| `app.screen.name` | Screen or Page | The screen's name. In the browser, the route template when the app named it (`setRoute`, the router, `recordNavigation`), else the path; in the apps the path or the class of the screen |
| `app.screen.route` | Route | The route template, when one is known |
| `app.screen.previous` | Previous screen or page | The screen before it |
| `app.screen.duration_ms` | Time on screen or page | How long the screen had been shown |
| `viewport` | Viewport | The window size: CSS pixels in the browser, dp or points in the apps |

The browser SDK puts the same keys on log lines and actions, so [Logs](/learn/logs) can be filtered by page too.

## Connection to Traces

Issues can be **linked to a trace** via context. When an exception occurs during an HTTP request or background task, the trace ID is automatically attached to the issue.

This linkage means:

- Viewing an issue shows which endpoint or task triggered it
- Viewing a trace shows any issues that occurred during execution
- Attributes from the trace context are included in the issue

<img src="/endpoint-exception.png" alt="Endpoint with Exception" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

Issues captured outside of a trace context (no active request or task) are recorded as standalone issues without a trace link.

## Fingerprinting

Every error is assigned a **fingerprint**: a 16-character hash of its normalized stack trace. The fingerprint is the identity of an issue. All occurrences that share it fold into a single issue, the issue URL contains it (`/issues/<hash>`), and archiving, regression detection, and alerting all key on it.

### Why Group Errors

Without grouping, one bug in a hot path produces thousands of raw exceptions that differ only in runtime data: another user ID, another memory address, another server. Grouping reduces that stream to one issue with an occurrence count, which keeps two things useful:

- **The issues list stays readable.** One row per root cause instead of pages of near-duplicates, so the list ranks real problems rather than repetitions of the same one.
- **Alerts stay consistent.** A [New Issue](/learn/alerts#new-issue) rule fires once per group, not once per occurrence, and [Error Regression](/learn/alerts#error-regression) can tell that a previously resolved error has genuinely returned. If grouping were unstable, every alert rule would either flood you or stay silent.

### How the Hash Is Computed

Before hashing, Traceway normalizes the stack trace so values that vary between occurrences of the same bug never affect the hash:

| Normalization | Effect |
|---------------|--------|
| Error message | Only the error type is kept (`TimeoutError`, `*net.OpError`). The message text, which often embeds user data, is dropped, including the messages on JVM `Caused by:` lines. The type has to be letters, digits, dots and underscores, so a PHP class written with backslashes (`App\Exception\Foo`) is not recognised and keeps its message in the hash. |
| Runtime values | Hex addresses, UUIDs, IP addresses and ports, email addresses, goroutine numbers, and long numbers (epoch timestamps, numeric IDs) are replaced with placeholders. |
| File locations | Absolute paths collapse to `filename:line`, URL origins are stripped from browser frames, and `@v1.2.3` module version suffixes are removed so a dependency bump does not split a group. |
| JVM frames | Line numbers inside `(File.java:123)` are dropped, and `... 12 more` becomes `... more`. |
| Column numbers | Dropped from frames that end in `:line:col`, unless the line number is 1. Minified bundles put everything on line 1, and the column is the only thing distinguishing frames there. Frames that carry the position inside brackets, such as Dart `(main.dart:20:3)`, keep the column. |
| App issue types | `NativeCrash`, `ApplicationNotResponding`, `AppHang` and `WatchdogTermination` are hashed from their type and their top five in-app frames: system libraries, program counters in them, install paths and build ids are left out. Without an in-app frame (an ANR on an idle main thread) the top five frames are used, and without frames the message with its numbers removed. |
| Resolved function names | JavaScript function-name lines are collapsed to `<fn>`, so better JS name resolution alone does not re-bucket an issue. Function and method names in other formats, such as Dart, iOS and JVM frames, are part of the hash. Uploading debug info for the first time also rewrites each frame's file, line and column, so occurrences from before the upload keep their old hash and later ones form a new issue. |
| Whitespace | Runs of spaces and blank lines are collapsed. |

The normalized trace is hashed with SHA-256 and truncated to 16 characters.

### What Stays Together, What Splits

The same logical error keeps the same hash across servers, environments, app versions, and users. A new hash (and therefore a new issue and a New Issue alert) appears when the failure itself changes: a different error type, or a different code path with different frames. Line numbers are part of the hash for most languages, so a refactor that moves code within a file can legitimately re-group an error after a deploy. JVM frames are the exception. Their line numbers are removed, so moving Java, Kotlin or Scala code inside a file keeps the same issue.

### Messages

Captured messages (strings sent through the SDK’s message API, without an exception) skip stack trace normalization and group by their exact text. Keep message text stable and put variable data in [attributes](/learn/attributes), otherwise every occurrence becomes its own issue:

```javascript
import { captureMessage } from "@tracewayapp/frontend";

captureMessage("payment provider unreachable", { order_id: String(orderId) });
```

## Issue Lifecycle

1. **Active**: When an issue first occurs
2. **Archived**: Marked as resolved by you (hidden from the default view)
3. **Reopened**: An archived issue that occurred again (regression detected)

## Attributes on Issues

Each occurrence carries the attributes recorded by its instrumentation. For an exception recorded on an OTLP span, Traceway includes the span’s attributes. Client-side exceptions can also carry browser, device, session and user metadata from the resource. Request headers, URLs or bodies appear only if the instrumentation captured them.
