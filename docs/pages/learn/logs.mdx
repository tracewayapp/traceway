# Logs

Logs are time-stamped records emitted by your application as it runs. Traceway ingests OpenTelemetry logs via OTLP/HTTP, indexes them by body, severity, service, trace, and attributes, and links each log back to the trace and span that produced it.

## Log Volume

The top of the list shows how many logs matched over the selected time range: one bar per time slice, stacked by severity from Fatal at the bottom through Error, Warn, Info, Debug and Trace, plus No level for records that carry none. The header shows the total and a count for each level.

<img src="/logs/logs-volume-chart.png" alt="The log volume chart, with a tooltip showing error, warning and info counts for one minute" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

- Each record counts toward the level its badge shows in the table: the severity text when it names a level (`WARNING` and `CRITICAL` included), otherwise the range of its severity number.
- Every filter and search applies, so the chart always describes the same logs as the list below it.
- Hover a bar to see its time range and its count per level.
- Click a bar to zoom in on it, or drag across several to zoom in on that stretch. Zooming sets a custom time range. Press Esc to cancel a drag.
- The bar width follows the time range, from one second to whole days, so a range of any length fits the chart.
- During [live tail](#live-tail) the chart refreshes every 30 seconds.

## Log Record Structure

Each log record contains the following fields:

| Field                 | Description                                                                         |
| --------------------- | ----------------------------------------------------------------------------------- |
| Timestamp             | When the log was emitted                                                            |
| Severity Number       | OTLP severity number (1-24) that maps to a text level                               |
| Severity Text         | `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, or `FATAL`                               |
| Service Name          | From the resource attribute `service.name`                                          |
| Body                  | The log message                                                                     |
| Trace ID              | Hex-encoded OTel trace ID of the active span (if any)                               |
| Span ID               | Hex-encoded OTel span ID of the active span (if any)                                |
| Resource Attributes   | Key-value pairs from the resource (e.g. `service.version`, `deployment.environment`) |
| Scope Attributes      | Key-value pairs from the instrumentation scope                                      |
| Log Attributes        | Key-value pairs attached to the log record itself                                   |

## Severity Levels

Traceway supports six severity levels, matching the OpenTelemetry specification:

| Severity | OTLP Number Range | Use Case                                          |
| -------- | ----------------- | ------------------------------------------------- |
| TRACE    | 1-4               | Very detailed diagnostic output                   |
| DEBUG    | 5-8               | Developer-level debug information                 |
| INFO     | 9-12              | Routine operational messages                      |
| WARN     | 13-16             | Unexpected but recoverable conditions             |
| ERROR    | 17-20             | Errors that don't stop the service                |
| FATAL    | 21+               | Errors that cause termination or severe impact    |

If your SDK sends only a severity number (no text), Traceway assigns the text level based on the number's range. If the exporter supplies only severity text, the stored number remains 0. The dashboard recognizes standard text levels when assigning badges and volume-chart buckets.

The severity dropdown on the Logs page filters by threshold. Picking `WARN+` keeps records with severity number 13 or higher. A text-only warning therefore appears with a warning badge but falls outside that numeric filter.

## Attributes: Resource, Scope, Log

OTel logs carry three layers of attributes, all of which are indexed and searchable in Traceway:

- **Resource attributes** describe the emitting process, e.g. `service.name`, `service.version`, `host.name`, `deployment.environment`. Every log emitted by a given service carries the same resource attributes.
- **Scope attributes** describe the instrumentation library or logger emitting the record, e.g. `logger.name`, scope `version`. Useful for separating framework logs from application logs.
- **Log attributes** are specific to a single log record, e.g. `user.id`, `order.id`, `request.method`. These are the per-event details you add when logging.

Click any log row to expand it. The expanded view shows the raw body, the linked trace and span IDs, and every attribute from all three layers. Each attribute has a filter toggle, so you can pivot from a single log line to all logs sharing that value in one click.

<img src="/logs/logs-expanded-row.png" alt="Expanded log row with attributes" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

See [Attributes](/learn/attributes) for the general model used across traces, spans, and logs.

## Message Templates

Many logging libraries send structured message templates instead of pre-rendered strings. The body keeps placeholders like `{Provider}`, and the values arrive as log attributes. This is the default in Serilog and `Microsoft.Extensions.Logging`, and other ecosystems use the same convention.

Traceway renders these templates inline. Each placeholder is resolved against the log's attributes and the value is highlighted in the message. Hover a highlighted value to see the parameter name it came from.

<img src="/logs/logs-template-tooltip.png" alt="A templated log message with the parameter name shown in a tooltip" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

A few details:

- Alignment and format specs are understood, so `{ElapsedMs:N0}` resolves to its attribute value.
- The `@` and `$` operator prefixes from Serilog-style templates are supported.
- A placeholder with no matching attribute stays as literal text, like `{MaxAttempts}` in the row above. Nothing is silently dropped.

## Searching Logs

The **Logs** page supports filtering and search across all three attribute layers plus the body:

- **Severity threshold**: keep only records at or above a minimum level (e.g. `WARN+` hides INFO and below).
- **Service**: exact match on `service.name`.
- **Trace**: exact match on the hex trace ID.
- **Body search**: full-text search over the log message. Single-token queries use a token-bloom index for speed; multi-word or punctuation-heavy queries fall back to substring matching.
- **Attribute filters**: match on any `resource.*`, `scope.*`, or log attribute key, with equals, not equals, contains or not contains, or on whether the key is there at all.
- **Time range**: pick from presets (24h, 7d, 30d) or a custom window, or drag across the [volume chart](#log-volume).

All filters combine. Results load newest first, and a "Load more" button at the end of the list fetches older records in the same query.

### Attribute Filters

Click **Add filter** to open the filter dialog. Enter a key with its layer prefix, pick the operator, and set the value. The **Not equals** operator excludes matching logs, which is useful for muting a noisy logger or a known-chatty endpoint.

**Key exists** and **Key does not exist** match on the key alone and take no value: `log.retries` exists keeps the logs that carry a `retries` attribute, whatever its value, and does not exist keeps the others. Value filters that exclude (not equals, not contains) also keep logs without the key.

<img src="/logs/logs-filter-dialog-negative.png" alt="Attribute filter dialog with the Not equals operator selected" style={{ maxWidth: '520px', width: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

Active filters show as pills under the search bar. Exclusion pills render the operator in red. Click a pill's key or value to edit it, its operator to switch to another one in place, or its X to remove it.

<img src="/logs/logs-filter-pills-zoom.png" alt="Filter pills, one equals and one not equals" style={{ maxWidth: '700px', width: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

### Filtering from a Log Row

Click a row to expand it. The body, trace ID, span ID, scope and every attribute show as tiles, and a row with many attributes shows the first six followed by a **Show N more attributes** tile.

The filter icon on an attribute tile opens a menu with the value operators, applied to that tile's value, and the two key operators, applied to its key. Once a filter is active the icon turns blue for an including filter and red for an excluding one, with the operator beside it. Choose the active operator again, or **Clear filter**, to remove it. The body, trace ID, span ID and scope tiles filter on an exact match with a single click.

<img src="/logs/logs-attribute-menu.png" alt="The filter menu of an attribute tile, with the six operators and Chart values" style={{ maxWidth: '420px', width: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

Resource and scope attributes are shown with a `resource.` or `scope.` prefix and log attributes without one. A log attribute whose own key starts with `resource.` or `scope.` is shown as `log.<key>`, so a filter made from it matches the log attribute, not a resource attribute of a similar name.

## Charting Attribute Values

When an attribute holds a number, its menu also offers **Chart values**. A chart opens above the list, for the logs the current filters and search select, so you can follow process data such as timings or counters without exporting the logs.

**Over time** draws one line per statistic for each time slice: the average, the median (P50), P95 and P99, the minimum, the maximum, the sum and the count of values. Average and maximum are shown by default, and the buttons above the chart switch the others on and off. Hover the chart to read every line for one slice, and drag across it to zoom the page to that stretch of time, as on the [volume chart](#log-volume). A slice without any value leaves a gap.

<img src="/logs/logs-attribute-chart.png" alt="The TimerSend attribute charted over time, with average, P95 and maximum lines and a tooltip" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

**Distribution** counts the values in bins with round edges, and marks P50, P95 and P99. An attribute that only ever holds whole numbers, such as a count, gets one bin per number when the range is small enough.

<img src="/logs/logs-attribute-distribution.png" alt="The distribution of TimerSend values, with P50, P95 and P99 marked" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

- A value is charted when it is a number written the way JSON writes one: `12`, `-3.5` or `1e3`. Text such as `timeout`, and forms such as `007` or ` 12`, are left out, and a note under the chart says how many values were.
- The header shows how many values were charted, with their minimum, average and maximum (and P50 and P95 for a distribution).
- The chart, its view and its lines are kept in the URL, so a link or a [saved filter](#saved-filters) opens the same chart.
- Every filter applies, including attribute filters on other keys: filter on one node, one host or one service to compare it with the rest.

## Saved Filters

**Saved filters**, at the right of the filter pills, keeps the filters you use often. **Save current filters** stores the search, the severity, the service and attribute filters and an open chart under a name. Tick **Include the time range** to store the range too; without it, a saved filter applies to whatever range is selected when you open it.

<img src="/logs/logs-saved-filters.png" alt="The saved filters menu, with two filters and what each one selects" style={{ maxWidth: '420px', width: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

- Saved filters belong to the project and are shared with everyone who can open it. Members with read-only access can apply them but not save, change or delete them.
- Click a saved filter to apply it. While the page shows exactly what a saved filter selects, the button carries its name.
- The pencil renames a saved filter or replaces what it selects with the current filters. The bin deletes it for everyone.
- Names are unique within a project, ignoring case, and a project holds at most 100 saved filters.

## Live Tail

The **Live** button next to the time range picker turns the Logs page into a live tail. While it is on, Traceway polls for new records every few seconds and prepends them to the list, so you can watch logs arrive as you exercise your system.

<img src="/logs/logs-live-button-zoom.png" alt="The Live button, active" style={{ maxWidth: '400px', width: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

A few details worth knowing:

- Live tail works with preset ranges only. A custom range is a fixed window in the past, so there is nothing to tail.
- The list is pinned to newest first. Changing the sort stops the tail.
- All active filters apply to the tail, so you can live-follow a single service or severity.
- If you scroll down to read, the view holds its position while new rows arrive above. Scroll back to the top to follow the newest logs again.
- Under very high log volume the tail jumps ahead to the newest records instead of trying to backfill every line in between.

## Linking to Traces

When your SDK emits a log inside an active OTel span context, the log record automatically carries that span's `trace_id` and `span_id`. This means:

- Every endpoint and task detail page has a **Logs** panel showing the log lines for that trace.
- Logs from services reporting to the selected project are shown together when they share the trace ID. The trace log panel does not cross project boundaries.
- Jumping from a log to the trace that produced it is a single click in the dashboard.

No extra configuration is required. The standard OTel context propagation carries the IDs to your logger.

## Retention

Logs are stored in ClickHouse with daily partitioning and a 90-day TTL on the timestamp date. Older logs are removed automatically without operator intervention. Self-hosted deployments on SQLite or DuckDB prune logs after 30 days by default, configurable with `SQLITE_RETENTION_DAYS` (on DuckDB, `DUCKDB_RETENTION_DAYS`). They can additionally cap the log table with `LOG_RECORDS_MAX_ROWS`. The cap is a cleanup task, not a hard limit: every minute the oldest logs are deleted until only the newest N rows remain. A burst that ingests more than N rows within one minute can still push the table past the cap until the next run, so size the cap with headroom for your peak log volume.

## Sending Logs

See the SDK-specific guides for setup instructions:

- [OpenTelemetry](/client/otel/logs): direct SDK export or OTel Collector
- [Symfony](/client/otel/symfony/logs): Monolog handler and the OTel PHP Logs API
- [Cloudflare Workers](/client/otel/cloudflare): Worker-side OTel logs exporter

For API callers, `POST /api/logs` accepts `traceId` and optional `spanId`, scoped to the selected project and time window. The retired `distributedTraceId` and `excludeTraceId` selectors return 400, so stale clients cannot silently widen a query. Invalid trace IDs also return 400. Each entry of `attributeFilters` takes `scope`, `key`, `value`, `exclude`, `contains` and `exists` (match on the key alone). `POST /api/logs/histogram` takes the same filters plus `maxBuckets` (10 to 200, default 80) and returns the counts behind the volume chart: `intervalSeconds`, `total`, and one bucket per interval with a count for each level.

The attribute charts take the same filters plus `attribute` (`{"scope": "log", "key": "TimerSend"}`). `POST /api/logs/attribute-series` also takes `maxBuckets` and returns `intervalSeconds`, `present` (logs carrying the attribute), `numeric` (of those, the numbers) and one bucket per slice holding a number, with `count`, `sum`, `avg`, `min`, `max`, `p50`, `p95` and `p99`. `POST /api/logs/attribute-distribution` takes `bins` (5 to 200, default 40) and returns the same counts, the overall statistics, `binWidth` and every bin with its `start`, `end` and `count`. Both answer 504 when the read takes longer than 30 seconds.
