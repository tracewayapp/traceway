# Set up remote config

import { Callout, Steps } from "nextra/components";

This page takes a browser app from install to its first rule, trigger and capture. How the pieces fit together is on [Remote SDK Config](/learn/remote-config); every field of the settings document is in the [settings reference](/learn/remote-config/reference).

<Callout type="info">
  You need `@tracewayapp/frontend` 2.0 or later, or the React, Vue, Svelte or jQuery wrapper of the same version, and a React, Vue, Svelte or jQuery project in Traceway. The examples use the start call of 2.1.0, `init({ token })`. The **Data Collection** page is also shown for Flutter, Android and iOS projects; those apps take the same rules from the 2.x SDKs, set up as in the [Flutter](/client/flutter#remote-config), [Android](/client/android#remote-config) and [iOS](/client/ios#remote-config) guides. For replay alone, each platform has a **Configure Session Capture** tutorial, for example [JavaScript](/client/js-sdk/session-capture) and [Android](/client/android/session-capture).
</Callout>

### Install and initialize the SDK

```bash
npm install @tracewayapp/frontend
```

For a framework wrapper, install `@tracewayapp/react`, `@tracewayapp/vue`, `@tracewayapp/svelte` or `@tracewayapp/jquery` instead. The legacy 1.x SDK never polls for settings: an app still on it has to [upgrade](/client/js-sdk/migration) first.

```ts
import * as Traceway from "@tracewayapp/frontend";

Traceway.init({
  token: import.meta.env.VITE_TRACEWAY_TOKEN, // the project token, from its Connection page
  serviceName: "shop-web",        // service.name, defaults to the page's host name
  version: "2.4.1",               // service.version: rules target releases with it
  environment: "production",      // deployment.environment.name
  propagateTraceHeaderCorsUrls: [/api\.example\.com/], // traceparent on your cross-origin API calls
});
```

The SDK sends to Traceway Cloud (`https://cloud.tracewayapp.com`). For a self-hosted server, add `baseUrl: import.meta.env.VITE_TRACEWAY_URL` with your server's address. Use your bundler's public prefix for the variables (`VITE_`, `NEXT_PUBLIC_`, SvelteKit's `PUBLIC_`).

That is all remote config needs: it is on by default (`remoteConfig: true`). The SDK polls for its settings right away and starts on the defaults until the first answer arrives; on later pages it starts with the settings it applied last.

Set `version` and `environment`. They are what most rules target, and without them you cannot tell a canary from production.

The React, Vue, Svelte and jQuery wrappers take the same `token`, `baseUrl` and options (React `<TracewayProvider token={…} options={{…}}>`, Vue `createTracewayPlugin({ token, options })`, Svelte `setupTraceway({ token, options })`, jQuery `init({ token, … })`), and re-export every function used below (`setAttribute`, `refreshConfig`, `track`, `recordAction`, `getInstanceId`, ...). On the CDN the jQuery wrapper is `TracewayJQuery`.

### Decide what the page may never send

The `capture*`, `sessionRecording` and `sessions` options are **ceilings**. A rule can switch a signal off or keep it on the device, but it can never turn on what `init()` turned off, and neither can a trigger or a capture.

```ts
Traceway.init({
  token: import.meta.env.VITE_TRACEWAY_TOKEN,
  version: "2.4.1",
  sessionRecording: false, // no replay on this app, whatever the dashboard says
  captureLogs: false,      // console lines never leave the page
});
```

| Option | Ceiling for |
|---|---|
| `sessionRecording` | Session replay |
| `captureLogs` | `console.*` |
| `captureNetwork` | `fetch` and XHR spans |
| `captureNavigation` | Route changes |
| `captureUserActions` | Clicks |
| `captureWebVitals` | Web vitals |
| `captureResourceTiming` | Resource and navigation timing |
| `captureLongTasks` | Long tasks |
| `captureRouteTiming` | Route change timing |
| `captureMetrics` | Aggregated performance metrics |
| `sessions` | Session start and end events |

All of them default to `true`. Use them for data your app must never collect, such as console output that could carry personal data.

### Identify users and name your events

Rules and captures can only target what the browser reports. Set the user once they sign in, then ask for the settings that apply to them right away instead of at the next poll:

```ts
Traceway.setAttribute("user.id", user.id);
await Traceway.refreshConfig();
```

Any global attribute works for targeting (`setAttribute("tenant.id", "acme")`, `setAttribute("plan", "enterprise")`). Name the moments that matter, so triggers can react to them:

```ts
Traceway.track("checkout_failed", { step: "payment" });
Traceway.recordAction("cart", "add_item", { sku: "CHAIR-1" });
```

In the dashboard, choose **Data Collection** in the sidebar of the project.

<img src="/remote-config/data-collection-tab.png" alt="The Data Collection page of a browser project: four rules, each with its targeting and its effect on one line, an enable switch, reorder, edit and delete buttons; below them an active capture of one user" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

### Create a rule

Click **New Rule**. Give the rule a **Name**; the **Enabled** switch next to it turns it off without deleting it. The dialog has four tabs:

- **Applies to**: conditions over the attributes clients report, all of which must hold. No condition matches every client. Useful keys: `service.version`, `deployment.environment.name`, `browser.name`, `browser.version`, `os.name`, `user.id`, and anything your app sets with `setAttribute`. Operators include equals, is one of, contains (also case-insensitive), starts with, matches pattern (`*` and `?`), version matches (`>=2.4 <3`), greater or less than a number (`>`, `≥`, `<`, `≤`), is set and is not set. **Roll out to** applies the rule to a share of the matching clients. Each browser profile lands in a fixed bucket per rule, so the same clients stay in as you raise the percentage; **Keep the same cohort by** buckets by another attribute instead, such as `user.id`.
- **Triggers**: recording triggers (a sequence of clicks, hovers, navigations and log lines, see [Recording trigger sequences](/learn/remote-config/trigger-sequences)) and **Capture when a log line appears** (see [Add a trigger](#add-a-trigger)).
- **Signals**: for each signal, **Inherit** (keep what earlier rules and the defaults say), **Off**, **Buffer** or **Stream**; the same for **Session replay**. **Replay images** is **Inherit**, **Off**, **Wi‑Fi only** or **Always** (`replay.images`, see [the reference](/learn/remote-config/reference#replay)): in the browser **Off** replays pictures as empty boxes and **Always** adds small copies of the page's own pictures. **Sessions**, **Performance metrics** and **All collection** (the kill switch) are **Inherit**, **On** or **Off**. Below them, **Healthy session sample (%)** and **Sessions that record metrics (%)**. A Flutter project also has **Replay type**: **Inherit**, **Video** or **Wireframe** (`replay.captureMode`).
- **JSON**: the whole settings document, for sample rates, buffer sizes and triggers the form cannot build.

<img src="/remote-config/rule-dialog-form.png" alt="The rule dialog on its Applies to tab: a condition service.version version matches >=2.4 <2.5, rolled out to 25% of matching clients" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

<img src="/remote-config/rule-dialog-signals.png" alt="The Signals tab of the same rule: Inherit, Off, Buffer or Stream for each signal, Network, Navigation and Session replay on Stream, and the Replay images select" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

Three rules that cover most needs:

| Rule | Applies to | Signals |
|---|---|---|
| Quiet console in production | `deployment.environment.name` equals `production` | Console: Off |
| Watch the 2.4 release closely | `service.version` version matches `>=2.4 <2.5`, rolled out to 25% | Network, Navigation, Session replay: Stream |
| Kill switch for old Safari | `browser.name` equals `Safari` and `browser.version` version matches `<15` | All collection: Off |

Saving a rule takes effect on each matching browser at its next poll (5 minutes by default) or when its tab becomes visible after the polling interval has elapsed.

### Add a trigger

Triggers decide what leaves the device when something goes wrong. The **Triggers** tab of the rule dialog has two builders. **Recording triggers** match a sequence of clicks, hovers, navigations and log lines and then upload the replay; see [Recording trigger sequences](/learn/remote-config/trigger-sequences). **Capture when a log line appears** starts a capture when a log line matches: choose how to match (contains, any case; matches a pattern with `*` and `?`; starts with), the minimum level, how many times within how long, how long to capture, how far back to upload, and whether to include replay.

<img src="/remote-config/log-trigger-builder.png" alt="The log-line trigger builder: contains (any case) 'payment failed', error or worse, 3 times within 60 s, capture for 30 minutes including the last 5 minutes, with replay" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

**Add trigger** switches the dialog to the **JSON** tab and inserts the trigger, where you can adjust anything the form does not show. The JSON tab also has template buttons after **Add a trigger:**

| Template | What it does |
|---|---|
| Error clip (change the built-in) | The built-in trigger: on an exception, upload the last 10 minutes of buffered breadcrumbs and a 30-second replay clip (at most every 5 seconds, 20 times per session) |
| Failed requests | After 3 responses of 500 or more within a minute, upload the last 2 minutes and stream for 5 |
| Log line → capture | When a log line contains a text, capture this device for a while |
| Error log burst → capture | After 5 error-level log lines within a minute, capture this device |
| Frozen page → capture | When the page freezes for a second or more, capture this device |
| Slow route change → capture | When a route change takes 3 seconds or more, capture this device |
| Custom event | When the app calls `track("checkout_failed")`, upload what led to it |

<img src="/remote-config/rule-dialog-json.png" alt="The JSON tab after Add trigger: the trigger from the log-line builder in the settings document, Triggers (1) in the tab bar, and the template buttons after Add a trigger" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px' }} />

The trigger the log-line builder above inserts:

```json
{
  "schemaVersion": 1,
  "triggers": [
    {
      "id": "log-payment-failed",
      "name": "Capture when \"payment failed\" is logged 3 times in 60 s",
      "steps": [
        {
          "match": { "all": [
            { "key": "signal", "op": "in", "values": ["console", "messages"] },
            { "key": "body", "op": "icontains", "value": "payment failed" },
            { "key": "severity", "op": "gte", "value": 17 }
          ] },
          "count": 3,
          "periodSeconds": 60
        }
      ],
      "actions": [
        { "type": "capture", "durationSeconds": 1800, "lookbackSeconds": 300, "signals": ["*"], "replay": true }
      ]
    }
  ]
}
```

The capture brings back what other rules switched off. With the "Quiet console in production" rule above, console lines still stream for the 30 minutes after `payment failed` is logged three times within a minute, starting with the line that completed the count.

To turn off the SDK's built-in error clip, add a trigger that only names it: `{ "id": "default-exception", "enabled": false }`.

### Capture a user or a device

When someone reports a problem, capture them:

- On a **session** page, **Capture this device** targets the browser that recorded the session, so it also covers that device's next visits.
- On an **issue**, the event card offers **Capture device** (or user, or session, whichever the event carries).
- On the Data Collection page, **New Capture** targets a device, a user, a session or any attribute.

Pick a duration (up to 24 hours), a lookback (how much of what the device was holding to upload first), and whether to include replay.

<img src="/remote-config/capture-from-session.png" alt="The New Capture dialog opened with Capture this device on a session page: Device (instance id) prefilled, for 1 hour, including the last 10 minutes, with session replay" style={{ maxWidth: '360px', width: '100%', height: 'auto', marginTop: '16px' }} />

The capture reaches the browser at its next poll or when the tab becomes visible after the polling interval has elapsed. Cancel it from the active captures list. A connected client stops that capture at its next successful poll; an offline client keeps the last settings until their capture expiry. “Nothing earlier” selects zero lookback.

### Verify it on a device

The SDK reports what it did as log events that always stream. In [Logs](/learn/logs), filter the project's logs by:

| Event | Means |
|---|---|
| `traceway.config.applied` | A settings document was applied |
| `traceway.trigger.fired` | A trigger fired (`traceway.trigger.id`) |
| `traceway.capture.started` | A capture started on this device (`traceway.capture.id`; `traceway.capture.source: trigger` for a trigger's capture) |

In the browser, `Traceway.getInstanceId()` returns the device id to capture or preview. `debug: true` in `init()` logs, with the page's own `console.warn`, the start, each settings document applied, rejected or unavailable, every exception or message the SDK dropped and why, and SDK failures it contained.

## Self-hosted operators

| What | Details |
|---|---|
| `OPAMP_POLL_INTERVAL_SECONDS` | How often browsers and mobile apps poll, default `300`, between 60 and 86400. Every open tab and running app polls, so this is a load setting. Clients under a capture poll every 60 seconds whatever it says |
| `OPAMP_MAX_CONCURRENT` | Polls processed at once, default 4 × CPU cores (at least 8). Its own gate, so polls and ingest cannot starve each other; above it a poll answers 503 with `Retry-After: 60` and the browser keeps its settings |
| Routes | `POST /api/otel/v1/opamp` and `POST /api/recordings`, both under `/api`, so existing proxy rules cover them |
| Load | One small protobuf request per open tab per interval. A poll reads its rules from an in-memory cache. A capture's progress (delivered, applied, data received) is written to the main database in the background, once per stage, so polls and ingest never wait on it |
| Several instances | On Postgres, saving a rule or a capture refreshes the cache on every instance; any instance can answer any browser |
| Content Security Policy | `connect-src` must allow the Traceway origin, as it already must for telemetry |

## Troubleshooting

| Symptom | Check |
|---|---|
| A rule does not apply | Wait for the next poll, focus the tab, or call `refreshConfig()`. Use **Preview** with the client's attributes: a condition on `user.id` only matches after `setAttribute("user.id", ...)`. Check that `init()` does not turn the signal off. A `403` on `/api/otel/v1/opamp` means the token is a backend project's or a React Native project's, and the SDK stops polling: use the browser, Flutter, iOS or Android project's token. A `404` means the server predates remote config: the SDK turns remote config off and keeps sending OTLP with its local settings (`collection` and the defaults) |
| A capture does not start | The target must match exactly what the browser reports: its instance id, `user.id` or session id. The capture starts at the next poll or tab focus |
| A trigger fires but little is uploaded | A flush uploads only what was buffered: a signal that is off has nothing to upload. The buffer keeps 10 minutes or 2 MB by default (`buffer` in the [settings reference](/learn/remote-config/reference#buffer)) |
| Nothing arrives at all | Look for a kill switch rule that matches the client, and for a plan without the data you expect. A 401 on the OpAMP endpoint stops polling: check the project token |

## Check a session’s SDK version

Open a session and read the **SDK** row of its overview, separate from **App version**: the platform and the exact SDK package version that V2 session logs report, such as `JavaScript 2.1.0`, `Flutter 2.1.0`, `Android 2.1.0` or `iOS 2.1.0`. Browser sessions received through legacy ingestion read `JavaScript v1 · legacy ingestion`. Historical sessions without version metadata read **Not reported**; missing metadata does not prove that a session used v1.

OpAMP rules and targeted captures require the JavaScript SDK v2, or the Flutter, Android or iOS SDK 2.x. V1 clients continue ingesting normally but do not apply remote settings.
