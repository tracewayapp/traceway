# Sessions & Replay

Sessions and replay are the investigation layer of [Real User Monitoring (RUM)](/learn/rum). Start with frontend performance across your users, then open a slow-session exemplar or an issue to investigate an individual experience. Metrics do not require every session to have a replay; recording depends on your SDK and Data Collection settings.

A **session** groups one visit to a browser app, typically the lifetime of an open tab, or one stretch of use of a mobile app. Its metadata, events and errors can exist without an uploaded replay. Where an [Issue](/learn/issues) shows you a single moment that something broke, a session helps you investigate the journey: what the user clicked, navigated to, scrolled past, and saw on screen, with the same console logs and network calls layered on top.

Sessions are emitted by the JavaScript SDK and its framework wrappers (React, Vue, Svelte, jQuery), and by the [Flutter](/client/flutter), [iOS](/client/ios) and [Android](/client/android) SDKs 2.x. The 2.x SDKs report every session unless `sessions: false` is set, and keep the replay on the device until an error, a trigger or a capture asks for it (see [Remote SDK Config](/learn/remote-config)). The legacy 1.x SDK emits sessions only when **always-on session recording** is enabled (`recordAllSessions: true`). The app SDKs record replay differently from a browser, since an app has no DOM; see [Replay in apps](#replay-in-apps). The Sessions page is shown for browser, Flutter, iOS and Android projects; backend and React Native projects have none.

## Sessions vs. Exception Clips

Traceway's browser SDK has always shipped a short rrweb clip alongside every captured exception: the rolling window of events from just before the error fired. That clip stays on the issue detail page; it answers "what did the page look like the moment things went wrong?".

A session is the larger envelope around those moments:

| | Exception Clip | Session |
|---|---|---|
| Default behaviour | On (rolling window flushed with a captured exception; 2.x uploads at most one clip per 5 seconds and 20 per session) | 2.x: the session is reported, its full replay is uploaded only with `recordAllSessions: true` or a remote config rule. 1.x: off (opt in with `recordAllSessions: true`) |
| Scope | The seconds before an exception: 30 s with 2.x (on Flutter, Android and iOS at most the frames of the replay ring, `maxBufferFrames`), about 10 s with 1.x | Entire tab lifetime, capped at 60 min |
| Storage | The clip's segments, tagged with the exception (1.x: one file per exception) | One file per ~30 s segment, many per session |
| When uploaded | At exception capture | Continuously, every segment rotation |
| Where surfaced | Inline on the issue page | Sessions list + dedicated detail page; linked from issues |

Both can coexist: an exception fired during a session gets its inline clip on the issue page **and** a "View full session →" link to the parent session.

## What a Session Records

The recording uses [rrweb](https://github.com/rrweb-io/rrweb) to capture DOM mutations, input events, mouse movement, and viewport changes. Replay is a faithful reconstruction: text, layout, scrolling, hover states, even mouse trails. Privacy classes work the same way they do for exception clips: `traceway-mask` replays an element's text as `*` and its images as empty boxes, and `traceway-blank` replays an empty box of the element's size (browser SDK 2.1.0 and later); rrweb's `rr-mask`, `rr-block` and `rr-ignore` keep working in 2.x and 1.x. See [Session Replay](/client/js-sdk/session-replay#privacy) for the classes and input masking in 2.x. Pictures outside a mask load from their URLs when the replay plays; the `replay.images` setting turns them into empty boxes (`off`) or adds small copies of the page's own pictures to the recording (`always`), see [`images`](/learn/remote-config/reference#replay).

With the 2.x SDK, segments carry the recording only. Console lines, `log()` lines, navigation, clicks and app events (`track(...)`, `recordAction(...)`) are stored as log records and `fetch` / `XMLHttpRequest` calls as spans, tagged with the session id, and the session page reads them from there; which of them leave the browser is set per signal by [Remote SDK Config](/learn/remote-config).

With the legacy 1.x SDK, each segment carries them alongside the rrweb stream:

- **Logs**: every `console.{debug,log,info,warn,error}` call recorded during the segment window.
- **Actions**: `fetch` / `XMLHttpRequest` calls, History API navigations, and any `recordAction(...)` breadcrumbs.

Either way, the dashboard's session detail page renders them as **Logs** and **Actions** tabs below the player, scrub-synced to the replay timeline.

### Replay in apps

The iOS and Android SDKs record the screen as a **wireframe**: the view hierarchy (UIKit and SwiftUI on iOS, views and Jetpack Compose on Android) is converted to HTML boxes, text and placeholders and recorded as rrweb events, so the same player as a browser session replays it. The Flutter SDK records a wireframe of the widget tree the same way, by default. The player's header shows the platform's icon and **Wireframe replay** instead of a page address. A wireframe carries small pictures of the images on screen when the `replay.images` setting and the app's `replayImages` option allow them (on Wi-Fi by default), never a screenshot; otherwise images are grey placeholders (see [`images`](/learn/remote-config/reference#replay)). While the soft keyboard is up, all three draw a neutral **Keyboard** box where it covers the app; its keys are never recorded. Text typed into fields is masked unless a rule sets `replay.maskAllInputs: false`, and a mask in the app blanks or blurs a view: `TracewayMask` or a `ValueKey('traceway-mask')` in Flutter, `view.tracewayMask`, `Modifier.tracewayMask()` or an `android:tag` / `testTag` of `traceway-mask` on Android, `tracewayMask` or an `accessibilityIdentifier` of `traceway-mask` on iOS (`traceway-blank` for the blank mode).

Video is Flutter only: with the `traceway_video` add-on package and `screenCaptureMode: video` (or a rule's `replay.captureMode: "video"`), the Flutter SDK records MP4 clips from the device's hardware encoder (Android, iOS, macOS), and the player shows **Flutter Screen Recording**. One session's replay is all video or all wireframe. The iOS and Android SDKs always record a wireframe and ignore `replay.captureMode`. Every app SDK uploads a clip before each exception, and consecutive segments while a capture or a rule streams replay.

In an app, a click row of the **Actions** tab is a tap and reads as the control that handled it, what it shows and the screen it was on, for example `Tap MaterialButton#pay “Pay now” on /CheckoutActivity`. The selector is the one the SDK recorded, so it can be copied into a [recording trigger](/learn/remote-config/trigger-sequences) step as it is, and a trigger's click steps show as `tap(…)` on the session's recording-reason tags.

## Session Lifecycle

With the 2.x SDK, a session begins whenever the SDK initializes, `recordAllSessions` or not, unless `sessions: false` is set. The session is kept per tab: a page load in the same tab continues it while it is within the inactivity timeout and the maximum duration below, and starts a new one otherwise. The Flutter, Android and iOS SDKs 2.x keep the session on disk with the same two limits, so a restart of the app within them continues it; their activity is a tap, a screen change or the app returning to the foreground.

With the legacy 1.x SDK, a session begins when the SDK initializes with `recordAllSessions: true` (or when the page is restored from the bfcache after a back/forward navigation; a fresh `sessionId` is generated each time).

It ends on the first of:

| Trigger | When | Behaviour |
|---|---|---|
| **Inactivity timeout** | 15 minutes without user activity (2.x: the last pointer, key, scroll or touch event; 1.x: the last DOM event rrweb observed) | Session is closed; subsequent activity opens a new one |
| **Maximum duration** | 60 minutes from session start | Hard cap regardless of activity |
| **Page unload** | `pagehide` fires (close tab, hard refresh, navigate away) | Final segment is drained, closing payload sent via `fetch keepalive`. With 2.x, the next page load in the same tab reopens the session if it is still within the two limits above |

The closing payload is not guaranteed to arrive: the browser can be force-quit before `pagehide` runs, mobile browsers freeze background tabs without firing it, and the flush itself can be dropped. The backend therefore does not depend on it. Once no replay segment has arrived for 15 minutes, the session ends at the time of its last recorded segment. A close reported more than 15 minutes after the last segment, which is what the inactivity timer sends from a tab that sat frozen in the background, is replaced the same way, so the duration reflects activity rather than time the tab spent unattended. Replay segments recorded more than 65 minutes after a session started (the 60 minute cap plus slack for a late timer) are not part of it: browser SDK versions up to 1.2.0 kept uploading segments under an ended session for as long as the tab stayed open, and those sessions end at their last recorded activity within the first 65 minutes. A session with no recorded segments and no close is shown as **No recording**.

## Attributes

Every session ships with a context map. Three layers contribute:

1. **Auto-collected defaults**: the browser SDK stamps `url`, `path`, `referrer`, `userAgent`, `language`, `platform`, `viewport`, `screen`, and `timezone` from `window` / `navigator`; exceptions, messages, log lines and actions also carry the screen they happened on (`app.screen.name`, `app.screen.route`, `app.screen.previous`, `app.screen.duration_ms`, see [Screen Context](/learn/issues#screen-context)). The Flutter, Android and iOS SDKs send their resource attributes instead (`os.*`, `device.*` and the others listed in each SDK's guide), and the session takes them over. The backend additionally stamps `client.ip` from the request.
2. **Global scope**: anything set via `setAttribute("user.id", "u_42")` / `setAttributes({ tenant: "acme" })` on the SDK. These refresh the open session and flow through subsequent sessions and exceptions. You can also pass `attributes` at initialization.
3. **Per-call attributes**: `captureExceptionWithAttributes(err, { … })` for exceptions only.

Layering: defaults → global scope → per-call. Higher layers win on key collision.

See the framework-specific guides for the API:

- [JS SDK initialization](/client/js-sdk/initialization)
- [React](/client/react/provider): `setAttribute*` plus the `<TracewayAttributes>` component / `useTracewayAttributes` hook for declarative reactive scope
- [Svelte](/client/svelte/context): `setAttribute*` plus the `useTracewayAttributes` factory
- [Vue](/client/vue/plugin): `setAttribute*` plus the `useTracewayAttributes` composable / `<TracewayAttributes>` component
- [React Native](/client/react-native): same as React, layered above device info

## Filtering Sessions

The Sessions page in the dashboard accepts:

- **Search**: paste a full session UUID for an exact match, or search a partial session ID, IP address, or attribute value (such as a user ID or email). Text search ignores case.
- **Attribute filters**: click **Add filter** or an attribute on a session row. Choose **Equals**, **Not equals**, **Contains**, or **Not contains**. Equals is case-sensitive; Contains ignores case and treats characters such as `%` literally. Excluded filters also include sessions without that attribute.
- **Filter chips**: click a chip to edit it or its × to remove it. All filters and the search combine with AND. Filters are stored in the URL for sharing and back/forward navigation.

For example, attach identity in your browser app:

```javascript
import { init, setAttributes, clearAttributes } from "@tracewayapp/frontend";

init({
  token: import.meta.env.VITE_TRACEWAY_TOKEN,
  attributes: { tenant: "acme" },
});

// After login:
setAttributes({ "user.id": "u_42", plan: "pro" });

// On logout:
clearAttributes();
```

Then add `user.id=u_42` to find that user's sessions, or combine `tenant=acme` with `plan=pro`. Attribute values must be strings. Changes replace the current session's context; `clearAttributes()` removes app-defined values while retaining browser defaults. `user.id` is also the key a [capture](/learn/remote-config#captures) of one user targets.

Older SDKs that omit session attributes remain supported.

## Sessions and Issues

Every exception captured during a session is stamped with the session's id (with 1.x, during an always-on session). From the dashboard:

- The **issue detail page** keeps showing the inline clip but renders a "View full session →" button when a session id is present.
- The **session detail page** renders a table of every exception that fired during that session, each linked back to its issue.

This stitching is independent of whether the exception was caught by your code or by the SDK's global handlers.

## Cost and Storage

Always-on session recording is more data than exception-only capture: every active tab uploads continuously, ~30 s segments, until the user leaves. Plan accordingly:

- Default segment duration is 30 s. This is a 3× reduction in S3 reads compared to a 10 s cadence; tune via `sessionRecordingSegmentDuration` (ms) if your traffic profile differs.
- With 1.x, logs and actions are drained from the rolling buffer at each segment rotation, so a single segment carries the activity it spans (no double-counting across segments). With 2.x they are not part of a segment: they are log records and spans.
- Recordings older than the platform retention window are pruned automatically.

For most apps, recording a sample of sessions (or only premium-tier users, etc.) is the right balance. With 2.x, leave `recordAllSessions` at its default of `false` and stream replay for a share of sessions or one cohort with a [Data Collection rule](/learn/remote-config/setup#create-a-rule) (`replay.mode: stream`, `replay.sessionSampleRate`). Without such a rule the SDK uploads exception clips only, with no per-segment uploads.

Build click, hover, navigation and log sequences through the [recording trigger editor](/learn/remote-config/trigger-sequences). A completed sequence requests replay and adds a filterable reason to the session. Multiple triggers can explain the same recording, and their historical names and sequences remain available after a rule changes.
