# Spans

Spans are the underlying primitive Traceway stores. Everything else (Endpoints, Tasks, AI Traces, Issues) is a [materialized view](/learn/traces#spans-are-the-primitive) derived from the spans you ingest. The shape is OpenTelemetry-native, so your existing OTel instrumentation works without translation.

## What a span captures

| Field | Description |
| --- | --- |
| `trace_id` | The OTel trace id the span arrived with, 32 hex characters |
| `span_id` | 16 hex characters for OTLP input; native and migrated UUID IDs can be 32 in the Traceway API |
| `parent_span_id` | The span's direct parent within the trace, empty for a root span |
| `name` | Descriptive label (`db.users.find`, `POST https://api.stripe.com/v1/charges`, etc.) |
| `kind` | One of OTel's `SERVER`, `CLIENT`, `INTERNAL`, `PRODUCER`, `CONSUMER` |
| `start_time` / `duration` | When it started and how long it ran |
| `attributes` | Arbitrary key-value metadata (HTTP, DB, AI, custom) |
| `events` | Timestamped events on the span; `"exception"` events become [Issues](/learn/issues) |

## A trace is a trace, a span is a span

Traceway stores accepted spans after sampling, permission and healthcheck filtering, with the trace id, span id and parent span id it arrived with. Nothing is renamed or re-rooted at ingestion.

An endpoint, a task and an AI trace are each a copy of one span, the one that started the request, the job or the LLM call. The copy carries the same three ids as its span. That is all the pages need:

- The waterfall of an endpoint is the spans of its trace that sit below its span.
- Everything connected to it is whatever else shares its trace id, in any project you can open.
- An exception records the trace and the span it happened on. The endpoint or task it belongs to is the nearest one above that span.

Canonical span storage preserves IDs across export batches. Entity classification can depend on visible ancestry: a nested HTTP server span is suppressed only when a local HTTP server ancestor is present in its resource block. Missing parents are treated as unknown, so separately exported nested server spans can produce extra endpoint projections. A child can join its parent once both are stored and included in the query window and graph limits.

Span reads look 24 hours either side of the endpoint, task or AI trace you opened. A span recorded further away than that is not shown on its page.

## Span explorer

The **Spans** page searches every span of the project in a time range, the last hour by default and up to 31 days: by name, service, kind, status, minimum and maximum duration, trace ID and span attributes. Click a result to open its whole trace with that span selected.

### Attribute filters

**Add attribute filter** takes an OpenTelemetry attribute key, such as `http.request.method` or `db.system.name`, and an operator:

| Operator | Matches |
| --- | --- |
| **Equals** | Spans whose attribute has exactly this value |
| **Not equals** | Spans whose attribute has another value, and spans without the attribute |
| **Contains** | Spans whose attribute contains the text, ignoring case |
| **Not contains** | Spans whose attribute does not contain the text, and spans without the attribute |
| **Key exists** | Spans that carry the attribute, whatever its value |
| **Key does not exist** | Spans without the attribute |

Each filter is a pill under the search bar, with exclusions in red. Click a pill's operator to switch it in place, its key or value to edit it, or its X to remove it. A search takes up to 10 attribute filters.

### Charting durations

A chart above the results shows the duration of every span the filters match. **Over time** draws P50, P95 and P99 for each slice of the range; the buttons above it add the average, minimum, maximum, sum and count. Hover to read every line for one slice, and drag across the chart to zoom the page to that stretch of time. A deploy that made an operation slower shows up as a step, as in the picture above.

**Distribution** counts the durations in bins and marks P50, P95 and P99. When the slowest span took at least 20 times as long as the fastest, every bin covers the same ratio instead of the same width, so the axis is logarithmic and two kinds of request that share a name, such as cache hits and cache misses, show up as separate humps.

<img src="/spans/spans-duration-distribution.png" alt="The durations of GET product spans on a log scale: cache hits near 1.5 milliseconds and cache misses near 40 milliseconds, with P50, P95 and P99 marked" style={{ maxWidth: '100%', height: 'auto', marginTop: '16px', borderRadius: '8px', border: '1px solid #e5e7eb' }} />

- The chart reads the same spans as the table, one copy of each: a span that an exporter retried, and Traceway stored twice, counts once.
- The X closes the chart and **Chart** brings it back. Whether it is open, what it charts, its view and its lines are kept in the URL, so a link or a saved filter opens the same chart.
- A chart over a long range of busy services takes as long as the search itself; when either takes too long, the page asks you to narrow the range or add a filter.

### Charting an attribute

The picker in the chart's corner, **Duration** by default, switches the chart to a numeric attribute of the matching spans, such as `db.response.returned_rows` or `http.response.body.size`. It offers the same views and lines. Only spans carrying the attribute are charted, and only values written as numbers (`12`, `-3.5`, `1e3`); a note under the chart says how many were not.

### Filtering from a trace

In any span waterfall, on the trace page, an endpoint request or a task run, click a span to see its attributes. The filter icon beside each attribute opens the span explorer filtered on it, with the same six operators. An attribute holding a number also offers **Chart values**, which opens its chart across the same operation: the same service and span name. The explorer keeps the time range of the page you came from, or else looks at the hour around the span, and searches the span's own project.

### Saved filters

**Saved filters**, at the right of the filter pills, store the search, its filters and the chart under a name, with or without the time range, exactly as on the [Logs page](/learn/logs#saved-filters). They belong to the project and are shared with everyone who can open it, and each page keeps its own list.

## What spans are good for

Spans tell you **where the time went**. If an endpoint takes 500ms and 450ms of that is in a `db.users.find` span, you know what to optimize. The dashboard's drill-down (Endpoints / Tasks / AI Traces → instance → waterfall) bottoms out in spans.

Common things to wrap in a span:

- Database queries (auto-instrumented in most stacks)
- External HTTP calls (`http.client` auto-instrumentation)
- Cache operations
- File I/O
- Business-logic steps you want to time

## Naming

Hierarchical names group well in the dashboard's filters:

```
db.users.find
db.orders.insert
api.stripe.charge
api.sendgrid.send
cache.redis.get
logic.pricing.calculate
```

`category.resource.action` is a useful default. Pick something and stay consistent.

## Nesting

In Traceway's storage, span nesting is reconstructed from `parent_span_id`. The waterfall view renders children indented under their parent in chronological order, exactly the way the OTel spec defines a trace tree.

```
endpoint POST /api/checkout: 200ms
├── validate.cart           20ms
├── pricing.calculate       80ms
│   └── db.products.batch    40ms
├── stripe.charge           60ms
└── db.orders.insert        30ms
```

## Manual spans

The Traceway SDKs and any standard OTel SDK can create spans manually. See the per-framework client docs for the exact API; the underlying shape is always the same OTel span model described above.
