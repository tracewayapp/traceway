# Upgrade notes: V2 telemetry tables

This release uses OpenTelemetry trace and span identity throughout telemetry storage. Accepted OTLP spans keep their source trace, span and parent IDs, and their endpoint, task, AI trace and exception projections carry that identity. Sampling, ingest permissions, health-check filtering and rejected input can leave spans absent. Native `/api/report` data is adapted as described below.

No ClickHouse version upgrade is required. Legacy telemetry tables are not rewritten or dropped.

## What changes

Five new tables are created next to the ones they replace: `spans_v2`, `endpoints_v2`, `tasks_v2`, `ai_traces_v2` and `exceptions_v2`. The table-creation migrations are `0085` to `0089` on ClickHouse, `0025` on SQLite and `0005` on DuckDB. They create empty tables without rewriting telemetry history; completion still depends on database availability and schema locks.

From the first start of the new release:

- New telemetry is written to the V2 tables only.
- The dashboard, the API, the CLI and notification rules read the V2 tables only.
- The old tables (`spans`, `endpoints`, `tasks`, `ai_traces`, `exception_stack_traces`) stay as they are and receive nothing new.

So right after the upgrade the dashboard shows new data and none of your history. The history is still there, in the old tables. The next section brings it over.

ClickHouse migration `0090` adds `span_version`, a materialized 32-byte fingerprint, to `spans_v2`. New inserts compute it once, so topology and search can select consistent retries without reading the full protobuf payload. Existing V2 parts remain readable: ClickHouse computes the expression when the column is absent. Those parts still pay the payload-read cost until a merge or an operator-scheduled `ALTER TABLE spans_v2 MATERIALIZE COLUMN span_version` writes the column. This optional mutation consumes I/O; the upgrade does not start a bulk rewrite. Equal-duration conflicting retries may select a different version than an earlier preview, but all ClickHouse readers use the same order.

## Moving your history over

Set one environment variable and restart:

```
V2_MOVE_OVER=true
```

The backend then copies the old tables into the V2 tables in the background, while it keeps serving traffic. It works newest day first, so yesterday is back before last month, and within a day it moves endpoints, tasks and AI traces before exceptions and spans.

| Variable | Default | Meaning |
|----------|---------|---------|
| `V2_MOVE_OVER` | unset | `true` runs the move on startup, then again one hour after each pass ends. |
| `V2_MOVE_OVER_OLDEST` | unset | A `YYYY-MM-DD` date. Days before it are left in the old tables. |

Things worth knowing:

- **It can stop and resume.** Each UTC day of each source table is recorded in `v2_move_over_days` in the **transactional database** (PostgreSQL or the main SQLite database), created by migrations `pg/0143` and `sqlite/0077`. The worker commits `started` before copying and `done` only after every batch succeeds, including canonical row validation. After a failure it retries in one hour; after a restart it runs immediately. Destination identity checks skip rows already present when an interrupted day is scanned again.
- **It runs inside the backend.** There is no separate tool, because an embedded DuckDB file cannot be opened by a second process.
- **Finish upgrading old writers first.** Completed source-table/date pairs are skipped on later passes. Rows written into an already completed day by an old server or a historical importer are not picked up automatically.
- **Run it on one instance.** With several backend replicas, set the variable on exactly one of them.
- **On SQLite and DuckDB it stops at your retention window.** Days older than `SQLITE_RETENTION_DAYS` or `DUCKDB_RETENTION_DAYS` would be deleted by the retention worker straight away, so they are not moved.
- **Progress is logged.** Each day prints a line such as `move-over: 2026-09-19 spans: 23677 rows in 1.0s`, and the last line says it is done. After that you can remove the variable. Leaving it set checks for remaining work hourly, but skips completed source-table/date pairs. The one-hour delay starts after a pass finishes, so a long pass cannot overlap the next one.

The move reads at most 20,000 source rows at a time, narrowing time slices when they fill. An overfull second uses offset pages ordered by every copied source value. This preserves equal IDs across projects, traces and occurrences, including identical retry rows on a fresh pass. Keep the legacy tables immutable while copying: complete the writer cutover first and do not import or delete source rows during a pass. Sorting and offset scans still compete with ingest for CPU, memory, disk and database connections; this page bound is not an I/O rate limit. Disable the worker and restart if you need to stop that load.

Inspect progress in the transactional database:

```sql
SELECT source_table, day, state, moved_rows, updated_at
FROM v2_move_over_days
ORDER BY day DESC, source_table;
```

`moved_rows` counts source rows scanned by the completed pass, including rows skipped during recovery because they were already copied. It is not a count of newly inserted V2 rows: one old endpoint, task or AI trace also produces its own span. No main-DB transaction is held while telemetry is copied. The two stores do not share a transaction. On recovery, projections match project, occurrence ID, trace ID, span ID and recorded time at the destination's precision; canonical spans match project, trace and span. A repeated occurrence with that exact identity is treated as already copied, so recovery can coalesce legacy retries.

If you ran an earlier V2 preview with ID-only paging or recovery, some days may be marked done despite skipped rows. Stop the worker, back up the transactional database, and mark the affected source-table/date pairs `started` (do not delete the markers). For example:

```sql
UPDATE v2_move_over_days
SET state = 'started'
WHERE source_table = 'endpoints' AND day = '2026-09-19';
```

Restart with `V2_MOVE_OVER=true` to re-scan that day using destination identity checks. Use the actual affected table/date, within the configured retention window. The fix does not automatically reset completed production history.

## What moved history looks like

- Endpoints, tasks and AI traces keep their ids, so existing links keep working.
- Recovered spans are attached using available legacy owner IDs and timestamps. Parents or resource metadata the old schema never stored cannot be reconstructed, and ambiguous reused owner IDs or long gaps can limit reconstruction.
- An exception is attached to the endpoint or task it belonged to.
- A task that came from OpenTelemetry is now recorded at the time it started. The old tables recorded the time it ended.
- The endpoints and tasks of one trace are listed together on the Distributed Trace card, but not nested under each other. The old tables never stored which span an endpoint was called from. New data nests.
- Downloading an old span as OTLP returns a span rebuilt from its stored fields, since the original payload was never kept.

## Disk usage

Until you remove the old tables, moved days exist twice. V2 keeps the full span payload and stores the span behind each endpoint and task as its own row. Storage cost depends on attributes, resources, payload size and compression; the historical benchmark figures are not current capacity estimates. Measure your workload and include both stores. ClickHouse's per-table part and row metrics include both legacy and V2 tables, distinguished by the `table` tag.

The ClickHouse V2 tables have no TTL, like the tables they replace. Plan disk for them or drop old daily partitions. SQLite and DuckDB keep following `SQLITE_RETENTION_DAYS` and `DUCKDB_RETENTION_DAYS`, for the old tables and the new ones.

Once the move is done and you are happy with what you see, the old tables are only a backup. A later release will drop them. On ClickHouse you can reclaim the space earlier by dropping their partitions.

## Rolling back

The previous release still works after the upgrade, on every backend, because its tables were not touched. It shows the history it always had, and nothing that was recorded by the new release. Telemetry recorded while the new release ran stays in the V2 tables and is shown again when you upgrade.

## API changes

Clients of the HTTP API see these changes. The Traceway CLI and MCP server of the same release already use them.

- Endpoints, tasks and AI traces carry `traceId`, `spanId`, `parentSpanId` and `linkedTraceId` as hex strings. `distributedTraceId` is gone.
- Spans carry `traceId`, `spanId` and `parentSpanId`. `id`, `otelTraceId` and `distributedTraceId` are gone.
- An exception's `traceId` is now the trace id, and `spanId` is the span it was recorded on. The endpoint, task or AI trace it happened in is returned as `relatedEntity` on the exception responses.
- `POST /api/distributed-traces/:traceId` takes the hex trace id. A dashed UUID is still accepted. Omitting `recordedAt` anchors entity lookup on now (48 hours either side); pass an RFC 3339 timestamp for historical traces. Malformed timestamps return 400. The response carries `traceId` in place of `distributedTraceId`.
- `POST /api/logs` keeps `distributedTraceId` and `excludeTraceId` for linked-trace expansion within the selected project. `traceId` searches one exact trace.
- The span attribute `traceway.distributed_trace_id` no longer replaces a row's trace id. It is stored as the row's linked trace.

Native `/api/report` IDs remain UUID-width in the HTTP API. When synthesized spans are exported as OTLP, native span and parent UUIDs are mapped to eight bytes using the first eight bytes of SHA-256 over `traceway.native.span-id.v1:` followed by the decoded UUID bytes (an all-zero result is replaced by `0000000000000001`). Already eight-byte span IDs are preserved. Trace IDs remain sixteen bytes. The original native IDs are included as `traceway.native.span_id` and `traceway.native.parent_span_id` attributes, and the export includes native attributes, `service.name` and available scope metadata. Actual OTLP input retains its original payload.

Span search, graph topology, graph attributes and export choose one deterministic retry version: longest duration first. ClickHouse breaks ties by the stored SHA-256 fingerprint of the length-prefixed span, resource and scope protobuf bytes; SQLite and DuckDB use descending stored protobuf bytes. Search filters and pagination apply to those logical spans. These reads do extra work in the database to select a consistent version; attributes still obey per-span and total UTF-8 byte limits before transfer.

Detail responses expose `spanGraphStatus`. When membership is partial or unavailable, exceptions on missing descendant spans may also be absent; an empty exception list does not establish that the occurrence succeeded. The dashboard warning and CLI `traces show` graph status make this limitation visible.
