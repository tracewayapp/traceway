# Android

A release build of an Android app runs R8, which minifies and obfuscates the bytecode. When a Kotlin or Java exception is thrown out of that code, every class and method has been renamed and the line tables rewritten, so the trace arrives obfuscated:

```
a.b: card declined for $30.59
	at a.a.a(SourceFile:2)
	at com.example.app.MainActivity.a(SourceFile:3)
```

The trace is reversed with the build's `mapping.txt`. With it uploaded, the trace above resolves to source:

```
com.example.app.PaymentDeclinedException: card declined for $30.59
	at com.example.app.Checkout.chargeCard(Checkout.kt:5)
	at com.example.app.Checkout.applyTax(Checkout.kt:10)
	at com.example.app.Checkout.checkout(Checkout.kt:18)
	at com.example.app.MainActivity.crashKotlin(MainActivity.kt:33)
```

This page covers how to upload `mapping.txt` with the Gradle plugin, the upload API, how a trace is recognized and resolved, and how to migrate an app off Honeycomb. For when symbolication runs, the cache, and the `.tw` format, see [Architecture](/symbolicator).

## R8: what `mapping.txt` says

A release build with `minifyEnabled true` runs R8, which shrinks, optimizes, and obfuscates the bytecode. It renames classes and methods to short tokens, inlines small methods into their callers, and rewrites the line-number table. The reverse map is the `mapping.txt` written to `app/build/outputs/mapping/<variant>/mapping.txt`.

Retracing reads three things from it: a class line maps the original fully qualified name to the obfuscated one; a `sourceFile` comment records the original file; and member lines map each method with line ranges on both sides. Because R8 inlines, one obfuscated frame can expand to several source frames, listed innermost first. The grouping hash is therefore computed **after** retrace, so inline expansion does not split one error into many issues.

## Uploading symbols with the Gradle plugin

The Traceway symbols Gradle plugin finds the `mapping.txt` and posts it. It's published to Maven Central, so add `mavenCentral()` to your `pluginManagement` repositories in `settings.gradle.kts`:

```kotlin
pluginManagement {
  repositories {
    gradlePluginPortal()
    mavenCentral()   // resolves com.tracewayapp.symbols
  }
}
```

Then apply it to your app module:

```kotlin
plugins {
  id("com.tracewayapp.symbols") version "0.0.1"
}

android {
  buildFeatures { buildConfig = true }   // required for the injected UUID field
  buildTypes {
    release { isMinifyEnabled = true }
  }
}

traceway {
  uploadToken = "<your project upload token>"
  url = "https://your-traceway-host"    // instance base URL
  autoUpload = true                     // run after assembleRelease; default false
  // proguardUuid = "..."               // optional: pin the build UUID yourself
}
```

`uploadToken` is your project's **upload token** from the dashboard, the same one used for JavaScript source maps and iOS dSYMs. It is **not** the runtime token in your SDK connection string — using the connection-string token here is rejected with a 401.

With `autoUpload = true` the upload runs automatically after `assembleRelease`. The default is `false` (so a release build never depends on backend availability); upload explicitly instead, which is the better fit for CI:

```bash
./gradlew assembleRelease uploadReleaseTracewaySymbols
```

The plugin embeds a ProGuard UUID into `BuildConfig.TRACEWAY_PROGUARD_UUID` and names the uploaded mapping `<uuid>.txt`. The UUID is derived from the module path, variant, and app version (`versionName` + `versionCode`), so each released version gets its own mapping — **bump the version each release** so a new upload doesn't overwrite a previous release's mapping (or set `proguardUuid` explicitly for full control). Pass that value to the SDK so reported crashes carry the matching UUID:

```kotlin
Traceway.init(
  application = this,
  connectionString = BuildConfig.TRACEWAY_DSN,
  options = TracewayOptions(
    version = "1.0.0",
    proguardUuid = BuildConfig.TRACEWAY_PROGUARD_UUID,
  ),
)
```

## The upload API

The plugin posts to the shared symbols endpoint:

```
POST /api/symbols/upload
Authorization: Bearer <upload token>
Content-Type: multipart/form-data
```

| Field | Required | Notes |
|---|---|---|
| `files` | yes | The `mapping.txt` file. 200 MB per file. |
| `proguard_uuid` | yes | The build UUID. The mapping is stored as `<uuid>.txt`. |

The backend recognizes an R8 mapping by its header and class lines. The stored key is:

```
androidmappings/{projectId}/{proguardUuid}.txt     # R8 mapping, by build UUID
```

## How a trace is recognized and resolved

- A `at pkg.Class.method(File:line)` frame is retraced through the build's mapping, expanding inlined frames.
- Any other line passes through; obfuscated class tokens in the exception header and `Caused by:` lines are deobfuscated too.

A maximum of 50 frames are emitted, inline expansions included. A frame with no match keeps its raw form, so a trace is never worse than it arrived.

## Migrating from Honeycomb

Honeycomb symbolicates Android in its OpenTelemetry Collector, keying ProGuard mappings by the `app.debug.proguard_uuid` resource attribute and storing them as `<uuid>.txt`. Traceway reads that **same** attribute and `<uuid>.txt` naming on the OTLP path, so a migrating app does not change its instrumentation.

To move an app from Honeycomb to Traceway:

1. Point the OpenTelemetry Android SDK's OTLP exporter at Traceway's endpoint (`/api/otel/v1/traces`) with a Bearer project token.
2. Keep your existing `proguard-uuid` Gradle plugin, which sets `app.debug.proguard_uuid`.
3. Upload your `<uuid>.txt` mappings to Traceway (via the Gradle plugin above, or any POST to `/api/symbols/upload` with a `proguard_uuid` field).

Symbolication then happens in Traceway, in the collector processor or in the backend, with no Honeycomb collector in the path.
