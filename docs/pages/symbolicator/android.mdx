# Android

A release build of an Android app runs R8, which minifies and obfuscates the bytecode. When a Kotlin or Java exception is thrown out of that code, every class and method has been renamed and the line tables rewritten, so the trace arrives obfuscated:

```
a.b: card declined for $30.59
	at a.a.a(SourceFile:2)
	at com.example.app.MainActivity.a(SourceFile:3)
```

The trace is reversed with the build's `mapping.txt`. With it uploaded, the trace above resolves to source:

```
com.example.app.PaymentDeclinedException: card declined for $30.59
	at com.example.app.Checkout.chargeCard(Checkout.kt:5)
	at com.example.app.Checkout.applyTax(Checkout.kt:10)
	at com.example.app.Checkout.checkout(Checkout.kt:18)
	at com.example.app.MainActivity.crashKotlin(MainActivity.kt:33)
```

This page covers how to upload `mapping.txt` with the Gradle plugin, the upload API, how a trace is recognized and resolved, the compact `.tw` artifact each mapping compiles into, and how to migrate an app off Honeycomb. For the shared cache model and when symbolication runs, see [Architecture](/symbolicator).

## R8: what `mapping.txt` says

A release build with `minifyEnabled true` runs R8, which shrinks, optimizes, and obfuscates the bytecode. It renames classes and methods to short tokens, inlines small methods into their callers, and rewrites the line-number table. The reverse map is the `mapping.txt` written to `app/build/outputs/mapping/<variant>/mapping.txt`.

Retracing reads three things from it: a class line maps the original fully qualified name to the obfuscated one; a `sourceFile` comment records the original file; and member lines map each method with line ranges on both sides. Because R8 inlines, one obfuscated frame can expand to several source frames, listed innermost first. The grouping hash is therefore computed **after** retrace, so inline expansion does not split one error into many issues.

## Uploading symbols with the Gradle plugin

The Traceway symbols Gradle plugin, `com.tracewayapp.symbols`, finds the `mapping.txt` and posts it. It shares its version with the [Android SDK](/client/android) (2.1.0) and is published to Maven Central, so add `mavenCentral()` to your `pluginManagement` repositories in `settings.gradle.kts`:

```kotlin
pluginManagement {
  repositories {
    gradlePluginPortal()
    google()
    mavenCentral()   // resolves com.tracewayapp.symbols
  }
}
```

Then apply it to your app module and configure the upload:

```kotlin
// app/build.gradle.kts
import java.util.Properties

plugins {
  id("com.android.application")
  id("com.tracewayapp.symbols") version "2.1.0"
}

val localProperties = Properties().apply {
  rootProject.file("local.properties").takeIf { it.exists() }?.inputStream()?.use { load(it) }
}

android {
  buildTypes {
    release { isMinifyEnabled = true }
  }
}

traceway {
  // The project's upload token, not the SDK's token: from the environment on CI, else local.properties.
  uploadToken = System.getenv("TRACEWAY_UPLOAD_TOKEN") ?: localProperties.getProperty("TRACEWAY_UPLOAD_TOKEN")
  // A self-hosted server; blank or unset is Traceway Cloud.
  url = System.getenv("TRACEWAY_URL") ?: localProperties.getProperty("TRACEWAY_URL", "")
  autoUpload = true                     // run after assembleRelease; default false
  // proguardUuid = "..."               // optional: pin the build UUID yourself
}
```

Put `TRACEWAY_UPLOAD_TOKEN=YOUR_UPLOAD_TOKEN` in `local.properties` (git-ignored, next to the SDK's `TRACEWAY_TOKEN`), or set the `TRACEWAY_UPLOAD_TOKEN` environment variable on CI. Never write the token into `build.gradle.kts`, which is committed. `url` is only for a self-hosted server: an unset or blank value uploads to Traceway Cloud (`https://cloud.tracewayapp.com`), so the same line works on both.

The plugin may be applied before or after the Android plugin. In a module that has neither `com.android.application` nor `com.android.library`, the build fails at configuration time with `com.tracewayapp.symbols needs an Android app or library module: apply com.android.application or com.android.library too`.

`uploadToken` is your project's **upload token** from the dashboard (Connection page, Symbol Upload), the same one used for JavaScript source maps and iOS dSYMs. It is **not** the project token the SDK starts with; that one is rejected with a 401.

With `autoUpload = true` the upload runs automatically after `assembleRelease`. The default is `false` (so a release build never depends on backend availability); upload explicitly instead, which is the better fit for CI:

```bash
./gradlew :app:assembleRelease :app:uploadReleaseTracewaySymbols
```

The plugin makes a ProGuard UUID per variant and app version, writes it into the app's assets, where the SDK reads it at start and sends it as the `app.debug.proguard_uuid` resource attribute of every record, and names the uploaded mapping `<uuid>.txt`. Nothing has to be passed to `Traceway.init`. When the module builds a `BuildConfig`, the UUID is also `BuildConfig.TRACEWAY_PROGUARD_UUID`. The UUID is derived from the module path, variant, and app version (`versionName` + `versionCode`), so each released version gets its own mapping. **Bump the version each release** so a new upload doesn't overwrite a previous release's mapping (or set `proguardUuid` explicitly for full control; an app that uploads `mapping.txt` itself passes the same value as `TracewayOptions(proguardUuid = …)`). A minified build without a UUID (no plugin, no `proguardUuid`) logs one warning at start: its crashes arrive obfuscated.

The same plugin also records `android.util.Log` lines (Timber's too), configured in the same `traceway { }` block:

```kotlin
traceway {
  logcat {
    enabled = true                // default true
    minLevel = "info"             // default "info": verbose, debug, info, warn, error or assert
    includeDependencies = true    // default true: libraries' calls too (Timber lives in one)
    disabledFor("benchmark")      // variants or build types left as they are
  }
}
```

See [Automatic log capture](/client/android#automatic-log-capture) on the Android SDK page for what it rewrites.

## The upload API

The plugin posts to the shared symbols endpoint:

```
POST /api/symbols/upload
Authorization: Bearer <upload token>
Content-Type: multipart/form-data
```

| Field | Required | Notes |
|---|---|---|
| `files` | yes | The `mapping.txt` file. 200 MB per file, 250 MB and 1000 files total per request (a larger body answers `413`, too many files `422`). |
| `proguard_uuid` | yes | The build UUID. The mapping is stored as `<uuid>.txt`. |

The backend recognizes an R8 mapping by its header and class lines. The stored key is:

```
androidmappings/{projectId}/{proguardUuid}.txt     # R8 mapping, by build UUID
```

## How a trace is recognized and resolved

- A `at pkg.Class.method(File:line)` frame is retraced through the build's mapping, expanding inlined frames.
- Any other line passes through; obfuscated class tokens in the exception header and `Caused by:` lines are deobfuscated too.

A maximum of 50 frames are emitted, inline expansions included. A frame with no match keeps its raw form, so a trace is never worse than it arrived.

## The flat format

Memory mode parses the build’s `mapping.txt` and caches that mapping on the heap. In disk mode the engine compiles the mapping to a [`.tw` artifact](/symbolicator#the-tw-resolver-format) on a cache miss, or reuses one already in blob storage.

Where the other languages' `.tw` files map an address (a bundle position, a program counter) to a span of frames, the R8 `.tw` maps an obfuscated **(class, method, line)** to its original frames. It holds two sorted tables, both binary-searchable, with every class, method, and file name interned once:

- A **class table**, sorted by obfuscated class name, mapping each token to its original fully qualified name and source file.
- A **member table**, sorted within each class by obfuscated method name. Each record carries the original class, method, and file, plus the obfuscated and original line ranges. One obfuscated method can map to several records, because R8 inlines small methods into their callers, so a single frame resolves to a chain of source frames innermost first, with the obfuscated line selecting which records apply. Synthesized members are flagged and skipped.

A lookup binary-searches the class table, then the member table, then filters by line range, so resolution stays a handful of comparisons no matter how large the mapping is. The artifact is read in place: in disk-cache mode a crash retraces straight off the memory-mapped `.tw` with the name tables living in the OS page cache, while in memory mode the parsed mapping is held on the heap. In disk mode an incompatible artifact is rebuilt from the uploaded mapping. The throughput and memory trade between the two modes is measured on [Performance](/symbolicator/performance).

## Migrating from Honeycomb

Honeycomb symbolicates Android in its OpenTelemetry Collector, keying ProGuard mappings by the `app.debug.proguard_uuid` resource attribute and storing them as `<uuid>.txt`. Traceway reads that **same** attribute and `<uuid>.txt` naming on the OTLP path, so a migrating app does not change its instrumentation.

To move an app from Honeycomb to Traceway:

1. Point the OpenTelemetry Android SDK's OTLP exporter at Traceway's endpoint (`/api/otel/v1/traces`) with a Bearer project token.
2. Keep your existing `proguard-uuid` Gradle plugin, which sets `app.debug.proguard_uuid`.
3. Upload your `<uuid>.txt` mappings to Traceway (via the Gradle plugin above, or any POST to `/api/symbols/upload` with a `proguard_uuid` field).

Symbolication then happens in Traceway, in the collector processor or in the backend, with no Honeycomb collector in the path.
